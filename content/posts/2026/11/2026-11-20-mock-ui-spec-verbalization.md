AI エージェントに UI のモックを作らせると、数分でそれらしい画面ができあがります。ただ、モックの「見た目」や「振る舞い」が文章になっていないと、意図がうまく伝わりません。本番で実装し直すときや、別のエージェントに作業を渡すときに困ります。

この記事では、モックのプレゼンテーション層（見た目と振る舞い）を**言語化・仕様化する方法**を、A2UI・仕様駆動開発・デザイントークンの 3 つに分けて整理します。

- **UI を JSON で宣言する**：A2UI などの生成 UI プロトコル
- **振る舞いをテキストの仕様にする**：仕様駆動開発（SDD: Spec-Driven Development）の道具と記法
- **見た目をトークンと仕様書にする**：デザイントークンと画面仕様書

どれを選ぶかは、仕様を何に使うかで決まります。大きくは、**本番の実装につなげたい**のか、**AI に UI を安全に描かせるための共通の言葉がほしい**のか、です。デザイントークンはどちらの場合にも使えます。詳しくは最後の「目的別の選び方」の表で整理します。

## 登場するプロダクトと用語

| 名前 | 種類 | 一言でいうと |
|---|---|---|
| A2UI（Agent-to-User Interface） | 生成 UI の仕様 | Google が公開したオープンなプロトコル。エージェントが UI を宣言的な JSON で書き、クライアントが自前の部品で描く |
| Open-JSON-UI | 生成 UI の仕様 | OpenAI 社内の宣言的 UI スキーマを公開したもの（CopilotKit / AG-UI のドキュメントが紹介） |
| AG-UI | エージェントとアプリをつなぐプロトコル | CopilotKit が推進。UI の仕様そのものではなく、A2UI などを運ぶ双方向の通信層 |
| GitHub Spec Kit | SDD ツールキット | 仕様 → 計画 → タスク → 実装の流れとテンプレートを AI エージェントに持ち込む |
| Kiro | SDD 向け AI IDE | AWS の AI 開発環境。要件・設計・タスクの 3 文書を作ってから実装する |
| EARS 記法 | 要件の書き方 | `When <条件>, the <システム> shall <振る舞い>` のような決まった型で要件を書く |
| Gherkin 記法 | 振る舞いの書き方 | `Given` / `When` / `Then` でシナリオを書く。BDD（振る舞い駆動開発）で使われる |
| デザイントークン（W3C DTCG フォーマット） | 見た目の値の標準形式 | 色・余白・文字などの値を JSON で定義する |
| Figma MCP | デザインツールとの連携 | Figma のデザインデータを、MCP（Model Context Protocol：AI エージェントが外部のツールやデータを使うための標準プロトコル）経由でエージェントに渡す |

## 1. UI を JSON で宣言する（A2UI / Open-JSON-UI）

1 つ目は、AI エージェントに HTML や React のコードを直接書かせない方法です。エージェントには「どの UI 部品を、どう並べるか」だけを、決まった形式の JSON で書かせます。

### A2UI（Agent-to-User Interface）

**A2UI** は Google が公開したオープンなプロトコルです。考え方は次のとおりです。

- エージェントは UI の意図を**宣言的な JSON** で送る。実行できるコードは含まない
- 使える部品は、クライアント側が持つ**コンポーネントカタログ**の中から選ぶ。カタログに登録された部品しか描画されない
- 描画は React・Angular・Flutter など、クライアントが使っている技術で行う

エージェントが書けるのは「カタログにある部品の組み合わせ」だけなので、任意のコードを実行される心配がありません。また、同じ JSON をどのフレームワークでも描けます。

モックの「見た目の意図」を、特定のフレームワークに依存しない仕様として取り出したいときに相性のよい方法です。イメージとしては、次のような情報を JSON で表します。

```json
{
  "component": "Card",
  "children": [
    { "component": "Text", "text": "予約日時を選んでください" },
    { "component": "DateTimeInput", "label": "日時" },
    { "component": "Button", "label": "予約する", "action": "submit_reservation" }
  ]
}
```

※ 上の JSON は考え方を示すための簡略化した例で、A2UI の正式なスキーマではありません。実際の A2UI では、部品は入れ子にせず `id` 付きのフラットなリストで送り、親子関係は `children` に子の `id` を並べて表します。詳しくは [a2ui.org](https://a2ui.org/) の仕様を確認してください。

### AG-UI と Open-JSON-UI

似た名前で並べて語られることが多いのが、**AG-UI** と **Open-JSON-UI** です。ただし、この 2 つは役割が違います。

- **Open-JSON-UI**：A2UI と同じく、UI を JSON で宣言するための**仕様**
- **AG-UI**：エージェントとフロントエンドのあいだで、イベントや状態をやり取りするための**通信プロトコル**。AG-UI のドキュメントでも「AG-UI は生成 UI の仕様ではない」と説明されている

つまり、A2UI や Open-JSON-UI が「何を描くか」を表し、AG-UI はそれを「どう運ぶか」を受け持ちます。A2UI のメッセージは、AG-UI のほか、A2A（エージェント同士の通信プロトコル）、MCP、WebSocket など、すでに使っている通信路に載せて送れます。

## 2. 振る舞いをテキストの仕様にする（仕様駆動開発）

2 つ目は、画面の仕様や振る舞いを、あいまいさの少ないテキストの仕様に書き起こす方法です。AI に雰囲気で書かせる「バイブコーディング（Vibe Coding）」は速い反面、作り直しが多くなりがちです。それを防ぐために、仕様を先に固める考え方が**仕様駆動開発（SDD）**です。SDD の全体像は「[仕様駆動開発の概要](/blogs/posts/2026/11/spec-driven-development-overview/)」にまとめています。

### GitHub Spec Kit と Kiro

[GitHub Spec Kit](/blogs/posts/2026/11/github-spec-kit-intro/) や AWS の [Kiro](/blogs/posts/2026/11/kiro-ai-ide-intro/) は、要件・設計・タスクを Markdown の文書として管理します。この文書を、AI と人間が共通して参照する**唯一の情報源（Single Source of Truth）**にします。

本来は仕様から実装へ進む道具ですが、逆向きにも使えます。すでにあるモックのコードや画面をエージェントに読ませて、そこから仕様書を書き起こさせます（リバースエンジニアリング）。いったん仕様書にしておけば、以降の変更は仕様書を起点に進められます。

### EARS 記法と Gherkin 記法

モックの振る舞いを 1 文ずつ書き出すときは、決まった型を使うと解釈のぶれが減ります。

[EARS 記法](/blogs/posts/2026/11/ears-requirements-syntax/)では、たとえば次のように書きます。1 行目はイベントに反応する型（When）、2 行目は望ましくない状況に対応する型（If-Then）です。

```text
When the user clicks the "削除" button, the system shall open a confirmation modal.
If the input email is invalid, then the system shall display the error message in red.
```

1 つ目の振る舞いを [Gherkin 記法](/blogs/posts/2026/11/gherkin-bdd-cucumber/)のシナリオとして書くと、次のようになります。

```gherkin
Feature: 削除の確認
  Scenario: 削除ボタンを押すと確認モーダルが開く
    Given 一覧画面にアイテムが 1 件表示されている
    When 利用者が「削除」ボタンをクリックする
    Then 確認モーダルが表示される
```

Gherkin で書いておくと、Cucumber などのテストツールにつなげやすくなります。モックで確かめた振る舞いを、そのまま受け入れテストとして残せます。

## 3. 見た目をトークンと仕様書にする（デザイントークン）

3 つ目は、余白・配色・文字・部品の階層といった**見た目の仕様**を、テキストとして書き出す方法です。

### デザイントークン（W3C DTCG フォーマット）

**デザイントークン**は、色や余白などの値に名前を付けて JSON で定義したものです。W3C の Design Tokens Community Group（DTCG）が、その書き方の標準フォーマットを定めています。たとえば `design-tokens.json` として、次のように書きます。

```json
{
  "color": {
    "primary": {
      "$type": "color",
      "$value": {
        "colorSpace": "srgb",
        "components": [0.118, 0.435, 0.851],
        "hex": "#1e6fd9"
      }
    }
  },
  "spacing": {
    "md": { "$type": "dimension", "$value": { "value": 16, "unit": "px" } }
  }
}
```

現在の DTCG フォーマットでは、色の値を `"#1e6fd9"` のような文字列ではなく、色空間と成分を持つオブジェクトで書きます（`hex` は任意の補助）。古いツールや記事では文字列で書く例も多いので、使うツールがどの版に対応しているかを確認してください。

モックに直接書かれた `#1e6fd9` や `16px` をトークンに置き換えておけば、エージェントが勝手に似た色を作ってしまうことを防げます。デザイントークンを使って AI エージェントにデザインの意図を伝える方法は、「[AIエージェントにデザインの意図を伝える](/blogs/posts/2026/11/design-concept-and-design-tokens-for-ai-agents/)」で詳しく解説しています。

### エージェントに画面仕様書を書き出させる

モックが Figma にあるなら、**Figma MCP** を使って、デザインデータを Claude Code や Cursor などのエージェントに読ませる方法があります。エージェントは画面を見た目で推測するのではなく、デザインデータとして読めます。

モックがコード（React や HTML）にある場合は、エージェントに直接頼む方法が手軽です。たとえば次のように指示します。

```text
このモックの DOM 構造・CSS・状態遷移を解析して、画面仕様書を Markdown で出力してください。
画面遷移と状態遷移は Mermaid 図で書いてください。
振る舞いは EARS 記法で 1 行ずつ列挙してください。
色と余白は design-tokens.json のトークン名で書いてください。
```

出力された仕様書は、人間がレビューしたうえで次の実装の入力にします。

## 目的別の選び方

目的ごとの選び方をまとめます。

| 目的 | 向いている方法 |
|---|---|
| AI に UI を安全に描かせたい（チャットの中に UI を出すなど） | A2UI / Open-JSON-UI + AG-UI |
| モックを本番の実装につなげたい | Spec Kit / Kiro で仕様書にし、振る舞いを EARS / Gherkin で書く |
| 見た目のぶれをなくしたい | デザイントークン（DTCG フォーマット） |
| まず今あるモックの仕様を残したい | Figma MCP やエージェントに画面仕様書を書き出させる |

これらは組み合わせて使えます。たとえば、見た目はデザイントークンで固定し、振る舞いは EARS で書いて仕様書にまとめ、画面の一部だけを A2UI でエージェントに描かせる、といった構成です。

## まとめ

- モックを仕様にする方法は、**UI を JSON で宣言する**、**振る舞いをテキストの仕様にする**、**見た目をトークンと仕様書にする**、の 3 つに分けられる
- A2UI と Open-JSON-UI は UI の仕様、AG-UI はそれを運ぶ通信プロトコルで、役割が違う
- どれを選ぶかは、仕様を**本番の実装に使う**のか、**AI に UI を描かせる共通の言葉にする**のかで決まる。デザイントークンはどちらにも使える

まずは手元のモックをエージェントに読ませて、画面仕様書を 1 枚書き出させるところから始めると、どの方法が足りないかが見えてきます。上のプロンプト例をそのまま使えます。
