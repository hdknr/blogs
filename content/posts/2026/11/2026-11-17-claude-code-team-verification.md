## はじめに

Claude Code チームの Addy Osmani 氏が、X の記事機能で「[How the Claude Code team thinks about verification](https://x.com/addyosmani/status/2122590683055993308)」を公開しました。冒頭によると、Claude Code チームではコードのおよそ 9 割を Claude が書き、Claude がレビューしています。この規模になると、エージェントが自分の仕事を**証拠つきで検証できる**ように整えることが何より重要になる、というのが元記事の出発点です。

元記事の要点は次のとおりです。

**検証ループがあれば、Claude に任せられる仕事が増える。** 検証ループがなければ人間が全部を確かめることになり、同時に走らせられる Claude は 1〜2 個が限界になる。検証ループがあれば、数十〜数百を並列で走らせられる。

本記事では、元記事の前半「どのテストに投資するか」と後半「Claude Code チームの検証の進め方」を順に整理し、最後に自分のリポジトリへ持ち込むときの要点をまとめます。

## 用語の整理

先に、元記事に出てくる用語をまとめておきます。

| 用語 | 意味 |
|---|---|
| 検証ループ（verification loop） | エージェントが変更を実行・テストし、結果を見て直す、を繰り返す仕組み |
| E2E テスト | 「カートに入れる → 購入 → 確認画面」のような、実際のユーザー操作の流れを通しで確かめるテスト |
| プロパティテスト | 「常に成り立つはずの性質」を書き、ライブラリが生成した大量の入力で反例を探すテスト |
| 差分テスト（differential test） | 旧システムと新システムに同じ入力を与え、出力の違いを探すテスト。旧システムが正解（オラクル）になる |
| `verify` スキル | アプリの起動・操作・確認の手順を Claude に覚えさせるためのスキル（`.claude/skills/` に置く） |
| Code Review | Claude Code の PR 自動レビュー機能（製品名。一般名詞の「コードレビュー」と区別する） |
| `REVIEW.md` | Code Review に、このリポジトリで何に注意してレビューすべきかを伝えるために置くファイル |
| observe モード | 新しいゲートを、ブロックはせず「ブロックしていたはず」をログに残すだけで動かすモード |

## なぜ検証が効くのか

元記事は、検証の効果を社内の数字で示しています。構造化ファイルを生成するタスクで社内テストをしたところ、別の採点役（grader）がルーブリック（評価基準表）に照らして Claude の出力をチェックすると、タスク成功率が上がりました。通常のプロンプトのループと比べて、最大 10 ポイントです。伸びが最も大きかったのは、いちばん難しい問題でした。

もう一つの理由はコストの変化です。テスト・ベンチマーク・仕様・実際の E2E 実行は、以前は用意するのが高くつく検証手段でした。いまはエージェントがコードと同じように素早く生成できます。しかも一度できたテストはソフトウェアとして走るので、何度実行してもトークンはほとんど増えません。

さらに、検証の結果をエージェントの改善に戻すこともできます。たとえば「ログにユーザーデータが出ていないか」を見るテストにエージェントが何度も落ちるなら、hook を作るか `CLAUDE.md` にルールを明記します。これで同じ問題は（ほぼ）起きなくなる、と元記事は述べています。

## 投資する価値のある 3 種類のテスト

どの種類を選んでも、避けるべき失敗が 2 つあります。

- **不安定（flaky）なテスト**: エージェントは、失敗したコードを直すのではなく「もう一度走らせる」ことを覚えてしまう
- **遅いテスト**: エージェントはテストの回数を減らすので、どの変更で壊れたのかを特定しにくくなる

元記事は、重いテストはコミット前の段階で走らせるよう勧めています。そのうえで、投資する価値が高いテストとして次の 3 種類を挙げています。

### 1. E2E テスト — 1 種類だけ選ぶならこれ

テストを 1 種類に絞るなら E2E テストを選べ、というのが元記事の推奨です。E2E テストは**ごまかしにくい**からです。機能全体が動くか動かないかのどちらかしかなく、完了の基準がはっきりしていて、何が壊れているかを具体的に示せます。

ユニットテストは速くて不安定さも少ないものの、テストが通っても機能が壊れていることがあります。エージェントもテストもタスクの全体像を理解していないためです。元記事の図では、ユニットテストが「Error: Timeout after 30 seconds」としか言わないのに対し、E2E テストは何が壊れているかをスクリーンショットと説明で示せる、と対比されています。

E2E テストでは、エージェントに**実際に動いているシステムを触る手と見る目**を与えるのが効果的です。スキルを使って、[CDP（Chrome DevTools Protocol）](https://chromedevtools.github.io/devtools-protocol/)・シミュレーター・API ハーネスなどでアプリを起動し、操作し、確認させます。

機能一覧（feature map）は、エージェントにとっての手引きにも採点基準にもなります。機能一覧には普通、ユーザー視点の機能ごとに、画面の遷移・キーボードショートカット・セレクター・期待される結果が書かれているからです。

### 2. プロパティテスト（Hypothesis / fast-check）— 壊れてはいけない制約

多くのテストは「何が起こりそうか」という作り手の想像に基づいています。プロパティテストは、人が見落としがちなエッジケースを突きます。そしてエッジケースこそ、エージェントがよく失敗する場所です。

やり方は、「絶対に成り立つはず」という性質を書き、テストライブラリに反例を探させるだけです。ライブラリは数千通りの入力を生成して、その性質を破ろうとします。

| 言語 | ライブラリ |
|---|---|
| JavaScript / TypeScript | [fast-check](https://fast-check.dev/) |
| Python | [Hypothesis](https://hypothesis.readthedocs.io/en/latest/) |
| Rust | [proptest](https://proptest-rs.github.io/proptest/) |

ほとんどのプロジェクトには、次のような性質がたくさんあります。

- **往復（round-trip）**: X をエンコードしてデコードすると X に戻る。パースとシリアライズにも当てはまる
- **不変条件（invariant）**: 「口座残高は決して負にならない」のように、常に真であるべきこと
- **冪等性（idempotency）**: マイグレーション・正規化・リトライなどを 2 回やっても 1 回と同じ結果になる
- **等価性（equivalence）**: 最適化したコードが、素朴だが正しいコードと同じ結果を返す

Python の Hypothesis で往復の性質を書くと、たとえば次のようになります。

```python
import json
from hypothesis import given, strategies as st

# JSON で表現できる値を再帰的に生成する
json_values = st.recursive(
    st.none() | st.booleans() | st.integers() | st.text(),
    lambda children: st.lists(children) | st.dictionaries(st.text(), children),
)

@given(json_values)
def test_json_round_trip(value):
    assert json.loads(json.dumps(value)) == value
```

元記事は、プロパティテストのライブラリを**エージェントのごまかしを防ぐ（keep agents honest）**手段として位置づけています。入力が、元のコードを書いたエージェントと同じバイアスで作られていないからです。仕様が本番の挙動とずれ、検証の拠り所にならなくなったシステムもあります。その書き直しにも特に役立つ、としています。

### 3. 差分テスト — 旧システムが正解になる

差分テストは、機能が変わらないはずの大規模な移行で特に効果を発揮します。旧システムと新システムを同じ入力で動かし、結果が違えば、それは直すべきバグか破壊的変更です。

ポイントは 3 つあります。

- 入力には、ランダムに生成したものか、本番トラフィックのサンプルを使う
- 空白など、比較に関係のない違いは正規化して消す
- 新環境で意図的に変える挙動は、「承認済みの変更」として一覧で管理する

## Claude Code チームの検証の進め方

元記事の後半は、Claude Code チーム自身のやり方です。以前公開された「[Solving code review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)」の続編として、検証をより深く掘り下げています。

### 検証とは「変更を実行すること」

**テストより、アプリを端から端まで動かすことのほうが大事**だ、と元記事は言い切ります。iOS の変更をシミュレーターで試さずに出荷する人はいません。Claude も同じです。

Claude は人間や QA エンジニアと同じようにアプリ全体をテストできます。対象ごとの手段は次のとおりです。

| 対象 | 手段 |
|---|---|
| Web | Claude の Chrome 拡張 |
| モバイル | iOS / Android の MCP |
| デスクトップ | コンピューター操作（computer use） |
| バックエンド | サービスをローカルで起動 |

起動や操作の手順は、**`verify` という名前のスキル**にまとめます。関係するコードにできるだけ近いディレクトリの `.claude/skills/` に置き、必要なだけ増やしてかまいません。元記事によれば、Claude はコミット前に `verify` スキルを使うことを心得ています。

そのうえで、`verify` スキルを速く確実にすることに投資します。Claude に改良と負荷試験を繰り返させます。`verify` スキルはスモークテストのハーネスなので、盤石であってほしいからです。Anthropic では、ほぼすべての変更をこの方法でテストしているそうです。

### 失敗したチェックだけが人間を呼ぶ

すべての変更を人が読むことはできません。そこで、失敗したチェックを**人の手が必要な変更の目印**にします。Claude がチェックを走らせ、失敗したものを直そうとします。3 回やり直しても失敗が残れば、Claude は手を止めて人間を呼びます。

### チェックはコードの持ち主が書く

コードの持ち主が、そのコードのチェックを書きます。持ち主が指摘するであろうことを指摘できるまで磨き込みます。チェックがレビュアーを呼ぶときは、**なぜ呼んだのかを書く**ことも求めます。そうすればレビュアーは、差分から理由を推理せずに済みます。

### 信頼性チェックは差分をきっかけに発動する

チームには 39 項目の信頼性チェックリストがあります。各項目は次の 3 つを持ちます。

- 差分から読み取れる**発動条件（trigger）**
- 実施する**チェック**
- その項目のもとになった**障害や PR**

例として挙がっているのが「`--resume` が古いトランスクリプトを読み込める」という項目です。セッションの保存形式やメッセージ型が変わったら、新しく足したフィールドを安全に読み込めるかを問います。古いトランスクリプトにはそのフィールドがないからです。

Claude は差分を読み、発動条件に当てはまる項目（たいてい 3〜10 個）だけをチェックします。これで、過去の障害を誰かが暗記しておく必要がなくなります。

### レビュアーは 1 人、ラウンドを重ねる

レビューの質を上げるために、レビュアーを積み増すことはしません。主レビュアーの上に、より高価な 2 人目のレビュアーを重ねるのは、主レビュアーを調整するより悪手であることが多い、としています。代わりに、そのコードでレビュアーが何に注意すべきかを [`REVIEW.md`](https://code.claude.com/docs/en/code-review-customize) に書きます。

また、レビューと検証のラウンドは積み上げていくべきだ、とも述べています。各ラウンドに、それまでのラウンドの文脈や過去の失敗を渡し、毎回ゼロから全部を見直すことはしません。そのほうが安く、見つかるものも多いからです。

### 変更が自分を裁くチェックを書き換えられないようにする

変更が、自分を判定するチェックを書き換えられるなら、そのチェックは壊れています。Code Review は `REVIEW.md` を、PR の変更からではなく、ベースブランチまたはデフォルトブランチから読みます。チームは、変更を止めるルールを、その変更が書き換えられないブランチに置いています。

なお、公式ドキュメントによると `REVIEW.md` を読むのは Code Review サービスで、ローカルで実行する `/code-review` コマンドは読みません。また、この仕組みはデフォルトブランチが保護されていることを前提にしています。

レビューはコミットに対して行います。レビュー中に誰かが push したら、そのレビュー結果はもう役に立ちません。**古いコミットに対する合格のレビューには意味がない**からです。

### 安いチェックを先に走らせる

エージェントがローカルでテストせずに push すると、自分で見つけられたはずのバグのために、共有のレビュー時間と CI 時間を使ってしまいます。Claude Code チームでは、Claude がプルリクエスト（PR）を開く前にテスト・ビルド・リンターを走らせます。

この順序は 2 つの方法で強制できます。1 つは [hook](https://code.claude.com/docs/en/hooks) で、Claude が作業を終えたときにテストを走らせる設定です。もう 1 つは [`/goal`](https://code.claude.com/docs/en/goal) で、Claude が目指す完了条件として「テストスイートが通ること」を設定します。

### 新しいゲートは observe モードで始める

チームのリポジトリでは、各コミットに「どう検証したか」の印を付けています。印には「none（検証なし）」もあり、検証されなかったコミットを後から検索できます。

さらに、セッションの中で `/code-review` か `/verify`（`verify` スキルの呼び出し）が実行されていなければコミットを止めるコミットゲートを作りました。モードは off・observe・enforce の 3 つです。

| モード | 挙動 |
|---|---|
| off | 何もしない |
| observe | 止めるはずだったコミットをログに残すだけ。誤検知を見直し、誰も困っていないことを確かめる |
| enforce | コミットを止める。ただし、検証しなかった理由をコミットメッセージに書けば通せる |

enforce モードには、さらにもう一つ逃げ道があります。同じセッションで 2 回止められたら、次のコミットは通します。Claude Code は完璧ではないので、Claude が身動きできなくなるのを避けるためです。

### チェックを、本当に大事なもので試す

チームは定期的に**レビュアーをレビュー**しています。追っている指標は次の 2 つです。

- マージ後に revert された変更の数
- マージ前にメンテナーが却下した変更の数

比較の基準として、問題が起きなかった変更から規模をそろえて抜き出したサブセットも使います。

正式な評価も行えます。Code Review チームは、過去の障害と revert をもとに評価セットを作りました。手順は次のとおりです。

1. 各事例について、レビュー時点の状態にリポジトリを再現する
2. 「バグは何だったか」を 1 文で書いた模範解答を用意する
3. そのバグを正しく説明した指摘だけを得点にする
4. 過剰な指摘を防ぐため、マージ済みで安定している変更を対照群にする
5. 調整用のデータは、評価に使う固定のテストセットから分けておく

再現率（recall）も、生の指摘・検証後・最終レビューの 3 段階で別々に測ります。こうすると、一度見つけたバグを途中の段階で落としていないかが分かります。パイプライン全体を通した 1 つのスコアで評価すると、この違いは見えません。

正しさに加えてチームが重視するのが、**その指摘をどれだけ優先して直すべきか**という重要度です。良いレビュアーは技術的に正しい指摘をほとんど拾います。しかし人が知りたいのは、それが必ず直すべきものか、直したほうがよいものか、細かい好みの話かです。[Code Review](https://code.claude.com/docs/en/code-review-pull-requests) は指摘に Important・Nit・Pre-existing のタグを付けます。Pre-existing は「もともとあったバグなので、作者の責任にしない」という意味です。

最後に、再現率を上げ続けるのは、それ以上の改善が評価セットへの過剰適合にしかならなくなる手前まで、と元記事はしています。

### 見逃しをルールに変える

Claude Code のリポジトリでは、見逃しをルールに変える方法が 2 つあります。

#### 1. 人間のレビューコメントと revert からパターンを抜き出す

よくある問題を見つけるため、人間のコードレビューのコメントと PR の revert からパターンを抽出します。ルール候補になる条件は、少なくとも 2 つの PR で起きていて、かつ差分から見分けられることです。候補に対しては 3 つのエージェントが反証を試み、最後は人間が PR でレビューして承認します。

#### 2. 既知の障害に対してバグ探しを再実行する

既知の障害に関係する PR に対して、3 つのバグ探しエージェントを再実行します。2 つ以上がバグを見つければ、そのバグは「検出可能」です。小さな差分なのに見逃されたなら、それは `REVIEW.md` にルールとして書く価値のある穴です。

### 増え続けるものを刈り込む

前半で触れた不安定なテストについても、チームのルールは明確です。Claude はテストを飛ばしたり、sleep を足したり、通るまでリトライしたりできません。根本原因が見つからなければ、テストを削除して、その理由を書き残します。

ルールそのものも刈り込みが必要です。テストスイート、検証の手順、`.md` ファイルは、放っておけば増える一方です。チームは定期的に整理しています。

### 元記事の結論

元記事は、検証の層も、ほかのシステムと同じように扱うよう求めています。

- 判定する変更の手が届かない場所に置く
- 自分にとって重要だったバグで採点する
- 見逃したら教訓を書き残し、同じことが 2 度起きないようにする
- 教訓は、走らせる価値があり続けるよう刈り込む

そうすれば、人間の仕事は「すべての差分を読むこと」から「何をもって完了とするかを定義し、証拠をレビューすること」に移ります。それこそが、多くの Claude を同時に走らせることを可能にする、と元記事は締めくくっています。

## 自分のリポジトリに持ち込むなら

すぐに試せる順に並べると、次のようになります。

| 順番 | やること | 本記事の該当箇所 |
|---|---|---|
| 1 | アプリの起動・操作・確認を `verify` スキルにまとめ、コミット前に必ず走らせる | 検証とは「変更を実行すること」 |
| 2 | テスト・ビルド・リンターを hook で PR 作成前に走らせる | 安いチェックを先に走らせる |
| 3 | `REVIEW.md` をベースブランチ側に置き、PR から書き換えられないようにする | 変更が自分を裁くチェックを書き換えられないようにする |
| 4 | 不変条件・往復・冪等性をプロパティテストにする | 2. プロパティテスト |
| 5 | 新しいゲートは observe モードで始め、誤検知を見てから enforce にする | 新しいゲートは observe モードで始める |
| 6 | 見逃したバグを `REVIEW.md` やチェックリストに「発動条件つき」で書き足し、定期的に刈り込む | 見逃しをルールに変える／増え続けるものを刈り込む |

## まとめ

- エージェントに任せられる量は、**検証ループの強さ**で決まる。検証がなければ、人間がボトルネックになる
- 1 種類だけ選ぶなら **E2E テスト**。ごまかしにくく、壊れた箇所を具体的に示せる。プロパティテストはエージェントのバイアスを持たない入力で、差分テストは旧システムを正解として、それぞれ補強する
- Claude Code チームは、**実際にアプリを動かす `verify` スキル**、3 回で人間を呼ぶ失敗処理、差分で発動するチェックリスト、PR から書き換えられない `REVIEW.md` で検証を組み立てている
- レビュアーを増やすより、**1 人のレビュアーを調整し、ラウンドを積み上げる**
- 検証の層そのものも評価し、見逃しをルールに変え、ルールを刈り込み続ける
