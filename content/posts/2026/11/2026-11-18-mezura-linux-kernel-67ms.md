## はじめに

Rust 製のコード行数カウンタ **mezura** が、Linux カーネル（v6.15）の約 3,600 万行・約 6 万 3,700 ファイル・合計 1.37GB を **67 ミリ秒**で数え切る、という記事を X で柴田 淳 氏が紹介していました。作者の Petros Papatheodorou 氏による解説記事 [What it takes to count the Linux kernel's 36M lines of code in under 70ms](https://petros-papatheodorou.dev/writing/mezura/counting-the-linux-kernel/) は、単なる自慢話ではありません。「プロファイラに騙された話」「Windows のフィルタドライバに足を引っ張られた話」「速くしたら正確にもなった話」が詰まった、最適化の教科書のような内容です。

この記事では、その元記事の要点を日本語で整理し、ふだんの開発にも持ち帰れる教訓をまとめます。数値はすべて元記事の計測値で、マシンは Ryzen 7 9700X（8 コア 16 スレッド）、ページキャッシュが温まった状態です。Linux の数値は Debian 13 / ext4、Windows の数値は同じマシンの Windows 11 / NTFS で測られています。

## 用語の整理

| 用語 | 意味 |
|---|---|
| 行数カウンタ | ソースコードを「コード行・コメント行・空行」に分類して数えるツール。`tokei` や `scc` が有名 |
| SIMD | 1 命令で複数データを処理する CPU 命令。ここでは AVX2 / AVX-512（x86_64）と NEON（aarch64） |
| SWAR | SIMD 命令を使わず、64bit 整数演算で 8 バイトをまとめて処理するテクニック |
| 壁時計時間 | 実際に経過した時間（wall-clock time）。全スレッドの CPU 時間の合計とは別物 |
| フレームグラフ | プロファイラのサンプルを関数の呼び出し階層ごとに積み上げて描いた図 |
| IPC | Instructions Per Cycle。1 クロックサイクルあたりに実行できた命令数 |
| レキサ | 字句解析器。ソースを左から読み、コメント・文字列・コードを切り分ける部分 |
| PGO | Profile-Guided Optimization。実行プロファイルを元に再コンパイルする最適化 |
| ミニフィルタドライバ | Windows のファイル I/O に割り込むカーネルドライバ。ウイルス対策や暗号化が使う |
| ハードウェアの床（floor） | その処理をこのマシンで実行するのに最低限かかる時間 |

## 0.4 秒から 67ms までの道のり

mezura の処理時間は、段階的に次のように短縮されました。

| 処理時間 | 主な変更 |
|---|---|
| 約 0.4 秒 | v2.0.0。`str::lines()` で行に分け、行ごとに区切り文字を検索し、行ごとに整形済みコピーを作成 |
| 166ms | まだ safe Rust のみ。コピーをバイト範囲（スライス）に置き換え、ファイルをバッチで受け渡し |
| 88ms | 64 バイトブロック単位の SIMD 1 パス、大きなファイルは `mmap`、初めての `unsafe` |
| 67ms | 「普通の行」をブロック単位で一括分類、ホットループを CPU 世代別にコンパイル、単一のテーブル駆動レキサ |

なお、このマシンでの理論上の下限（ハードウェアの床、ディレクトリ走査＋読み込み＋簡易パーサ）は約 41ms です（教訓 1 参照）。

67ms の時点で、比較対象のツールとは次のような差がついています（機能を揃えた equal-work モード、30 回計測の平均 ± 標準偏差）。

| ツール | Linux (ext4) | Windows (NTFS) |
|---|---|---|
| mezura 3.5.0 | 67ms ± 2 | 175ms ± 15 |
| scc 4.1.0 | 208ms ± 3 | 521ms ± 36 |
| tokei 15.0.0 | 411ms ± 3 | 617ms ± 20 |

## 教訓 1: 「ハードウェアの床」を先に測る

フレームグラフだけを見て最適化していると、目立つボトルネックを潰し終えた段階で「もう限界だ」と思い込みがちです。どの関数も突出していない状態で 1〜2% の改善に何日もかかるようになると、それがハードウェアの限界に見えます。しかし実際には **今のアーキテクチャの局所最適** にすぎないことが多い、というのが作者の主張です。

そこで作者は、`opendir`/`readdir`・`open`/`read`/`mmap`・pthread・`<immintrin.h>` だけで書いた単一の C プログラム（`gcc -O3 -march=native`、ホットパスでヒープ確保なし）を用意し、段階的に床を測りました。

| ステップ | 内容 | 時間（16 スレッド） |
|---|---|---|
| 1. メモリ帯域 | 1.37GB をメモリから 1 回流す（約 60GB/s から計算） | 23ms |
| 2. ファイル I/O のみ | パスは既知、全ファイルを open・read・close | 30.4ms |
| 3. 走査＋読み込み | `readdir` での並行走査と読み込み（中身は見ない） | 35.9ms |
| 4. 走査＋読み込み＋SIMD＋状態機械 | 3 に SIMD パスと最小限の状態機械を追加 | 40.8ms |

個別に測ったコストは単純には足し算になりません。この床計測プログラムでは走査単体が 2.9ms ですが、読み込み（30.4ms）と同時に走らせると 35.9ms になります。走査スレッドと読み込みスレッドが同じコアやカーネルの VFS 構造を取り合うためです。

作者がこの床を測ったのは mezura がすでに 88ms で動いていたころで、「もうこれ以上は速くならない」と思いかけていた矢先でした。床が約 41ms（最良 40.8ms、中央値 42.3ms）だと分かったことで、**88ms のうち半分以上はまだ自分のコードが使っている** ことがはっきりし、さらなる高速化に踏み出せたわけです。

## 教訓 2: プロファイラの数字は逆を指すことがある

### フレームグラフは「消したら何 ms 戻るか」を教えてくれない

フレームグラフのサンプルの 2〜5% を占める小さな処理を削除しても、壁時計時間がまったく変わらないことが 3 回ありました。アウトオブオーダー実行の CPU は安くて頻繁な命令を周囲の処理と並行してパイプラインに流すため、それを消しても空くサイクルはゼロです。安定して効いたのは **関数呼び出しそのものを丸ごと消す** 変更だけでした。

### 分岐予測ミスを減らしたら遅くなった

行ごとに空白をトリムするバイトループを、分岐のない SWAR 演算に置き換えたところ、

- 分岐予測ミス: **14% 減少**
- 命令数: **16% 増加**
- 実行時間: **12% 悪化**

という結果になりました。元のバイトループは単に短いから速かったのであって、分岐レス化で 1 行あたり 0.17 回の分岐予測ミスを減らす代わりに、毎行約 75 命令を余計に実行していたのです。CPU の内部指標が改善しても、プログラム全体が速くなるとは限りません。

### プリエンプトされたスレッドの経過時間は CPU コストではない

mezura は、ディレクトリを走査してファイルパスを渡す「走査スレッド」と、パスを受け取ってファイルを読み・数える「消費者スレッド」に仕事を分けています。スレッドごとのフェーズタイマーを仕込んだところ、Linux では走査スレッドが実行全体（約 110ms）のうち 90ms にわたって動き続けており、走査が遅く見えました。しかし mezura の走査を単体で測ると 13ms で終わります。4 本の走査スレッドが、16 ハードウェアスレッドを埋め尽くす 32 本の消費者スレッドにプリエンプトされていただけでした。

Windows でも同様に、タイマー上は `File::open` が消費者時間の 62〜70% を占めていましたが、CPU サンプルでは 17% にすぎませんでした。`CreateFileW` の中でプリエンプトされたスレッドはタイマーが回り続けるためです。

### プロファイルに出てこないシステムコール

`perf stat` で見ると、1 回の実行で `sched_yield` が 66,831 回、`clock_nanosleep` が 18,628 回（全システムコールの 23%）呼ばれていました。キューを待つスレッドのものですが、スリープ中のスレッドは CPU に乗っていないため、CPU フレームグラフには 0.00% としか出ません。

そこでアイドルな消費者が忙しい消費者からファイルを盗む（work stealing）ようにしたところ、最初と最後の消費者の終了差は 25ms から 0.3ms に縮んだものの、壁時計時間はどのスレッド数でも改善せず、既定の 64 消費者では逆に 4% 遅くなりました。アイドルスレッドが同じ物理コアのハイパースレッド上で他のキューを覗いてスピンし、働いているスレッドの実行資源を奪っていたからです。しかも本当の末尾（テール）は、24MB もある自動生成の AMD GPU レジスタ定義ヘッダを 1 スレッドが解析する時間で、これはそもそも分割できませんでした。work stealing が効いたのは、消費者の既定数を 64 から 32 に減らし、盗むのをディレクトリ走査の完了後に限定してからでした（93.0ms → 88.5ms）。

## 教訓 3: ファイル I/O は Linux と Windows で別物

同じマシンでも、Linux（ext4）では 67ms の実行で消費した CPU 時間が全スレッド合計でユーザー空間 0.62 秒・カーネル 0.28 秒で、パーサ律速です。一方 Windows（NTFS）では 175ms かかり、ユーザー 1.14 秒・カーネル 1.30 秒と、CPU 時間の半分以上がカーネル内のファイル open/read/close とディレクトリ列挙に消えています。

### Linux: 63,934 回の `statx` を避ける

Rust の標準ライブラリはファイルを最後まで読むとき、まずサイズを問い合わせ、`read` を 2 回呼びます（2 回目が 0 を返して EOF を確認する）。Linux の `getdents64` はサイズを返さないので、走査中にサイズを取ると `statx` がファイル数ぶん、カーネルツリーで 63,934 回発生します。

mezura では、走査スレッドはサイズ 0 を渡し、消費者スレッドは次のように読み分けます。

1. スレッドローカルな 64KiB バッファに 1 回だけ `read` する。カーネルのファイルの 95.7% は 64KiB 未満なので、短く返った時点で「全内容」「正確な長さ」「EOF の証明」が 1 システムコールで揃う
2. バッファを埋め切った 2,778 ファイルだけが `fstat` を呼ぶ
3. 256KiB 以上のファイルは `mmap` する。この変更で壁時計時間が 9% 短縮し、ページフォルトは半減した。ただし直近 5 秒以内に更新されたファイルは `read` にフォールバックする。マップ中のファイルを切り詰められると `SIGBUS` でプロセスが落ちるため

### Windows: D ドライブだけ 36% 遅い謎

ページキャッシュに完全に載った同じ Linux カーネルのチェックアウトを数えるのに、`D:\` では `C:\` より 36% 長くかかる（611ms 対 450ms）という現象がありました。ディスク読み込みはゼロ、Defender の除外設定も D のほうが手厚く、NTFS の設定も同一です。

原因は管理者権限で `fltmc instances` を実行して判明しました。`D:\` にだけ **wcifs（Windows Container Isolation）** と **FileCrypt** という 2 つのミニフィルタドライバがぶら下がっていたのです。きっかけは、数か月前に「新しいコンテンツの保存先」で Microsoft Store アプリなどの保存先を D ドライブに変えたことでした。これにより Windows は、これらのフィルタを D ドライブの全 I/O に差し込んでいました。`fltmc detach FileCrypt D:` を実行するとカーネル CPU 時間が半減し（4.9 秒 → 2.5 秒）、D が C より 10% 速くなりました。

しかも設定を戻しても、再起動のたびにフィルタは再アタッチされます。作者は起動時に SYSTEM 権限のスケジュールタスクで `fltmc detach` を実行して対処しているそうです。

さらに、A/B 比較のために `mezura.exe` を `candidate.exe` や `control.exe` にコピーすると 24〜32% 遅くなる現象もありました。Defender のプロセス除外は **ファイル名** で一致させるため、`mezura.exe` はリアルタイムスキャンを免れ、名前を変えたコピーは 63,700 回のファイルオープンのたびに検査されていたのです。ベンチマークでバイナリ名を変えるときは要注意です。

## 教訓 4: SIMD とビット演算で「行」をまとめて処理する

### 64 バイトブロックごとの SIMD パス

88ms に到達した変更では、「ファイルを行に分けてから各行で区切り文字を探す」のをやめ、64 バイトブロックごとに AVX2（x86_64）または NEON（aarch64）で 1 パス走らせ、2 つの `u64` ビットマスクを作るようにしました。

- `newlines`: 改行の位置
- `candidates`: コメント・文字列・エスケープが始まる／終わりうるバイトの位置

この SIMD ルーチンは Claude の助けを借りてプロトタイプを作り、ランダム入力でスカラー実装と突き合わせてテストしたそうです。この変更だけで壁時計時間 15%、ユーザー CPU 20% の削減になりました。Linux カーネルの行の 87.6% は `"` も `/` も含まないため、複数行コメントや文字列の途中でない限り、こうした行は区切り文字のスキャン自体が不要になります。

`unsafe` の扱いも慎重です。166ms まではワークスペース全体が `#![forbid(unsafe_code)]` でしたが、SIMD と `mmap` のためにコアライブラリだけ `#![deny(unsafe_code)]` に緩め、**壁時計時間で明確に効くときだけ** 個別の `unsafe` ブロックを許可しています。実際、行スライスごとに `from_utf8_unchecked` を使う変更は命令数を 7% 減らしたものの、ホットループのコード配置が変わって IPC が 2.25 から 1.93 に落ち、CPU サイクルが 8.6% 増えたため却下されました。

### 二進数の繰り上がりで行を一括分類する

67ms への決め手の 1 つが、加算の繰り上がり（キャリー）を使った行の一括分類です。

`!newlines` は行の内側のバイトが 1、`\n` の位置が 0 のマスクです。これに「単語文字（英数字など、記号でも空白でもない文字）の位置」のマスク `words` を足すと、行内に単語文字が 1 つでもあれば、そこから繰り上がりが 1 の並びを伝わって、その行末の `\n` の位置の 0 を 1 に反転させます。単語文字が無い行では繰り上がりが届かず、`\n` の位置は 0 のままです。非空白文字のマスク `content` にも同じ計算をします。以下は元記事のコードからの抜粋で、`add_with_carry` はキャリー付きの 64bit 加算、`carried` は前のブロックから引き継いだキャリーです。

```rust
let not_newlines = !newlines;
let (words, words_out) = add_with_carry(not_newlines, classes.words, carried.0);
let (content, content_out) = add_with_carry(not_newlines, classes.content, carried.1);
let (word_lines, content_lines) = (words & newlines, content & newlines);
```

あとは `count_ones()` を 3 回（`word_lines`、`content_lines & !word_lines`、普通の行の改行位置 `plain & !content_lines`）呼ぶだけで、64 バイトブロック内の普通の行を「単語を含む行」「記号だけの行」「空行」に一括で数えられます。ビット 63 からの繰り上がりは次のブロックに引き継ぎます。平均行長が 64 バイトを超えるファイルは行ごとのループにフォールバックし、長い行が並ぶ AMD GPU のレジスタ定義ヘッダが遅くならないようにしています。

### CPU 世代ごとにホットループをコンパイルする

Rust の既定の x86-64 ターゲットは `popcnt` を有効にしないため、`u64` の `count_ones()` は 19 命令のソフトウェア実装になります。そこで `#[target_feature]` でホットループを 3 種類（ベースライン、AVX2＋popcnt/bmi、AVX-512）コンパイルし、実行時にファイルごとに選ぶようにしました。単一のポータブルなバイナリのまま、壁時計時間が 5〜9% 短縮されています。

## 教訓 5: 速くしたら正確にもなった

冒頭で触れた X のポストでも注目されていたのがこの点です。

候補バイトを含む残り 12.4% の行について、旧パーサは 1 行ごとに 4 種類の区切り文字リストを作り、330 行のインデックス計算で重なりを解決していました。これを **左から右へ 1 つのカーソルで進み、事前コンパイルした状態遷移テーブルで処理するレキサ** に置き換えたところ、カーネル全体の命令数が 21% 減り（3.4.0 → 3.5.0）、PGO ビルドで 80ms から 67ms になりました。

同時に、バグも消えました。`/`・`*`・`"`・`x`・空白をランダムに混ぜた入力を 20 行の参照レキサと突き合わせる小さなファザーが、数分で C の `/* x /*/` という入力を見つけました。旧パーサでは区切りの重なりの解決を誤り、ファイルの残り全体をブロックコメントとして数えてしまうバグで、実在の 37 万 8,000 ファイルでは見つかっていなかったものです。

テーブル駆動のレキサは明示的な状態を持って左から右に読むため、`/*` でコメントを開いた後に、その `*` を `*/` の開始として再利用することがありません。重なりを解決するステップ自体が不要になったのです。状態が分かっていることで、JavaScript の正規表現リテラルと除算の区別、文字列補間 `${...}` の中の字句解析、HTML のタグ内だけでの引用符の扱い、といった文脈依存のルールも素直に書けるようになりました。

80 以上の対応言語はすべてこの 1 つのエンジンで動いています。言語ごとの定義（コメントの対、文字列の区切り、エスケープ規則、ネスト、正規表現の文脈、補間の区切り）はプレーンテキストの設定ファイルに書かれ、初回使用時に遷移テーブルにコンパイルされます。

### 正確さにはコストがかかる

一方で、正確さはタダではありません。3.5.0 で入れた正規表現リテラル・文字列補間・HTML タグの引用符・PHP のページ境界の修正で、カーネルの命令数は 2.3% 増えました。`struct` や `class` が本当に型定義の開始かを確かめる処理は、既定設定の実行でさらに 2.6〜2.9% かかりますが、これはカーネルの `.c` ファイルで「単語 `struct` の出現 120 万回」と「実際に定義された構造体 33,589 個」の違いになります。

正確さの担保として、作者は **LineJudge** という適合性テストスイート（v0.4.0 で 107 個の難しいエッジケースファイル）を作り、CI で毎回実行しています。LineJudge は「正しい行数」を 1 つに決めるわけではありません。言語仕様に従って文字列とコメントのバイト範囲だけを定め、各カウンタはそれぞれの数え方の宣言に照らして検査されます。mezura 3.5.0 は 107/107 をパスしています。

さらに JavaScript の正規表現リテラルについては、38,433 個の実在 JS ファイルで acorn 8.15.0 と照合しました。48,114 個中 48,070 個がバイトオフセットまで一致し、残り 44 個も行数には影響しませんでした。

## まとめ

mezura の高速化の記録から、次のような教訓が引き出せます。

- **最初に「ハードウェアの床」を測る。** 床が分かれば、自分が限界にいるのか局所最適にはまっているのかを判断できる
- **プロファイラの指標を鵜呑みにしない。** 分岐予測ミスを減らしても遅くなる、フレームグラフ上の 2〜5% を消しても何も変わらない、プリエンプト中の経過時間はコストではない
- **I/O は OS とその設定で別物になる。** Windows ではミニフィルタドライバや Defender のファイル名ベースの除外が、ベンチマーク結果を大きく揺らす
- **設計を素直にすると、速さと正確さが両立することがある。** 状態遷移テーブルのレキサは、命令数を減らしながら重なりのバグを構造的に消した
- **正確さはテストで担保する。** ファザーと参照実装の突き合わせ、適合性スイートを CI に組み込む

元記事は 2 部構成の 1 本目で、続編では LineJudge のルールエンジンが取り上げられる予定です。行数カウンタに興味がなくても、パフォーマンスチューニングに関わる人なら一読の価値がある記事です。
