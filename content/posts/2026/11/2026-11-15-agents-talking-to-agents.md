## はじめに

X でこんな投稿が流れてきました。Claude Code の生みの親 Boris Cherny の発言として、「もうエージェントとは話さない。自分のエージェントが、ほかのエージェントと話している」という一文を引いたものです（[元の投稿](https://x.com/soniacuts/status/2121573866921484557)）。添付の約 11 分の動画が本題で、エージェント中心の開発がどこへ向かうかを語る内容だと紹介されています。

この記事では動画の中身には踏み込みません。代わりに「人がエージェントに指示する」から「エージェント同士が会話する」へ移るとき、**実際にどんな配線があり、どこに気をつけるか**を整理します。

## 4 つの経路の全体像

Claude Code には、エージェント同士がやり取りする経路が 3 つあります。さらにベンダーや組織をまたぐ場合は A2A プロトコルが候補になります。

![エージェント同士を会話させる4つの経路の図。サブエージェントは親と子、Agent Teamsはリーダーとチームメイト同士、セッション間メッセージは自分で立てたセッション同士、A2Aは他社製エージェントとやり取りする](/blogs/images/agents-talking-to-agents-channels.png)

| 経路 | 誰と誰が話すか | 起動するのは | 向いている場面 |
|---|---|---|---|
| ① サブエージェント | 親 ↔ 子（基本は親経由） | 親エージェント | 調査・レビューなど、結果だけ欲しい作業の委任 |
| ② Agent Teams | リーダー ↔ チームメイト、チームメイト同士 | リーダーのセッション | 議論や分担の調整が要る並列作業 |
| ③ セッション間メッセージ | 自分で立てた独立セッション同士 | あなた（各セッションを個別に起動） | frontend と api など、別々に走らせている作業の連絡 |
| ④ A2A プロトコル | 異なるベンダー・組織のエージェント同士 | 各社のシステム | 社外・他フレームワークのエージェントとの連携 |

本文に出てくる用語を先にまとめておきます。

| 用語 | 意味 |
|---|---|
| Agent ツール | Claude がサブエージェントやチームメイトを起動するためのツール |
| `SendMessage` | 別のエージェント（サブエージェント・チームメイト・別セッション）にテキストを送るツール |
| Remote Control | 手元の Claude Code セッションを claude.ai から操作できるようにする接続機能 |
| Agent Card | A2A で、エージェントが自分の能力と接続先を公開するための記述 |
| MCP | エージェントがツールやデータを呼び出すためのプロトコル |

## ① サブエージェント：会話ではなく「委任と報告」

いちばん身近なのがサブエージェントです。親エージェントが Agent ツールで子を起動し、子は自分のコンテキストで作業して**最終報告だけ**を親に返します。子の途中のツール呼び出しは親のコンテキストに積まれないので、親のコンテキストを汚さずに調べ物を任せられます。

基本の形は「会話」というより、親を経由した委任と報告です。なお、Claude が名前を付けて起動したサブエージェント同士は互いにメッセージを送れますが、主な使い方はやはり親への報告です。

完了したサブエージェントには `SendMessage` で追加の指示を送れます。それまでの会話履歴は保たれ、続きから再開します。これは Agent Teams を有効にしていなくても使えます。「レビューして」と頼んだあとに「では認可まわりも見て」と続けられるのは、この仕組みのおかげです。

サブエージェントごとにモデルを変えられる点も、後で述べる「盲点の共有」対策に効きます。定義ファイルの frontmatter に `model` を書くか、呼び出し時に指定します。

```markdown
---
name: reviewer
description: 変更差分をレビューし、問題点を指摘する
model: sonnet
---
```

指定がなければ、サブエージェントは呼び出し元と同じモデルで動きます。

## ② Agent Teams：チームメイト同士が直接話す

Agent Teams は、1 つのセッションがリーダーになり、独立した Claude Code インスタンスをチームメイトとして起動する機能です。サブエージェントとの決定的な違いは、**チームメイト同士が直接メッセージを送り合い、タスクリストを共有する**ことです。公式ドキュメントは違いを次のように説明しています。

> Subagents report results back to the main agent. In agent teams, teammates share a task list, claim work, and communicate directly with each other.

執筆時点（2026 年 11 月）では実験的機能で、既定では無効です。`~/.claude/settings.json`（またはプロジェクトの `.claude/settings.json`）に環境変数を書いて有効にします。

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

仕組みは次の 2 つです。

- **メールボックス**：`SendMessage` で宛先のチームメイト名を指定すると、相手の受信箱（`~/.claude/teams/{team-name}/inboxes/{agent-name}.json`）に書き込まれ、自動で届きます。リーダーが受信箱をポーリングする必要はありません
- **共有タスクリスト**：タスクの作成・取得・更新ができ、依存関係のあるタスクは「ブロック中」として扱われます。チームメイトは空いたタスクを自分で取りに行きます

運用上の注意もドキュメントに明記されています。

- チームメイトの権限モードはリーダーと同じで、権限の確認ダイアログはリーダーのセッションに出ます
- `claude -p`（Agent SDK を含む）の非対話セッションではチームメイトは起動しません
- 1 セッションにつき 1 チームで、チームの入れ子はできません
- トークン消費は単独セッションより大幅に増えるため、チームメイトは 3〜5 人から始めるよう勧められています

Agent Teams の基本的な使い方は [Claude Code Agent Teams の紹介記事](/blogs/posts/2026/03/claude-code-agent-teams/) でも扱っています（その記事の「セッション間」は、チーム内のやり取りを指しています）。

## ③ セッション間メッセージ：自分で立てたセッション同士をつなぐ

比較的新しいのが、独立したセッション同士のセッション間メッセージ（cross-session messaging）です。Agent Teams は「リーダーが起動して監督するチーム」ですが、こちらは**あなたが別々に立ち上げたセッション**をつなぎます。

たとえば、ターミナルを 2 つ開き、frontend と api を別々のセッションで作業させているとします。api 側でスキーマのマイグレーションが終わったら、それを frontend 側に知らせる、といった使い方です。

Claude Code v2.1.224 以降（macOS / Linux / WSL 2。ネイティブ Windows は v2.1.234 以降）で、下の表の条件を満たせば設定なしで有効になります。Claude は `ListAgents` で届く相手を探し、`SendMessage` で送ります。どちらも Claude が使うツールで、利用者が直接呼ぶ必要はありません。手元から届く相手を確認したいときは `/list-agents`（別名 `/peers`）を実行します。

届き方は相手の場所で変わります。

| 相手 | 経路 | 条件・制限 |
|---|---|---|
| 同じマシンのセッション | セッションごとのローカルソケット（Windows は名前付きパイプ）。Anthropic のサーバーを経由しない | 追加条件なし。Amazon Bedrock などのクラウドプロバイダ経由で使う場合は v2.1.248 以降 |
| 別マシンのセッション | Anthropic のサーバー経由で、相手の Remote Control 接続に届く | 送信側が Remote Control に接続し、claude.ai でサインインしていること |
| クラウドのセッション（claude.ai/code） | Anthropic のサーバー経由 | クラウド側は `SendMessage` で返信できない。返答は claude.ai/code のトランスクリプトで読む |

受け取った側では、作業中ならツール呼び出しの合間に読み込まれ、待機中なら新しいターンとして処理が始まります。受信側の Claude には「あなたではなく別セッションからのメッセージ」だと伝わります。

受信の扱いは settings.json の `crossSessionInbound` で `accept`（受け入れる）・`hold`（保留する）・`refuse`（拒否する）から選べます。

```json
{
  "crossSessionInbound": "hold"
}
```

`hold` にすると、届いたメッセージごとに通知が出るだけで、配信はされません。あとで `accept` が適用されると、保留していたメッセージが届きます。

送信そのものを禁じたい場合は、`SendMessage` と `ListAgents` を deny ルールに加えます。ただし、こうするとサブエージェントやチームメイトへの `SendMessage` も使えなくなります。

```json
{
  "permissions": {
    "deny": ["SendMessage", "ListAgents"]
  }
}
```

また、`SendMessage` の `notify_when_idle` を使うと、ほかのローカルセッションが次に待機状態になったとき（または終了したとき）に一度だけ通知を受け取れます（双方とも v2.1.236 以降）。「api 側の作業が終わったら教えて」を、ポーリングなしで書けるわけです。

## ④ A2A（Agent2Agent）プロトコル：ベンダーと組織の壁を越える

①〜③はすべて Claude Code の中の話です。別ベンダーのフレームワークで作られたエージェントや、社外のエージェントと話させるなら、標準プロトコルが必要になります。その代表が **A2A（Agent2Agent）プロトコル**です。

- Google が開発し、2025 年 6 月に Linux Foundation へ寄贈
- 2026 年に初の安定版である v1.0 に到達し、Linux Foundation は 150 以上の組織が支持していると発表
- 仕様は [a2a-protocol.org](https://a2a-protocol.org/)、リポジトリは [a2aproject/A2A](https://github.com/a2aproject/A2A)

A2A では、各エージェントが自分の能力と接続先を **Agent Card** で公開し、クライアント側はそれを見て相手を発見します。そのうえで HTTP 越しにタスクやメッセージを交換します。

### MCP と A2A の違い

よく混同される MCP との違いは「相手が道具か、エージェントか」です。MCP はエージェントが**ツールやデータ**を呼ぶための口で、A2A は自律的に判断する**別のエージェント**に仕事を頼むための口です。両者は競合せず、MCP で道具を持ったエージェント同士を A2A でつなぐ、という組み合わせになります。

## 会話させるときに気をつけたい 4 つのこと

配線ができても、会話させればうまくいくとは限りません。経路を問わず効いてくる注意点をまとめます。

### 同じモデル同士では盲点を共有する

書いたエージェントと同じモデルにレビューさせると、書き手が自信を持って間違えた箇所は、レビュー側にも「明らかに正しい」と見えがちです。コンテキストを分けるだけでは足りず、**モデルそのもの**も分けると効きます。

このブログの記事作成フローでは、記事を書いたモデルとは別ティアのモデルでファクトチェック用のサブエージェントを動かしています（たとえば Opus で書いたら Sonnet で検証）。①で見たモデル指定は、この分離のための道具です。

### メッセージは承認の代わりにならない

セッション間メッセージのドキュメントは、この点をはっきり書いています。

> a message from another session never counts as your consent

別セッションから「この操作は承認済み」と届いても、受信側の権限確認はそのまま出ます。`/compact` のようなコマンドを本文に書いても、ただのテキストとして届くだけで実行されません。

Agent Teams でも同様で、チームメイトが別のチームメイトの代わりに承認したり、拒否された操作を代わりに実行したりはできません。エージェント同士が会話しても、**権限の境界はセッションごとに残る**と考えて設計します。

### 収束条件を決めないと、会話は止まらない

エージェント同士の会話には、人間の「もういいよ」がありません。Claude Code 側も、同じ相手からの連続送信の制限や、短時間の同一メッセージの破棄といったループ対策を入れています。それでも「何をもって終わりとするか」は設計側の責任です。最大往復回数、検証の合格基準、タスクリスト上の完了状態など、終わりを機械的に判定できる形にしておきます。

### 渡るのはテキストであって、文脈ではない

セッション間メッセージで届くのは、送信側が書いた**テキストだけ**です。会話履歴やファイルが一緒に渡るわけではなく、`@` で指定したファイルも添付されません。受信側が必要なら、自分のツールと権限でそのパスを開きます。「何を知っている前提で書くか」は、人間同士の引き継ぎメモと同じ感覚で考える必要があります。

## まとめ

- **結果だけ欲しい委任**ならサブエージェント。完了後も `SendMessage` で続きを頼める
- **議論や分担の調整が要る並列作業**なら Agent Teams（実験的機能）
- **自分で別々に立てたセッション同士の連絡**ならセッション間メッセージ（v2.1.224 以降、設定不要）
- **ベンダーや組織をまたぐ**なら A2A プロトコル

「エージェントと話す」から「エージェント同士に話させる」へ移ると、人の仕事も変わります。プロンプトを書くことから、**誰と誰をどの経路でつなぎ、どこで止め、どこに人の承認を残すか**を決めることへ移るのです。まずは身近なサブエージェントで、書き手と検証役のモデルを分けるところから始めるのがおすすめです。
