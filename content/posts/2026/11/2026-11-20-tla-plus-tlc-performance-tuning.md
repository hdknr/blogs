## はじめに

TLA+ のモデル検査器 TLC は、仕様から到達しうる状態をすべて調べます。仕組みは [TLA+ のモデル検査器 TLC とは](/blogs/posts/2026/11/tla-plus-tlc-model-checker/) で整理しました。総当たりなので、プロセスやメッセージを少し増やしただけで検査が終わらなくなります。いわゆる**状態爆発（State Space Explosion）**です。

TLC を速くする方法は、次の 3 つに分かれます。

- **モデリングの工夫**：仕様の意味を変えずに、探索する状態の数そのものを減らす
- **実行の調整**：TLC の実行オプションや、検査する性質の範囲を調整する
- **検証方法の切り替え**：網羅的な検査にこだわらず、シミュレーションや別の検査器を使う

この記事では、効果の大きい順にこの 3 段階で整理します。

## TLC が遅い原因を切り分ける

手を付ける前に、TLC の出力を見ます。見るのは **Distinct states（重複を除いた状態数）** と経過時間です。

- **状態数が多すぎる** → モデリングを見直す（第 1 段階）
- **状態数は少ないのに遅い** → Liveness（活性：「いつかは〇〇になる」という性質）の検査や、実行環境（スレッド数・メモリ）が足を引っ張っている可能性があります。→ 第 2 段階へ
- **どちらを試しても終わらない** → 網羅的な検査をあきらめ、検証のやり方を切り替える（第 3 段階）

![TLC が遅いときの切り分けフロー。TLC の出力で Distinct states を確認し、状態数が多すぎればモデリングを見直し、そうでなく Liveness を検査していれば修正中は INVARIANT だけに絞り、どちらでもなければ -workers や -Xmx で実行環境を調整する。それでも終わらなければ小さい構成での実行、シミュレーションモード、Apalache の併用に切り替える](/blogs/images/tla-plus-tlc-performance-triage.png)

## 第 1 段階：モデリングで状態爆発を抑える（効果：極大）

TLC が遅い原因のほとんどは、探索する状態が多すぎることです。仕様の本質を変えずに状態数を削るのが、いちばん効きます。

### 対称性（SYMMETRY）を使う

複数のプロセス・ノード・クライアントが対等にふるまう場合、それらを入れ替えただけの状態は 1 つにまとめられます。

TLC の設定ファイル（`.cfg`）で `SYMMETRY` を指定し、モデル値（Model Values）の集合に対称性を定義します。

```text
\* Spec.tla（またはモデル用のモジュール）
Perms == Permutations(Procs)
```

```text
\* Spec.cfg
CONSTANTS
    Procs = {p1, p2, p3}
SYMMETRY Perms
```

`Permutations` は標準モジュール `TLC` の演算子なので、`EXTENDS TLC` が必要です。プロセス `p1, p2, p3` を区別しなくてよいなら、状態数は最大で 1/3!（= 1/6）まで減ります。

**注意**：対称性を使うと、Liveness の検査結果が正しくならないことがあります。対称性は Safety（不変条件）の検査で使うのが無難です。

### 状態の制約（CONSTRAINT）で探索範囲を打ち切る

タイムスタンプ、カウンタ、メッセージキューの長さのように、際限なく増えうる変数には上限を設けます。

```text
\* Spec.tla
StateLimit == /\ Len(queue) <= 3
              /\ clock <= 5
```

```text
\* Spec.cfg
CONSTRAINT StateLimit
```

制約を満たさない状態に到達すると、TLC はそこから先を探索しません。打ち切った先にあるバグは見つからないので、上限は「検証したい性質が現れるのに十分な大きさ」にします。

### アクションの粒度を粗くする

システム全体の整合性に影響しないローカルな処理は、`/\` でつないだ 1 つのアクションにまとめます。ステップが細かく分かれていると、並行動作のインターリーブ（実行順の組み合わせ）が爆発的に増えます。

たとえば「ローカルの値を準備する」と「それを送る」を別アクションにすると、その間に他のプロセスのあらゆる動きが割り込めます。

```text
\* 細かい：2 ステップに分かれ、間に他プロセスの動作が挟まる
Prepare(p) == /\ pc[p] = "init"
              /\ buf' = [buf EXCEPT ![p] = Value(p)]
              /\ pc' = [pc EXCEPT ![p] = "send"]
              /\ UNCHANGED queue
Send(p)    == /\ pc[p] = "send"
              /\ queue' = Append(queue, buf[p])
              /\ pc' = [pc EXCEPT ![p] = "done"]
              /\ UNCHANGED buf

\* 粗い：準備と送信を 1 ステップにまとめる
PrepareAndSend(p) == /\ pc[p] = "init"
                     /\ queue' = Append(queue, Value(p))
                     /\ pc' = [pc EXCEPT ![p] = "done"]
                     /\ UNCHANGED buf
```

準備が他のプロセスから見えないローカルな処理なら、まとめても検証したい性質は変わりません。

### 不要な変数を削り、抽象化する

- 検証したい不変条件に関係しないデータ（ペイロードの中身など）は、`{"data1", "data2"}` のような最小限の値に抽象化するか、変数ごと削除します。
- 他の変数から計算できる値は、独立した変数として持たず、演算子（定義）として書きます。

### VIEW で状態の同一性判定から変数を外す

デバッグ用のカウンタやログのように、状態が同じかどうかの判定に含めたくない変数があるときは、`.cfg` で `VIEW` を指定します。TLC は VIEW の値で状態の重複を判定します。コアの変数が同じで、外した変数だけが異なる状態は 1 つにまとまります。

```text
\* Spec.tla
CoreVars == <<state, queue>>
```

```text
\* Spec.cfg
VIEW CoreVars
```

外した変数が不変条件や次の遷移に影響する場合は、探索漏れが起きるので使えません。

## 第 2 段階：実行オプションと検査範囲を調整する（効果：中〜大）

仕様を書き換えずに、実行時の設定だけで速くする方法です。以下のコマンド例は、TLA+ の [GitHub Releases](https://github.com/tlaplus/tlaplus/releases) から取得した `tla2tools.jar` をカレントディレクトリに置いた前提です。

### マルチスレッドで動かす（`-workers`）

コマンドラインから TLC を起動すると、ワーカー数の既定値は 1（シングルスレッド）です。`-workers auto` でマシンのコア数ぶんのワーカーを使えます。TLA+ Toolbox や VS Code 拡張から実行する場合も、ワーカー数の設定を確認してください。

```bash
java -cp tla2tools.jar tlc2.TLC -workers auto Spec.tla
```

### ヒープを増やす（`-Xmx`）

状態数が増えると、Java のガベージコレクション（GC）が頻発して極端に遅くなります。`-Xmx` でヒープを増やします。目安は物理メモリの 7〜8 割程度です。

```bash
java -XX:+UseParallelGC -Xmx16G -cp tla2tools.jar tlc2.TLC -workers auto Spec.tla
```

`-XX:+UseParallelGC` は GC の方式をパラレル GC にする JVM オプションです。モデル検査では停止時間よりスループットが大事なので、[TLC の公式ドキュメント](https://docs.tlapl.us/using:tlc:start) もこの指定を勧めています。

### 指紋（fingerprint）のテーブルにメモリを割り当てる

TLC は、探索済みの状態を指紋（ハッシュ値）の集合として覚えています。状態数が増えると、指紋の集合がメモリに収まらなくなります。するとディスクへの読み書きが発生し、急に遅くなります。

`-fpmem` は、指紋の保存に回すメモリを指定するオプションです。0〜1 の小数なら物理メモリに対する割合、整数なら MB 単位の量になります（既定は 0.25）。ヒープとあわせて、指紋の集合がメモリに収まるように調整します。

### Liveness の検査は最後に回す

`<>`（いつかは）や `[]<>`（何度でも）を含む時相論理の性質を `PROPERTY` で検査するとき、TLC は状態グラフの強連結成分（SCC）を解析します。そのため、不変条件（`INVARIANT`）だけの検査に比べて大幅に時間がかかります。

仕様を直している間は `.cfg` から `PROPERTY` を外して `INVARIANT` だけを有効にし、Liveness は最終確認のときだけ回すのが定石です。

## 第 3 段階：検証のやり方を切り替える（効果：状況による）

網羅的な検査にこだわらない方法です。

### シミュレーションモード（`-simulate`）

状態空間が大きすぎて網羅的な検査が終わらないときは、シミュレーションモードが有効です。初期状態からランダムに遷移をたどる実行を繰り返し、深い状態まで素早く到達します。

```bash
java -cp tla2tools.jar tlc2.TLC -simulate -depth 100 Spec.tla
```

`-depth` は 1 回の実行でたどる最大ステップ数です。網羅性は失いますが、多くのバグは全状態を調べ切る前にこのモードで見つかります。

### 小さい構成で回し、大きい構成は CI に任せる

「ノード 3・メッセージ 2」で起きないバグは、「ノード 5・メッセージ 4」でも起きにくい、という経験則があります。Alloy の Daniel Jackson が提唱した **small scope hypothesis** です。

普段の開発では最小構成で素早く回し、パラメータを大きくした検査は CI や夜間バッチだけで回します。

### Apalache を併用する

TLC は、状態を 1 つずつ列挙する明示的状態（explicit-state）のモデル検査器です。TLA+ には、SMT ソルバ（Z3 など）をバックエンドに使う記号的なモデル検査器 **Apalache** もあります。

Apalache は、決められたステップ数までの実行を調べる有界モデル検査（Bounded Model Checking）を行います。データの値域が大きい仕様では、値を 1 つずつ列挙する TLC より速く反例を見つけることがあります。

## まとめ

| 段階 | 手段 | 効果 |
|---|---|---|
| 1. モデリング | SYMMETRY / CONSTRAINT / アクションの統合 / 変数の削減・抽象化 / VIEW | 極大 |
| 2. 実行オプション・検査範囲 | `-workers` / `-Xmx` / `-fpmem` / Liveness を後回し | 中〜大 |
| 3. 検証方法の切り替え | `-simulate` / 小さい構成 / Apalache | 状況による |

最初に TLC の出力を見て、**状態数が多すぎるのか**、それとも**状態数は少ないのに Liveness 検査や実行環境がネックなのか**を切り分けてください。状態数が多いなら、まず SYMMETRY と CONSTRAINT から試すのが近道です。
