## はじめに

X で「小規模なローカル LLM こそが未来」という投稿が拡散されていました（[投稿 1](https://x.com/n0tisma/status/2123751964735602905)、[投稿 2](https://x.com/n0tisma/status/2123751965494743074)）。スペイン語の投稿で、要旨は次のとおりです。

> みんな、ローカルの 3B モデルで済む仕事にフロンティアモデルを借りている。小さなローカル LLM こそが未来だ。
> 本当に問うべきは「ローカルモデルは同じくらい賢いか？」ではなく、「自分の 1000 回の呼び出しのうち、賢いモデルが本当に必要だったのは何回か？」だ。

投稿はこの発言を Andrej Karpathy 氏のものとして紹介しています。さらに「Claude Pro・ChatGPT Pro・Gemini Pro の死亡診断書」とまで煽っています。ただし、**Karpathy 氏がこの言い回しで発言したという一次ソースは確認できていません**。また、投稿の主眼は 18 ページの PDF への誘導にあります。

煽り文句と出典はさておき、後半の問いは実務でそのまま使えます。この記事では、この問いを出発点に「どの呼び出しを小型モデルに回せるか」と、その振り分け方を整理します。結論を先に書くと、**分類・抽出のように機械的に検証できる仕事は手元の小型モデルに回し、検証に落ちたときだけフロンティアモデルに回す**のが現実的な落としどころです。

## 登場するプロダクトと用語

| プロダクト | 役割 |
|---|---|
| [Ollama](https://ollama.com/) | ローカルで LLM を動かすツール。OpenAI 互換 API を持つ |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) | GGUF 形式のモデルを CPU / GPU で動かす C/C++ 製の推論エンジン |

| 用語 | 意味 |
|---|---|
| フロンティアモデル | 各社の最上位モデル。高性能だがトークン課金で、データは外部に出る |
| 小型モデル（SLM） | パラメータ数が数十億（3B〜8B 程度）のモデル。一般的なノート PC で動く |
| 量子化 | 重みを 4bit などに丸めてメモリと計算量を減らす手法。精度と引き換えに軽くなる |
| ルーティング | リクエストの性質を見て、どのモデルに送るかを決める仕組み |
| カスケード | まず安いモデルで処理し、失敗したときだけ高いモデルに回す構成 |
| エスカレーション | カスケードで、安いモデルの結果が不合格だったときに上位のモデルへ回すこと |

## 「賢さ」が要らない呼び出しは意外と多い

アプリやエージェントが LLM を呼ぶ場面を棚卸しすると、推論力がほとんど要らない呼び出しがかなりの割合を占めます。

- **分類**: 問い合わせを「請求」「不具合」「その他」に振り分ける、スパム判定
- **抽出**: メールや請求書から日付・金額・社名を JSON で取り出す
- **整形・変換**: 表記ゆれの正規化、Markdown から別形式への変換、定型文の言い換え
- **短い要約**: 1 段落程度のテキストの要約、コミットメッセージやタイトルの生成
- **埋め込み・検索の前処理**: クエリの書き換え、キーワード抽出

これらは「答えの形が決まっていて、正解かどうかを機械的に判定しやすい」という共通点があります。小型モデルでも十分にこなせることが多く、外れても後段のチェックで気付けます。

反対に、次のような仕事はフロンティアモデルの出番です。

- 複数ファイルにまたがる設計判断や、難しいバグの原因究明
- 長い文脈を読み込んで矛盾を見つける作業
- 正解の形が決まっていない企画・文章の生成
- 多段の計画を立てて道具を使い分けるエージェント処理

## ローカルに回すメリットと負担

小型モデルへ回す動機は、コストだけではありません。

- **コスト**: 呼び出し回数が多いバッチ処理ほど効きます。ローカルなら追加の課金は電気代とハードウェアだけです
- **プライバシー**: 顧客データや社内文書を外部 API に送らずに済みます
- **レイテンシ**: ネットワーク往復がなく、短い入出力なら体感で速いことも多いです
- **可用性**: API のレート制限・障害・仕様変更の影響を受けません

一方で、引き受けるべき負担もあります。

- **性能の上限**: 手元のマシンのメモリと計算資源で頭打ちになります
- **運用**: モデルの更新や評価を自分で回す必要があります

## 振り分けの基本形：ローカル優先のカスケード

おすすめは、すべてをローカルにすることでも、すべてをフロンティアモデルにすることでもありません。**ルールで振り分け、ローカルの結果を機械的に検証し、検証に落ちたときだけフロンティアモデルに回す**構成です。

![リクエストをルーターがタスク種別で振り分け、定型タスクは手元の小型ローカルモデルで処理して JSON スキーマで検証し、合格なら結果を返し、不合格ならクラウドのフロンティアモデルにエスカレーションする。難しいタスクは最初からフロンティアモデルに送る構成図](/blogs/images/small-local-llm-cascade.png)

ポイントは 2 つです。

1. **ルーターに LLM を使わない**: タスク種別はたいていアプリ側で分かっています。「この API は分類用」と決め打ちすれば、振り分け自体のコストはゼロです
2. **検証を機械的にする**: JSON スキーマ、列挙値のチェック、正規表現など、LLM に頼らない判定を置きます。これがあるから、小型モデルの失敗を安全に拾えます

## Ollama で試す

### モデルを取得して動かす

Ollama をインストールしたら、3B〜4B クラスのモデルを取得します。

```bash
ollama pull llama3.2:3b
ollama run llama3.2:3b "次の文を「請求」「不具合」「その他」のどれかに分類して: 先月の請求額が二重になっています"
```

4bit 量子化された 3B モデルのファイルサイズは 2GB 前後で、メモリ 8GB 程度のマシンでも動かせます。日本語の品質を重視するなら、Qwen 系や Gemma 系の小型モデルも候補になります。どれを選ぶかは、後述の「導入の進め方」のように評価セットで比べて決めるのが確実です。

### 構造化出力で抽出する

Ollama は `format` に JSON スキーマを渡すと、出力をそのスキーマに沿わせることができます。抽出系のタスクではこれが検証の土台になります。

```bash
curl http://localhost:11434/api/chat -d '{
  "model": "llama3.2:3b",
  "messages": [
    {"role": "user", "content": "次の請求書から会社名・日付・金額を抽出して: 株式会社サンプル 2026年11月20日 合計 12,800円"}
  ],
  "format": {
    "type": "object",
    "properties": {
      "company": {"type": "string"},
      "date": {"type": "string"},
      "amount": {"type": "integer"}
    },
    "required": ["company", "date", "amount"]
  },
  "stream": false
}'
```

返ってくる JSON の `message.content` に、スキーマどおりの文字列が入ります（値はモデルによって変わります）。

```json
"message": {
  "role": "assistant",
  "content": "{\"company\": \"株式会社サンプル\", \"date\": \"2026年11月20日\", \"amount\": 12800}"
}
```

### カスケードを Python で書く

Ollama は `http://localhost:11434/v1` で OpenAI 互換 API を提供しているので、OpenAI の SDK からそのまま呼べます。ローカルで試し、検証に落ちたらフロンティアモデルに回す最小構成は次のとおりです。Python 3.10 以上と `pip install openai` を前提にしています。

```python
import json
import os

from openai import OpenAI

local = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")  # キーは任意の文字列でよい
cloud = OpenAI()  # 環境変数 OPENAI_API_KEY を使う。他社 API でも同じ形で書ける
CLOUD_MODEL = os.environ["CLOUD_MODEL"]  # 利用するフロンティアモデルの名前を環境変数で渡す

LABELS = {"請求", "不具合", "その他"}
PROMPT = '問い合わせを分類し、{"label": "請求|不具合|その他"} の JSON だけを返してください。\n\n'


def classify_with(client: OpenAI, model: str, text: str) -> str | None:
    res = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": PROMPT + text}],
        response_format={"type": "json_object"},
    )
    try:
        label = json.loads(res.choices[0].message.content)["label"]
    except (json.JSONDecodeError, KeyError, TypeError):
        return None
    return label if label in LABELS else None  # 機械的な検証


def classify(text: str) -> tuple[str, str]:
    label = classify_with(local, "llama3.2:3b", text)
    if label is not None:
        return label, "local"
    # 検証に落ちたときだけフロンティアモデルへエスカレーション
    label = classify_with(cloud, CLOUD_MODEL, text)
    return (label or "その他"), "cloud"


if __name__ == "__main__":
    print(classify("先月の請求額が二重になっています"))  # 例: ('請求', 'local')
```

戻り値に `"local"` / `"cloud"` を含めているのは、**どれだけの割合がローカルで済んだかを数えるため**です。冒頭の問い「1000 回のうち何回が賢いモデルを必要としたか」に、勘ではなくログで答えられるようになります。なお、フロンティアモデルでも検証に落ちた場合は、安全側として「その他」に倒しています。

## 導入の進め方

いきなり置き換えるより、次の順で進めると失敗しにくいです。前節のカスケードを入れておけば、手順 5 の監視はログを集計するだけで回ります。

1. **呼び出しを棚卸しする**: 既存のログから、プロンプトの種類ごとに回数とトークン量を集計します
2. **評価セットを作る**: 種類ごとに数十件、正解付きのサンプルを用意します
3. **小型モデルで採点する**: 同じ評価セットをローカルモデルで流し、正答率と速度を測ります
4. **合格した種類から切り替える**: 検証とエスカレーションを付けた状態で本番に入れます
5. **エスカレーション率を監視する**: フロンティアモデルへ回る割合が増えたら、プロンプトやモデルを見直します

## 注意点

- **「3B で何でもできる」わけではない**: 長い文脈・多段推論・難しいコードは、小型モデルだと品質が大きく落ちます。投稿の煽りに乗って全面移行すると、品質問題がそのまま利用者に届きます
- **検証できないタスクは回さない**: 自由記述の文章のように正誤を機械的に判定できないものは、失敗に気付けません
- **ハードウェアの総コストを見る**: 呼び出し回数が少なければ、API 課金のほうが安いこともあります。ローカルが得をするのは、呼び出しが多いか、データを外に出せない場合です
- **サブスクリプションとは比較の軸が違う**: チャット用のサブスクリプションと、アプリから呼ぶ API の従量課金は別物です。「ローカルでサブスクが不要になる」かどうかは、使い方次第です

## まとめ

- 「小規模なローカル LLM こそが未来」という投稿の出典は確認できませんが、「1000 回のうち何回が賢いモデルを必要としたか」という問いは実務で有効です
- 分類・抽出・整形・短い要約のように、答えの形が決まっていて機械的に検証できる仕事は、3B〜8B の小型モデルに回せることが多いです
- 実装の基本形は「ルールで振り分け → ローカルで処理 → 機械的に検証 → 検証に落ちたときだけフロンティアモデル」のカスケードです
- ローカルで済んだ割合をログに残せば、どこまで置き換えられるかを数字で判断できます
- 投稿が煽る「サブスクの死」は言い過ぎで、ローカルが効くのは呼び出しの多い定型処理やデータを外に出せない場面です
