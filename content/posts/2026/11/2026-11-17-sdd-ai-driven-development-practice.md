## はじめに

Claude Code や Codex を使う開発者は増えましたが、「実際にどんな手順で開発を回しているか」が共有されることはまだ多くありません。
株式会社アサインのテックブログに、記事 [仕様駆動開発（SDD）を採用したAI駆動開発の実態と課題](https://zenn.dev/assign/articles/ab66b2843d9380)（2025 年 11 月 11 日公開）が掲載されました。
この記事は、同社の開発フローをフェーズごとに公開しています。
元はイベントでの登壇内容で、Zenn 公式アカウントのピックアップでも紹介されました。

この記事では、その内容を整理しながら、仕様駆動開発（SDD）を現場で回すときにどこが効き、どこでつまずくのかを見ていきます。

- フェーズごとに、どの設計書を作って次のフェーズへ渡しているか
- 運用して見えてきた 2 つの課題（スコープの肥大化、セルフレビューの負荷）とその対策
- SDD を導入するときの勘所

なお、元記事の内容と筆者（このブログの書き手）の見方を区別するため、筆者の解釈には「筆者の見方では」などと添えています。

## 登場するツールと用語

| 名前 | 種別 | この記事での役割 |
|---|---|---|
| 仕様駆動開発（SDD） | 開発手法 | 実装より先に仕様（設計書）を書き、AI にはその仕様を入力として渡す |
| PRD | ドキュメント | プロダクト要求仕様書。要件定義フェーズの成果物 |
| DesignDoc | ドキュメント | 設計の方針と背景をまとめた文書 |
| Claude Code | AI コーディングエージェント | 設計書から実装を進める |
| vibe coding | 開発スタイル | 仕様を固めずに、AI との対話の流れで場当たり的にコードを書かせる進め方。SDD の対比として登場する |
| Miro | オンラインホワイトボード | 開発フローの可視化 |
| v0 / Lovable / Bolt | UI 生成サービス | 要件定義段階でモックを量産する |
| Notion MCP / Figma MCP / Jira MCP | MCP サーバー | 各サービスの情報を AI に渡す |
| Claude Code GitHub Actions | CI 連携 | PR の一次レビューを AI に任せる |
| cc-sdd | SDD 支援ツール | 今後のフロー見直しで参考にしているもの |

## 開発フローの全体像

フローは **要件定義 → 設計（バックエンド／フロントエンド）→ 実装（バックエンド／フロントエンド）→ PR** の 4 ステップです。
基本方針は仕様駆動開発で、フローの可視化には Miro を使っています。
設計と実装はそれぞれバックエンドとフロントエンドに分かれるため、以下では 6 段階に分けて説明します。

ポイントは、各フェーズの **出力が次のフェーズの入力になる** ように設計書をつないでいることです。
AI に毎回ゼロから説明するのではなく、前段で作った文書を MCP 経由で読ませます。

## フェーズごとの AI の使い方

### 要件定義：モックを 10 パターン以上作って検証する

最初のフェーズなので、前段から受け取る文書はありません。出力は PRD、DesignDoc、モックの 3 つです。

特徴的なのはモックの作り方です。v0・Lovable・Bolt などで **10 パターン以上** のモックを生成し、想定ユーザー像（ペルソナ）に照らして検証しています。
UI を作るコストが下がったぶん、要件定義の段階で比較できる案の数を増やしている形です。

### 設計（バックエンド）：API 設計書が開発全体の要になる

入力は PRD と DesignDoc で、Notion MCP 経由で読み込みます。作る文書は次の 4 つです。

- API 設計書
- DB 設計書
- API 詳細設計書
- 全体設計書

元記事では、**API 設計書は全開発工程で 5 回参照される** 重要な文書だったと振り返っています。
また全体設計書は、AI に「今どこを作っているのか」を把握させるために用意したものです。
長い開発の途中で AI が現在地を見失わないための、地図の役割を果たします。

### 設計（フロントエンド）：画面仕様は具体的に書く

入力は Figma MCP 経由のデザイン、API 設計書、設計書テンプレートです。出力は画面仕様書、全体設計書、分割方針書、スコープ別仕様設計書の 4 つです。

画面仕様書には「左上にカラーコード #D70C18 のアイコン」のように、**AI が解釈に迷わない具体的な記述** を入れています。
筆者の見方では、「いい感じのヘッダー」のような曖昧な指示を残さないことが、出力のブレを抑えるコツです。

### 実装（バックエンド）：テスト駆動開発を組み合わせる

設計書群を入力に、テスト駆動開発（TDD）で実装を進めます。
元記事は TDD を選んだ理由として、AI はコードの生成が速く、変更が頻繁に入ることを挙げています。
筆者の見方では、テストが先にあれば、頻繁な変更で仕様とのずれが出ても早く気づけます。

### 実装（フロントエンド）：1 スコープ 1 PR でコンテキストを節約する

フロントエンドは **1 スコープ 1 PR** を基準に作業を分割しています。
以前は大雑把な指示を出していたため auto-compact（コンテキストの自動圧縮）が発生し、精度が落ちていたそうです。
作業単位を小さくすることは、そのままコンテキストウィンドウの節約になります。

### PR：チケットの文脈を自動で添えて一次レビューを AI に

Jira MCP でチケットの文脈を取得し、PR の説明文（description）に自動で追記しています。
さらに Claude Code GitHub Actions で一次レビューを行い、人間のレビューの前に AI のチェックを挟んでいます。

## 見えてきた 2 つの課題

### 課題 1：作業スコープの肥大化

「10 ファイル前後で分割して」と指示しても、AI はコード量を事前に予測できません。
特にフロントエンドで作業スコープが膨らみがちです。

対策は **暗黙知の言語化** です。
たとえば「UI コンポーネントとロジックは別 PR にする」のような、ベテランが無意識に守っている分割ルールを文書に書き起こして AI に渡します。

### 課題 2：実装者のセルフレビュー負荷

AI が書いたコードを実装者がセルフレビューする負荷も重くなっています。
元記事には、修正が必要な 20 箇所のうち 17 箇所は自分で見つけたものの、2〜3 箇所を見逃して PR で指摘された例が紹介されています（数字は元記事の表現のまま）。

対策として挙がっているのは次の 2 つです。

- コーディング規約に **「何をすべきでないか」** を明記する
- レビューで見つかった問題を、ドキュメントへ継続的にフィードバックする

筆者の見方では、「やるべきこと」だけを書いた規約では、AI がやりがちな誤りを防げません。

禁止事項は、AI がコードを生成するときにも、人がレビューするときにもチェック項目として働きます。

## 今後の改善の方向

記事では、今後の改善策として次の 3 つが挙がっています。

- 暗黙知の言語化（課題 1 の対策を継続して進める）
- ドキュメントテンプレートの改善
- コンテキストウィンドウの管理（サブエージェントへのコンテキスト退避を含む）

あわせて、現在は [cc-sdd](https://github.com/gotalab/cc-sdd) を参考にフローを見直していると述べています。

## まとめ：SDD は効くが、文書の重さと向き合う必要がある

著者は、仕様を先に定義する SDD は従来の vibe coding よりも出力精度のブレが小さく、手戻りが減ると判断しています。
一方で、次の課題も残っています。

- 文書の量が膨大になる
- 作業スコープが肥大化しやすい
- セルフレビューの負荷が高い

記事は「まだまだ道半ば」としつつ、やるべきことを愚直にやっていくしかない、と締めくくっています。

筆者がこの事例から読み取ったのは、SDD の効果は「仕様を書くこと」そのものより、**仕様をどの粒度で区切り、どの文書をどのフェーズに渡すか** という設計にかかっている、という点です。
API 設計書が 5 回参照される、全体設計書で現在地を示す、1 スコープ 1 PR に区切る。これらの工夫はどれも、同じ問いへの答えです。AI に渡すコンテキストをどう組み立てるか、という問いです。
SDD を導入するときは、テンプレートを入れるだけで終わらせず、自分たちのフローで「どの文書が何度読まれるか」を観察しながら育てていくのがよさそうです。
