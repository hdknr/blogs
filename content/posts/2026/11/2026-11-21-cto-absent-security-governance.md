## はじめに

CTO が不在の組織では、次の 3 つの機能の境界が曖昧になりがちです。

- 技術・セキュリティの**意思決定**（本来は CTO / CISO の機能）
- 日々の**運用**（情シス）
- 有事の**統制**（CSIRT）

境界が曖昧なまま運用を続けると、判断も実行も現場の担当者に集中します。その担当者が休んだり辞めたりした時点で、体制ごと止まってしまいます。

体制はゼロから設計するよりも、国内の標準ガイドラインや立ち上げ用の資料を土台にするのが定石です。本記事では、体制設計と役割分担の指針になる**公的機関・団体の資料**と**実践的な書籍**を紹介します。次に、それらを踏まえた現実的な役割の切り分け方として「経営層が決める・情シスが実行する・兼務 CSIRT が有事に判断と調整をする」の 3 層構造を整理します。最後に、従業員 100 人規模のベンチャーで、前提となる技術的な土台を整え、90 日で体制を立ち上げる例を紹介します。

想定読者は、CTO や CISO を置いていない中小企業やスタートアップで、情シスやコーポレート部門を担当している人です。

## 用語の整理

| 用語 | 意味 |
| --- | --- |
| CTO | 最高技術責任者。技術戦略とアーキテクチャの最終判断を担う |
| CISO | 最高情報セキュリティ責任者。セキュリティ方針・リスク評価・予算判断を担う |
| 外部 CISO | 社外の専門家に CISO の機能を委託する形態 |
| 情シス | 情報システム部門。アカウント、端末、SaaS、ネットワークなどの日常運用を担う |
| CSIRT | Computer Security Incident Response Team。インシデントの受付・判断・調整を担うチーム |
| トリアージ | インシデントの緊急度・影響度を判定し、対応の優先順位を決めること |
| コマンダー | CSIRT の統括役。隔離など、有事の現場判断を下す |
| PoC | Point of Contact。社内外（法務・広報・外部機関など）との連絡窓口 |
| ハンドラー | インシデントの処理担当。調査や復旧作業を進める |
| SSO | シングルサインオン。1 つの ID 管理の基盤で、複数の SaaS やシステムにログインする仕組み |
| MFA | 多要素認証。パスワードに加えて、スマートフォンなど別の要素で本人を確認する |
| MDM | Mobile Device Management。会社の端末を一括で設定・管理し、遠隔でロックや消去ができる仕組み |
| EDR | Endpoint Detection and Response。端末上の不審な挙動を検知し、隔離などの対応を行うツール |
| root | AWS で、アカウントを作ったときに作られる、すべての権限を持つ管理者（root ユーザー） |
| 監査ログ | 誰が、いつ、何をしたかを記録したログ。調査の手がかりになる |

## セキュリティ体制づくりの指針となる公的機関と団体

### 日本シーサート協議会（NCA）

- **参照資料**：「CSIRT スタータキット」「CSIRT 人材の定義と確保」
- **ポイント**：「CSIRT スタータキット」は、これから CSIRT を立ち上げる組織向けに構築の手順をまとめた資料です。「CSIRT 人材の定義と確保」では、コマンダー、PoC、ハンドラーといった CSIRT の役割が整理されています。役割ごとに誰が担うかを決める際の土台になり、少人数組織で兼務を設計するときにも使えます。

### 独立行政法人情報処理推進機構（IPA）

- **参照資料**：「[中小企業の情報セキュリティ対策ガイドライン](https://www.ipa.go.jp/security/guide/sme/about.html)」（第 4.0 版）
- **ポイント**：「経営者編」と「実践編」に分かれています。技術トップ（CTO / CISO）が不在のとき、**経営層が負うべき責任**と**現場の担当者が実施すべきステップ**の境界線を引くのに向いています。付録には、情報セキュリティ基本方針や関連規程のサンプル、インシデント対応の手引きなども用意されています。

### 経済産業省（METI）

- **参照資料**：「サイバーセキュリティ経営ガイドライン Ver 3.0」と、IPA が発行する「[実践のためのプラクティス集](https://www.ipa.go.jp/security/economics/csm-practice.html)」
- **ポイント**：経営者が CISO などのセキュリティ担当幹部に指示すべき「重要 10 項目」が定められています。CTO 不在の場合は、この「指示」を誰に割り振るかを決める基準になります。割り振り先は、情シス責任者やコーポレート部門長などです。

### JPCERT コーディネーションセンター（JPCERT/CC）

- **参照資料**：「[CSIRT マテリアル](https://www.jpcert.or.jp/csirt_material/)」
- **ポイント**：CSIRT の構想・構築・運用の 3 フェーズに分けて資料がまとまっています。組織内 CSIRT のミッション定義や、情シス（IT 運用部門）・法務・広報との連携を文書化する際の参考になります。

## CTO 不在組織の役割分担：経営層・情シス・兼務 CSIRT の 3 層構造

上記の資料を踏まえると、CTO / CISO 不在組織での現実的な切り分け方は次の 3 層構造になります。

![CTO・CISO 不在組織の役割分担を示す図。上段の経営層が意思決定と最終責任を持ち、左下の情シスに方針を指示する。右下の兼務 CSIRT は有事に情シスへ隔離・停止を指示し、経営層へエスカレーションする。外部技術顧問は情シスの運用を月次でレビューする](/blogs/images/cto-absent-security-governance-layers.png)

### 1. 意思決定・最終責任（経営層 / コーポレート担当役員）

CTO の代わりに、次の判断を担います。

- 事業リスクをどこまで許容するかの決定
- 予算の承認
- 業務停止の判断
- 対外公表の最終判断

### 2. 平時の基盤運用・技術実行（情シス、外部技術顧問がレビュー）

情シスが、アカウント管理、端末・SaaS の統制、バックアップなどの日常運用を担います。

技術的なアーキテクチャやセキュリティ方針の妥当性を社内で評価できない場合は、**外部技術顧問や外部 CISO** に月次レビューを委託し、判断の属人化を防ぎます。

### 3. 有事のトリアージ・横断調整（CSIRT：兼務チーム）

平時は情シスや総務・法務のメンバーが兼務し、インシデントを検知したときだけ CSIRT として次の役割を担います。

- **コマンダー**：隔離を即時に判断する。業務停止が必要なら経営層に上げる
- **PoC**：法務・広報・外部機関と連絡する
- **ハンドラー**：調査・復旧を進める。社内 IT の実作業は情シス、本番環境の実作業は開発側が担う

情シスは「CSIRT の指示を受けて、実際の端末隔離やアカウント停止を実行する部隊」と位置づけます。判断と実行が分かれるので、役割が衝突しません。

## 実践例：従業員 100 人規模のベンチャーでセキュリティ体制を構築する

ここからは、3 層構造を実際の会社に当てはめた例です。会社ごとに事情は違うので、たたき台として読んでください。

### 前提とする会社像

- 従業員は約 100 人で、うち開発者が 30〜40 人
- CTO はいない（または開発組織の長がマネジメント専任）
- 情シスは 1〜2 人。業務は SaaS が中心（Google Workspace か Microsoft 365、Slack、会計・人事の SaaS など）
- 本番環境は AWS などのクラウドにあり、**開発チームが権限を持っている**

ベンチャーで一番の穴になりやすいのは最後の点です。社員の端末と SaaS は情シスが見ていても、本番環境は誰の管理下にもない、という状態がよく起きます。

### 前提要件：体制を動かすための技術的な土台

体制表や手順書を作っても、それを実行する仕組みが無ければ有事に手が出せません。たとえばコマンダーが「このアカウントを止める」と判断しても、SaaS ごとに個別のアカウントがあれば、止め漏れが出ます。体制づくりの前に、次の土台を整えておきます。

| 前提要件 | これが無いとできないこと |
| --- | --- |
| ID 管理の基盤（Google Workspace、Microsoft Entra ID、Okta など）で SSO を導入し、全員に MFA を必須にする | 乗っ取られたアカウントを 1 か所で止めること |
| 入社・異動・退職の人事手続きを起点に、アカウントの発行・停止を連動させる | 退職者のアカウントを残さないこと |
| 全端末を MDM で管理し、EDR を入れる | 感染した端末を遠隔で隔離すること |
| 端末、SaaS（管理者アカウントの持ち主を含む）、クラウドアカウント（root や組織管理の権限を誰が持つか）を台帳にまとめる | 影響範囲をすぐに特定すること |
| 本番環境では個人ごとの固定アカウントをやめ、ID 管理の基盤経由で一時的な権限を受け取る方式にする。root は日常の作業に使わず、MFA を付け、アクセスキーは作らず、利用を監視する | 本番環境への侵入を止めること、誰が何をしたかを追うこと |
| ID 管理の基盤、主要な SaaS、クラウドの監査ログを、調査に必要な期間保存する。AWS CloudTrail の既定のイベント履歴は直近 90 日分の管理イベントだけなので、長く残すには証跡（trail）などを設定する | 何が起きたかを後から調べること |
| バックアップを取り、実際に復元できるかを確認する | ランサムウェアなどの被害から戻すこと |

コマンダーに「隔離までは自分で決めてよい」という権限を渡せるのは、この土台があって初めてです。

### 兼務 CSIRT の体制表：誰が何の権限と責任を持つか

前半の 3 層との対応は、第 1 層が「セキュリティ最終責任者」（以下、責任者）、第 2 層が情シスと外部技術顧問、第 3 層がコマンダー・PoC・ハンドラーです。

| 役割 | 担当者 | 持つ権限・責任 |
| --- | --- | --- |
| セキュリティ最終責任者 | 管理本部長（CFO / コーポレート担当役員） | リスクをどこまで受け入れるか、予算、業務停止、対外公表、監督官庁や警察への届け出の判断 |
| CSIRT コマンダー | 情シスのリーダー（兼務） | 重大度の判定、端末の隔離やアカウント停止の即時判断（あらかじめ権限を渡しておく） |
| CSIRT PoC | 法務・総務の担当者（兼務） | 弁護士、保険会社、個人情報保護委員会、取引先との連絡 |
| ハンドラー（社内 IT） | 情シスのメンバー（兼務） | 端末・SaaS の調査と隔離、アカウント停止の実作業 |
| ハンドラー（本番環境） | 開発リードかインフラ担当 1 人（兼務） | クラウドのログ調査、鍵の無効化、本番環境の隔離 |
| 広報 | 広報担当（兼務） | 公表文の作成（最終判断は責任者） |
| 外部パートナー | 外部技術顧問（月 1 回）、監視サービス、緊急対応の契約先 | 方針のレビュー、24 時間の監視、重大インシデント時の調査支援 |

この体制のポイントは 4 つです。

- **コマンダーに、隔離までは自分で決めてよい権限を事前に渡しておく。** 責任者の承認を待つ間に被害が広がるのを防ぐためです。業務停止や公表が必要になったら責任者に上げます。
- **情シスが 1〜2 人でも、判断する人と手を動かす人は分ける。** 部署は同じでも、有事にはリーダーがコマンダーとして判断に専念し、作業はメンバーが担います。情シスが 1 人なら、コマンダーの代行は開発リードが務めます。
- **CSIRT に開発側の担当者を必ず 1 人入れる。** 情シスだけでは本番環境に手が出せません。
- **社外の力は「監視」「緊急時の駆けつけ」「方針レビュー」に分けて調達する。** すべてを 1 社にまとめると、どこが手薄かが見えなくなります。

### セキュリティ体制を 90 日で立ち上げる手順

#### 0〜30 日目：決めることと棚卸し

- 取締役会か経営会議で、責任者を正式に任命する
- 情報セキュリティ基本方針を作る（IPA ガイドラインの付録にあるサンプルを土台にする）
- 前提要件のうち、台帳をまとめる
- 夜間・休日も含めた緊急連絡網を作る（責任者・コマンダー・PoC・外部の連絡先）

#### 31〜60 日目：前提要件を満たす

- 前提要件の表のうち、台帳以外の項目を整える
- 30 日で終わらない項目は、管理者アカウントと本番環境から優先する

#### 61〜90 日目：有事への備え

- インシデントの重大度の基準を決める（後述の「インシデントの重大度基準と判断者」を参照）
- プレイブックを 3 本だけ書く。最初から網羅しようとしない
  1. アカウントの乗っ取り・不正ログイン
  2. マルウェアに感染した端末（ランサムウェアを含む）
  3. 情報漏えい（メールの誤送信、公開設定のミス、鍵の流出）
- 机上演習を 1 回やる。「金曜 22 時に、GitHub に AWS の鍵が公開されていると連絡が来た」のような具体的な状況で、誰に連絡し、誰が何を決めるかを口頭でたどる

### インシデントの重大度基準と判断者

| 重大度 | 例 | 判断する人 | 責任者への報告 |
| --- | --- | --- | --- |
| 高 | 個人情報の漏えいの恐れ、ランサムウェア、本番停止 | コマンダーが即時に隔離し、責任者が業務停止・公表・届け出を判断 | すぐ（夜間も） |
| 中 | 1 アカウントの乗っ取り、1 台の感染（広がっていない） | コマンダー | 当日中 |
| 低 | フィッシングメールが届いた、ポリシー違反 | 情シス | 月次の定例でまとめて報告 |

個人データの漏えいなどが発生し（またはその恐れがあり）、それが一定の類型に当たる場合は、個人情報保護委員会への報告と本人への通知が必要です。一定の類型とは、要配慮個人情報が含まれる、財産的被害のおそれがある、不正の目的によるおそれがある、1,000 人を超える、のいずれかです。

報告は、事態を知った日から起算します。法人の場合は、いずれかの部署が知った時点が基準です。速報はおおむね 3〜5 日以内が目安で、確報の期限は 30 日以内です。不正アクセスなど不正の目的によるおそれがある場合、確報の期限は 60 日以内になります。この期限があるため、「高」と判定してから PoC が弁護士に連絡するまでの流れは、プレイブックに書いておきます。

### 平時のセキュリティ運用リズム（定例・演習・研修）

| タイミング | 中身 | 参加者 |
| --- | --- | --- |
| 毎月（30 分） | セキュリティ定例：起きたこと、台帳の差分、退職者アカウントの棚卸し | 責任者、情シス、開発リード、外部技術顧問 |
| 四半期 | 経営会議で報告：リスクの一覧、予算、未対応事項 | 経営層 |
| 年 1 回 | 机上演習、プレイブックの見直し、全社研修 | CSIRT 全員 |
| 入社時 | セキュリティ研修、端末の受け渡し | 情シス |

### ベンチャーでつまずきやすい点

- **開発者が SaaS を勝手に契約する。** 経費精算のデータから SaaS の利用を洗い出し、台帳に戻す運用が効きます。
- **鍵やトークンを個人が持ち続ける。** 退職時の停止チェックリストに、GitHub、クラウド、外部 API の鍵を含めます。
- **管理者権限が 1 人に集中する。** 情シスが 1 人なら、管理者権限を持つ人を必ず 2 人にします（もう 1 人は開発リードか外部技術顧問）。
- **規程だけ作って終わる。** 定例と演習を先に予定表へ入れておかないと、体制は形だけになります。

## まとめ

- CTO / CISO が不在でも、その**機能**（意思決定・運用・有事統制）は誰かに割り振る必要がある
- 体制は NCA・IPA・経済産業省・JPCERT/CC の公開資料を土台に設計するのが近道
- 「経営層が決める」「情シスが実行する」「兼務 CSIRT が有事に判断・調整する」の 3 層に分け、足りない技術判断は外部技術顧問で補う
- 体制を動かすには、SSO と MFA、MDM と EDR、台帳、監査ログ、バックアップといった技術的な土台が先に要る
- 100 人規模のベンチャーなら、本番環境を持つ開発側を CSIRT に入れ、90 日で「任命と棚卸し → 前提要件 → 有事の備え」の順に立ち上げる
- 判断する人と実行する人を分けておくことが、少人数組織で現場にリスクを集中させないための鍵になる
