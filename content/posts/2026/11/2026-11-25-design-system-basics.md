## はじめに

デザインシステム（Design System）とは、Web サイトやアプリなどのデジタルプロダクト開発で、UI の見た目・挙動・設計思想に一貫性を持たせるための「仕組み」です。中身はルール・部品・ガイドラインの集合体です。

デザインシステムは、デザインガイドライン（PDF の資料など）や UI パーツ集と混同されがちです。しかし実際は、それらを含みつつ、さらに広い仕組みです。**デザイナーとエンジニアが共通の言語・ツールを使い、プロダクトを効率的に開発・運用し続けるための仕組み全体**を指します。資料を一度作って終わりではなく、プロダクトとともに更新され続ける点が本質です。

この記事では、デザインシステムの構成要素、導入するメリット、参考になる公開事例と始め方を整理します。

## デザインガイドライン・UI パーツ集との違い

3 つを並べると、デザインシステムがどこまでを含むのかがわかりやすくなります。

| 観点 | デザインガイドライン | UI パーツ集 | デザインシステム |
| --- | --- | --- | --- |
| **形式** | PDF やスライドなどの資料 | 部品のデザインデータやコード | 原則・トークン・部品・ドキュメント・運用ルールの組み合わせ |
| **主な利用者** | 主にデザイナー | デザイナーまたはエンジニアのどちらか | デザイナーとエンジニアの両方 |
| **伝えるもの** | 見た目のルール | 使える部品 | ルール・部品に加えて、その使い方と判断の理由 |
| **更新** | 作った時点で止まりがち | 部品単位で場当たり的に増える | 運用ルールに沿って継続的に更新する |

ガイドラインや UI パーツ集は、デザインシステムの一部として取り込まれます。違いは「誰が、どう使い続けるか」まで設計されているかどうかです。

## デザインシステムを構成する 5 つの要素

デザインシステムは、おおむね次の 5 つの要素で構成されます。

| 要素 | 内容 | 具体例 |
| --- | --- | --- |
| **デザイン原則** | プロダクトが大切にすべき価値観や判断基準 | 「迷わせない」「誰にでも使える（アクセシビリティ）」 |
| **デザイントークン** | 色・余白・文字サイズなどの最小単位の変数データ | `color-primary: #0066cc`、`spacing-md: 16px` |
| **スタイルガイド** | タイポグラフィ、配色、アイコン、レイアウトのルール | フォントの種類と階層、エラー時の色の使い方 |
| **UI コンポーネント** | 再利用可能な部品の集まり（デザインツール Figma のデータと実装コード） | ボタン、入力フォーム、モーダル、ナビゲーション |
| **ドキュメント・運用ルール** | 部品の使い方、NG 例、システム自体の更新・管理フロー | 「このボタンは 1 画面に 1 つまで」などの利用規約 |

これらは並列というより、下の層が上の層を支える積み重ねとして捉えると理解しやすくなります。

- **デザイン原則**: 判断の拠り所
- **デザイントークン**: 原則を具体的な値に落としたもの
- **スタイルガイド**: トークンをどう使うかのルール
- **UI コンポーネント**: トークンとスタイルガイドに従って作られた部品
- **プロダクト画面**: コンポーネントの組み合わせでできあがる

ドキュメントと運用ルールは、すべての層にまたがってシステムを維持します。

### デザイントークンの具体例

デザイントークンは、デザインの判断を「名前のついた値」として管理するものです。たとえば CSS のカスタムプロパティで表すと次のようになります。

```css
:root {
  /* 色 */
  --color-primary: #0066cc;
  --color-danger: #d93025;

  /* 余白 */
  --spacing-sm: 8px;
  --spacing-md: 16px;

  /* 文字サイズ */
  --font-size-body: 16px;
}

.button-primary {
  background-color: var(--color-primary);
  padding: var(--spacing-sm) var(--spacing-md);
  font-size: var(--font-size-body);
}
```

コンポーネント側は `#0066cc` という生の値ではなく `--color-primary` という名前を参照します。ブランドカラーを変えるときはトークンの値を 1 か所直すだけで、そのトークンを使うすべての部品に反映されます。Figma 側でも同じ名前の変数を定義しておけば、デザインと実装が同じ語彙を共有できます（以降、CSS 以外の文脈ではトークン名の `--` を省いて表記します）。

デザイントークンを JSON で構造化する仕様として、W3C Design Tokens Community Group（DTCG）の仕様があります。この仕様や、AI エージェントにデザインの意図を伝える使い方は、[AIエージェントにデザインの意図を伝える：コンセプトの言語化とW3C DTCGデザイントークン](/blogs/posts/2026/11/design-concept-and-design-tokens-for-ai-agents/)で詳しく扱っています。

## デザインシステムを導入する 3 つのメリット

### 1. ユーザー体験（UX）の一貫性

画面や機能ごとにボタンの形や操作感がバラバラになるのを防げます。同じ見た目のものは同じように動きます。そのためユーザーは一度覚えた操作をほかの画面でもそのまま使え、直感的で使いやすい体験につながります。

### 2. 開発・デザインスピードの向上

毎回ゼロからボタンやフォームを作る「車輪の再発明」がなくなります。既存の部品を組み合わせるだけで、画面を素早く組み立てられます。その分、デザイナーもエンジニアも、プロダクト固有の課題の検討に時間を使えるようになります。

### 3. 職種間のコミュニケーションの円滑化

デザイナーとエンジニアが同じ名称（トークン名やコンポーネント名）で会話できます。「この青」「あのくらいの余白」といった曖昧な指示が `color-primary` や `spacing-md` に置き換わるので、認識の齟齬や実装時の手戻りが減ります。

## 代表的なデザインシステムの例

公開されているデザインシステムを眺めると、構成要素がどのように文書化されているのか具体的なイメージが掴めます。

| 名称 | 提供元 | 特徴 |
| --- | --- | --- |
| [Material Design](https://m3.material.io/) | Google | Android や Web で広く使われる体系 |
| [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/) | Apple | iOS や macOS の設計思想とルール |
| [デジタル庁デザインシステム](https://www.digital.go.jp/policies/servicedesign/designsystem) | デジタル庁 | 日本の行政サービス向けに公開されている、アクセシビリティ重視のシステム |
| [SmartHR Design System](https://smarthr.design/) | SmartHR | 国内企業の公開事例。React の UI コンポーネント集 smarthr-ui を OSS として公開 |
| [Spindle](https://spindle.ameba.design/) | サイバーエージェント（Ameba） | 国内企業の公開事例。Ameba のデザインシステムで、コンポーネントやアイコンを GitHub で公開 |

国内の事例は日本語のタイポグラフィや文言のルールまで踏み込んでいるものが多く、日本語のプロダクトを作るなら特に参考になります。

## 始め方と注意点

公開事例のような大規模なシステムを、最初から丸ごと作る必要はありません。小さく始めて育てるのが現実的です。

1. **既存 UI の棚卸し**：いまの画面にあるボタン・色・余白を洗い出し、似ているのに微妙に違うものを見つける
2. **トークンの定義**：洗い出した色や余白を、名前のついたトークンにまとめる
3. **よく使う部品から作る**：ボタンや入力フォームなど、多くの画面で使う部品からコンポーネント化する
4. **運用体制を決める**：誰が変更を承認し、どう周知するかを決めておく

注意したいのは、デザインシステムは作って終わりではなく、維持にも手間がかかる点です。

- **運用コスト**：部品の追加や仕様変更のたびに、デザインデータ・実装・ドキュメントをそろえて更新する必要があります。
- **作りすぎ**：使われない部品やルールまで先回りして用意すると、メンテナンスの負担だけが増えます。
- **形骸化**：更新されなくなったシステムは、現場が独自の部品を作り始めて、かえって不統一の原因になります。

小さなチームや短期のプロジェクトでは、まずトークンだけを共有するなど、身の丈に合った範囲から始めるのがよいでしょう。

## まとめ

- デザインシステムは、ガイドライン資料や UI パーツ集にとどまらない、デザイナーとエンジニアが共通の言語で開発・運用し続けるための仕組みです。
- 構成要素は、デザイン原則・デザイントークン・スタイルガイド・UI コンポーネント・ドキュメントと運用ルールの 5 つです。
- 導入すると、UX の一貫性、開発スピードの向上、職種間のコミュニケーションの円滑化が得られます。
- まずは Material Design やデジタル庁デザインシステムなどの公開事例を読み、自分たちに必要な要素を見極めましょう。そのうえで、既存 UI の棚卸しとトークンの定義から小さく始めるのがおすすめです。運用コストと作りすぎには注意が必要です。
