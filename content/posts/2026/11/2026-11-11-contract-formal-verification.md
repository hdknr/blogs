契約書の整合性チェックに形式手法（Formal Methods）を使うと、**条項どうしの論理的な矛盾やデッドロック、期限の破綻、条件分岐の漏れ**を機械的に洗い出せます。

契約書は「当事者の合意に基づき、特定の条件がそろうと状態が遷移する」仕組みを文章で書いたものです。発効・履行中・停止・解除といった状態があり、通知や支払い、期限の経過といったイベントで状態が移ります。これは状態遷移を持つプログラムとほぼ同じ構造です。そのため、ソフトウェアの設計検証で使われてきた数理論理のアプローチがそのまま当てはまります。

この記事では、形式手法で契約書の何を検証できるのか、どのツールが向いているのか、どこに限界があるのかを整理します。そのうえで、実際に存在するプロダクトや研究プロジェクトの現状を紹介します。先に結論を言うと、自然言語の契約書を丸ごと自動で形式検証してくれる汎用サービスは、まだ見当たりません。

## 形式手法で検出できる契約書の 3 種類の不整合

### 1. 論理的矛盾とデッドロック

たとえば次のような条項の組み合わせを考えます。

- 条項 A：「解除権を行使するには、事前に書面で催告しなければならない」
- 条項 B：「相手方が破産を申し立てた場合は、催告なしで直ちに解除できる」

条項 B が条項 A の例外であることを明記していなければ、両者は矛盾します。また「解除された契約に対して、さらに更新通知を求める」といった、**契約の終了後には実行できないアクションを要求する規定**が紛れ込むこともあります。

この記事では、このように「義務が残っているのに、それを果たす手段がない状態」をデッドロックと呼びます。モデル検査（Model Checking）では、契約を状態遷移モデルとして書き下し、到達しうる全状態を探索します。その結果、「契約が終了した状態なのに、まだ何かのアクションが要求されている」といったデッドロックを自動で見つけられます。

### 2. 期間・期限の不整合

「通知を受領してから 30 日以内に是正すればよい」という条項があるとします。同じ契約に「通知の発効から 14 日後に解除の効力が生じる」という条項もあると、是正期間が終わる前に契約が解除されてしまいます。

この種のタイムラインの破綻は、時相論理で表現できます。線形時相論理（LTL）や計算木論理（CTL）、時間制約を扱うリアルタイム時相論理などです。「ある事象が起きたら、将来のある時点で別の事象が必ず可能になる（あるいは不可能になる）」という性質を書いておけば、それが成り立つかどうかを機械的に検証できます。

### 3. 網羅性（条件分岐の漏れ）

人間のレビューで見落としやすいのが、**条件分岐の else ケースの欠落**です。「A の場合は X、B の場合は Y」と書かれていても、A でも B でもない場合に何が起きるかが書かれていないことは珍しくありません。

Alloy や TLA+ でモデル化して検査すると、こうした抜けがあれば、意図しない状況が具体的な反例（Counterexample）として提示されます。

## Alloy・TLA+・Z3（SMT ソルバ）の使い分け

SMT ソルバ（Satisfiability Modulo Theories ソルバ）は、整数や不等式を含む論理式について、すべてを同時に満たす値が存在するかを自動で判定するツールです。

| 手法・ツール | 得意な領域 | 契約検証での役割 |
| --- | --- | --- |
| **Alloy / TLA+** | 状態遷移と不変条件のモデル検査 | 契約の状態（発効・履行中・停止・解除）の遷移関係や、不変条件（例：「解除後に新たな履行義務が発生しない」）を検証し、反例を可視化する |
| **SMT ソルバ（Z3 など）** | 制約充足・論理的含意 | 支払期日、遅延損害金の計算式、閾値条件といった算術的・論理的な制約が互いに両立するかを調べる |
| **契約向け DSL / スマートコントラクト** | 実行可能な仕様の記述 | Accord Project や Lexon（後述）など、法文とコードを橋渡しする言語で契約を書き、検証や実行にかける |

状態の移り変わりが問題になるならモデル検査、数値や条件式の両立が問題になるなら SMT ソルバ、という切り分けが目安です。TLA+ のモデル検査器 TLC の仕組みについては「[TLA+ のモデル検査器 TLC とは](/blogs/posts/2026/11/tla-plus-tlc-model-checker/)」で詳しく解説しています。

## 実用上の課題と限界

形式手法は強力ですが、契約書ならではの性質がいくつかの壁になります。

### 意図的な曖昧さ（Constructive Ambiguity）

契約書には「合理的な範囲で」「信義誠実の原則に従い」「速やかに」といった文言が頻繁に登場します。これらは厳密な定義をあえて避け、後の当事者協議や裁判所の判断に委ねるための表現です。こうした要素は、離散的な数理モデルに落とし込むのが困難です。

### モデル化のコストと翻訳ミス

自然言語の契約書を形式論理に書き換える作業（Formalization）には大きなコストがかかります。しかも、書き換えの段階で解釈を誤れば、どれほど厳密に検証しても「誤ったモデル」の正しさを証明しているだけになります。

### 強行法規・判例との関係

契約書単体で論理的に閉じていても、公序良俗や消費者保護法、労働基準法などの強行法規に反していれば、その条項は無効になります。判例によって条項の解釈が変わることもあります。契約書だけを対象にした閉じたモデルでは、こうした外部の法規範との衝突は検出できません。

## 実務での現実的なアプローチ — LLM と形式検証の連携

現時点で現実的なのは、次の 2 つを組み合わせた運用です。

1. **LLM と形式論理エンジンの連携（ニューロシンボリック）**：自然言語の契約書から LLM が条件・関係・遷移ルールを抽出し、Z3 や Alloy の記述に変換したうえで、ソルバやモデル検査器で厳密に検証する。LLM が得意な「読み取り」と、ソルバが得意な「網羅的な証明」を分担させる構成である。
2. **対象を絞る**：売買取引の決済フロー、SLA（サービス水準合意）の計算、ライセンスの失効ロジック、デリバティブ契約（国際スワップ・デリバティブズ協会の ISDA マスター契約など）のように、**数値・期限・明確な状態遷移が中心になる契約分野に限定して導入する**。

意図的な曖昧さが多い条項は人間の判断に任せ、ロジックとして書ける部分だけを形式検証にかける、という線引きが現実的です。

## 契約の形式検証を扱うプロダクト・プロジェクトの現状

「自然言語の契約書をそのまま入力するだけで形式検証してくれる汎用ツール」は、まだ市場に確立されていません。一方で、特化型のフレームワークやオープンソース、近接領域のプロダクトはいくつも存在します。

### 計算可能契約（Computable Contracts）の DSL・フレームワーク

自然言語の契約と実行可能なコードを対応づけ、整合性や実行可能性を担保する領域です。

- **Accord Project（Cicero / Ergo）**：スマートリーガルコントラクト（機械が実行できる契約）のためのオープンソースプロジェクトで、2019 年から Linux Foundation がホストしている。契約テンプレートの文面とデータモデル、ロジックを結びつける。ロジックの記述には、型付きで決定論的な関数型 DSL である Ergo が使われてきた。ただし近年は Ergo と Cicero を非推奨とし、汎用プログラミング言語ベースへの移行を進めている。
- **Lexon**：英文に近い文法で書けて、そのまま機械が解釈できる契約向けのプログラミング言語。法律家が読める文面から、Solidity などの実行可能なコードにコンパイルされる。

なお、Accord Project の創設に関わった企業 Clause は、契約データと外部イベントを連動させるサービスを提供していました。Clause は 2021 年に DocuSign に買収されています。

### スマートコントラクト向けの形式検証ツール

商用化が最も進んでいるのが、ブロックチェーン上の契約（スマートコントラクト）を対象にした形式検証です。紙の契約書ではありませんが、**契約ロジックのバグやデッドロックを数学的に検出する**という目的は同じです。

- **Certora Prover**：スマートコントラクトに対して、事前条件・事後条件・不変条件（Invariants）を仕様として書き、SMT ソルバで成り立つことを証明するツール。「どんな入力でも資金がロックされない」「権限のない者が操作できない」といった性質を検証できる。
- **CertiK**：スマートコントラクトのセキュリティ監査を手がける企業で、形式検証の技術も監査に取り入れている。
- **Runtime Verification（K Framework / KEVM）**：形式手法の研究者が創業した企業。プログラミング言語の意味論を定義する K Framework を基盤に、Ethereum 仮想マシンを形式化した KEVM などを使って、スマートコントラクトの検証サービスを提供している。

### 研究発のプロジェクト

自然言語の契約書を形式論理に変換して検証する取り組みは、論文やオープンソースとして公開されています。

- **Symboleo（カナダ・オタワ大学ほか）**：契約の仕様記述と形式検証のための言語とツール群。義務（Obligations）と権能（Powers）、イベント、状態遷移を形式的に定義し、記号的モデル検査器 nuXmv と連携して「義務どうしの衝突」や「履行不可能な状態」を検証する。
- **Stanford CodeX（Computational Law）**：スタンフォード大学の法情報学センター CodeX では、法律や契約のルールを論理プログラミングで表現し、整合性や特定シナリオでの帰結を推論する「計算法学（Computational Law）」の研究が進められている。

## LLM 型のリーガルテック SaaS との違い

日本の「LegalOn」や「クラウドサイン レビュー」、海外の「Harvey」「Ironclad」「Spellbook」といった契約書レビュー SaaS があります。これらは形式手法（数理論理）ではなく、**大規模言語モデル（LLM）や機械学習による統計的なテキスト解析**を基盤にしています。

- **LLM 型の強み**：PDF や Word の契約書をそのまま投入すれば、不利な条項の指摘、条文の抜け、言い回しのチェックがすぐにできる。
- **形式手法との決定的な違い**：LLM が返すのは「もっともらしい」判断である。複雑な条件分岐が交差したときに「デッドロックが存在しない」「どの例外ケースでも論理が破綻しない」ことを網羅的に証明することはできず、ハルシネーションや見落としのリスクが残る。

## まとめ

- 契約書は状態遷移を持つプログラムとみなせるため、モデル検査や SMT ソルバで**矛盾・デッドロック・期限の破綻・条件分岐の漏れ**を検出できる
- 一方で、意図的な曖昧さ、モデル化のコスト、強行法規との関係といった限界があり、契約書全体を形式検証するのは現実的ではない
- 法務担当者が Word ファイルをアップロードするだけで裏で Alloy や Z3 が動き、論理矛盾を指摘してくれるような**完全自動の汎用サービスは、確認できた範囲ではまだ存在しない**
- これまで試みられてきたのは「Accord Project や Lexon などの DSL で最初から契約を書く」アプローチと、「スマートコントラクトとしてコード化し Certora などで検証する」アプローチの 2 つが中心。前者は Accord Project が独自 DSL から汎用言語ベースへ移行するなど、まだ模索が続いている
- LLM で自然言語契約を DSL・形式言語へ自動翻訳し、裏でソルバを走らせる研究や PoC は活発で、この仕組みを組み込んだリーガルテック製品が今後登場する可能性は高い

数値・期限・状態遷移が中心の定型的な取引ルールから、まず形式検証を試してみるのが現実的な第一歩です。
