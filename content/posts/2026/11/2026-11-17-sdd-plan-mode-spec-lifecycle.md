## はじめに

CodeZine に「[仕様駆動開発への期待と誤解 ～「仕様」とは、結局何なのか～](https://codezine.jp/article/detail/23908)」という記事が掲載されました。2026 年 4 月 23 日の掲載で、著者は NTT テクノクロスの渡邉洋平氏です。コーディングエージェントを使った開発手法を扱う連載の 1 本で、仕様駆動開発（Spec-driven Development、SDD）を「Vibe Coding」や「Planモード」と比べながら、その利点と懸念を整理しています。

この記事を紹介した和田卓人（t_wada）氏の[ポスト](https://x.com/t_wada/status/2047465643956716000)が、論点を短くまとめています。

> SDDへの過剰な期待や誤解、現実がよく整理されている。最近のPlanモードとSDDの違いは、作成された仕様書をどのように扱うか（Spec-first なのか Spec-anchored/Spec-as-source なのか）という一点に絞られてきている

先に結論を書くと、**Planモードと SDD は実装前には同じことをしていて、違いは実装の後で仕様書を保守し続けるかどうかだけ** です。本記事では、このポストの見立てを軸に次の 3 点を整理します。

- Planモードと SDD は何が同じで、何が違うのか
- Spec-first / Spec-anchored / Spec-as-source の違いは何か
- 自分のプロジェクトでどれを選び、何を準備すればよいか

### 用語

| 用語 | 意味 |
|---|---|
| Vibe Coding | 仕様を固めずに AI と対話しながら、動くものを直接作っていく進め方 |
| Planモード | Claude Code などのコーディングエージェントが持つ、実装の前に計画を立てて人間の承認を取るモード |
| 仕様駆動開発（SDD） | 仕様書を先に書いてレビューし、それを入力として AI に実装させる進め方 |
| Spec-first / Spec-anchored / Spec-as-source | 実装の後で仕様書をどう扱うかによる SDD の 3 つのレベル（後述） |
| 正本 | 食い違いがあったときに正しいとみなす、拠り所の文書（Single Source of Truth） |

## Planモードと SDD は「実装前」では同じことをしている

CodeZine の記事は、Planモードを、実装したがる AI エージェントにまず考えさせ、実装前に人間の意図をはっきりさせるためのブレーキのような機能として説明しています。SDD も、要求から設計・タスクへと書き下したものを人間がレビューし、承認してから実装に進みます。Vibe Coding には、AI がいきなり書き始めて意図とずれたものを量産するという弱点があり、どちらもそれを補う手段です。

つまり **実装前の段階だけを見ると、Planモードと SDD はほとんど同じことをしています**。意図を言語化し、AI に計画を出させ、人間がゲートとして承認する、という流れです。

違いが出るのは実装が終わった後、つまり **書いたものを次の変更のときにどう扱うか** です。t_wada 氏のポストが「一点に絞られてきている」と言っているのは、この部分です。

## 実装後の扱いで分かれる SDD の 3 つのレベル（Spec-first / Spec-anchored / Spec-as-source）

この 3 つの分類は、Thoughtworks の Birgitta Böckeler 氏が martinfowler.com で公開した「[Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)」によるものです。

![Planモードと仕様駆動開発の3つのレベルについて、実装前・実装・次の変更のときに計画や仕様書がどう扱われるかを比べた図](/blogs/images/sdd-plan-mode-spec-lifecycle.png)

| レベル | 実装後の仕様書 | 人が編集するもの |
|---|---|---|
| Spec-first | 目の前のタスクのために書くが、その後は保守しない | 主にコード |
| Spec-anchored | 残して、その機能の変更や保守のたびに更新する | 仕様書とコードの両方 |
| Spec-as-source | 長期にわたって保守する主な成果物（正本）にする | 仕様書だけ（コードは生成物） |

Böckeler 氏によると、調べた SDD のアプローチや定義はどれも Spec-first に当てはまります。一方、Spec-anchored や Spec-as-source まで目指しているものは一部にとどまります。また、仕様書を長期にわたってどう保守するかは、曖昧なまま残されがちだとも述べています。

ここで Planモードを並べると、**Planモードは Spec-first をさらに軽くしたもの** と見ることができます。計画はセッションの中で合意して実装に使い、終われば役目を終えます。ファイルとして残る場合でも、次の変更のときに正本として読み直す前提はありません。

### Spec-first は Planモードに吸収されつつある

CodeZine の記事の著者である渡邉氏は、別の発表資料「[仕様駆動開発の消費期限](https://speakerdeck.com/watany/expiration-date-of-sdd)」で、Spec-first のスタイルは Planモードに合流し、多くのコーディングエージェントに備わった当たり前のものになりつつある、と述べています。

そうなると、「SDD を導入する」と言ったときに Planモードと区別できる中身は、Spec-anchored か Spec-as-source の部分だけになります。

## SDD によくある期待と、実際に起きること

SDD に寄せられる期待のうち、実装後の扱いを決めないと裏切られるものを挙げます。

| 期待 | 実際に起きること |
|---|---|
| 仕様書を書けばドキュメントが揃う | Spec-first のままだと、最初の変更から仕様書とコードがずれ始める。古い仕様書は、無いより悪い誤情報になる |
| ツールを入れれば SDD になる | Böckeler 氏の評価では、Kiro は主に Spec-first。Spec Kit も GitHub は Spec-anchored を志向しているように見えるが、仕様ごとにブランチを作る設計から、Böckeler 氏は Spec-first にとどまると評価している。ツールが仕様書の保守まで強制してくれるわけではない |
| 仕様書が詳しいほど AI の出力が安定する | 仕様書が長くなるほど、人間のレビューが追いつかなくなる。読まれずに承認される仕様書は、ゲートとして機能しない |
| 仕様書があればコードを読まなくてよい | それが成り立つのは Spec-as-source だけで、生成の再現性が前提になる。Spec-anchored では人もコードを編集する |

「仕様書を書くこと」と「仕様書を保守すること」は別の作業で、SDD の効果の大半は後者から来ます。書くだけなら Planモードで足ります。では、保守すべき「仕様」とは何でしょうか。

## 「仕様」とは結局何なのか

CodeZine の記事の副題でもあるこの問いに、実装後の扱いという観点から答えるなら、こう言えます。

**仕様とは、次の変更のときに正本として読み直され、更新されるもの** です。一度きりの合意に使って捨てるものは、計画（プラン）と呼ぶほうが実態に合っています。

この線を引くと、プロジェクトの中にある成果物を次のように仕分けられます。

| 成果物 | 扱い | 置き場所の例 |
|---|---|---|
| 実装計画・タスクリスト | 使い捨て（計画） | Planモードの出力、PR の説明 |
| 機能の振る舞い・業務ルール | 保守する（仕様） | `docs/spec/` 配下の Markdown など |
| 受け入れ条件 | 保守し、実行できる形にする | 受け入れテスト、Gherkin（Given/When/Then で振る舞いを書く記法）のシナリオ |
| 設計判断の理由 | 追記していく | ADR（Architecture Decision Record） |

仕様を保守する仕組みとして最も確実なのは、**仕様から導いたテストを CI で回すこと** です。文章の仕様書はコードと黙ってずれていきますが、テストはずれた時点で落ちます。Spec-anchored を名乗るなら、少なくとも受け入れ条件はテストとして実行できる形にしておくのが現実的です。

## Planモードか SDD か：プロジェクト別の選び方

判断の軸は「そのコードを何回変更するか」と「仕様を読み直す人が自分以外にいるか」です。

- **使い捨てのスクリプトや検証用のプロトタイプ**：Planモードで十分です。仕様書を残しても読み直す機会がありません
- **一人で短期間に作る小さなツール**：Planモード、または Spec-first で始めます。仕様書を残すなら、古くなったら消す前提で置きます
- **チームで長く保守するプロダクト**：Spec-anchored を目指します。ツールの導入より先に、次のルールを決めます
  - 機能の変更では、ドラフト PR の段階で仕様書の差分だけを先にレビューし、承認されてから同じ PR に実装を追加する
  - 仕様書とコードの変更は同じ PR に入れる
  - 受け入れ条件はテストとして CI で検証する
- **API の定義から生成するクライアントやスキーマなど、コードを生成物として扱える部分**：この範囲に限って Spec-as-source を適用できます

Spec-anchored のルールは、たとえば PR テンプレートに次のようなチェック項目として入れておくと、日々の運用に乗せやすくなります。

```markdown
## 仕様との整合

- [ ] 振る舞いが変わる場合、`docs/spec/` の該当箇所を同じ PR で更新した
- [ ] 実装を追加する前に、仕様書の差分をレビューしてもらった
- [ ] 受け入れ条件に対応するテストを追加・更新した
```

## まとめ

- Planモードと SDD は、実装前に意図を言語化して人間が承認する点では同じです
- 両者の違いは、書いた仕様書を実装の後でどう扱うか（Spec-first か、Spec-anchored / Spec-as-source か）の一点に絞られてきています
- Spec-first は Planモードに吸収されつつあり、SDD を導入する意味は「仕様書を保守し続ける仕組み」を持てるかどうかで決まります
- どちらを選ぶかは、コードを何回変更するかと、仕様を読み直す人が自分以外にいるかで決めます
- 仕様を保守する仕組みは、ツールよりも運用ルールと、仕様から導いたテストで作ります

SDD の 3 つのレベルや代表的なツールの全体像は、[仕様駆動開発（SDD）とは？ 3 つのアプローチ・EARS 記法・Kiro / Spec Kit・TDD との違い](/blogs/posts/2026/11/spec-driven-development-overview/) でも整理しています。
