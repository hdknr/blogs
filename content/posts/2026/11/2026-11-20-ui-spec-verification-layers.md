言語化した UI 仕様が正しいかどうかは、どうやって確かめればよいのでしょうか。形式手法を使えばよいのでしょうか。答えは「形式手法も使う。ただし効くのは一部」です。仕様の検証は、**何と照らし合わせるか**で 4 つの層に分かれ、層ごとに向く道具が違います。

この記事は「[AIが作ったUIモックを仕様にする3つの方法](/blogs/posts/2026/11/mock-ui-spec-verbalization/)」の続編です。前回は、AI エージェントが作った UI モックを、A2UI・仕様駆動開発・デザイントークンで仕様にする方法を整理しました。今回は、そうして書いた仕様を検証する 4 つの層を整理します。形式手法が効く層については、手元で動く小さな例を 2 つ示します。

## 登場する道具と用語

| 名前 | 一言でいうと |
|---|---|
| 形式手法 | 仕様を数学的なモデルにして、検査器に正しさを調べさせる手法の総称 |
| 反例 | 「この性質は成り立たない」ことを示す具体的な入力や手順。検査器が見つけて返す |
| 陽性対照 | わざと誤りを入れた対象で、検査が誤りを検出できることを先に確かめること |
| Z3 | Microsoft Research が開発した SMT ソルバ。条件を満たす値があるかを探す |
| TLA+ / TLC | 状態遷移のモデルを書く言語と、到達できる全状態を総当たりで調べるモデル検査器 |
| EARS / Gherkin | 要件や振る舞いを決まった型で書く記法（[EARS](/blogs/posts/2026/11/ears-requirements-syntax/)、[Gherkin](/blogs/posts/2026/11/gherkin-bdd-cucumber/)） |
| ビジュアル回帰テスト | 画面のスクリーンショットを基準画像と比べて、見た目の変化を検出するテスト |

## 検証の 4 つの層

![UI モックの仕様を検証する 4 つの層を示す図。上から、書式（仕様と決まった型を照らし、機械が判定）、仕様の中の整合（仕様と仕様自身を照らし、形式手法で機械が判定）、実装との一致（仕様と実装を照らし、テストで機械が判定）、意図との一致（仕様と利用者の意図を照らし、人が判定）が並ぶ。形式手法で見つけた反例を、利用者への質問に変えて返す矢印がある。下の層ほど手間がかかり、機械に任せにくい](/blogs/images/ui-spec-verification-layers.png)

| 層 | 何と照らし合わせるか | 判定するのは | 見つかる誤りの例 |
|---|---|---|---|
| 1. 書式 | 仕様 ↔ 決まった型 | 機械 | 必須の属性の抜け、存在しないトークンへの参照 |
| 2. 仕様の中の整合 | 仕様 ↔ 仕様自身 | 機械（形式手法） | 抜け出せない画面、ルールの抜けと矛盾 |
| 3. 実装との一致 | 仕様 ↔ 実装 | 機械（テスト） | 仕様と違う遷移、見た目のずれ |
| 4. 意図との一致 | 仕様 ↔ 利用者の意図 | 人 | 矛盾はないが、利用者の望みと違うルール |

形式手法が主役になるのは 2 つ目の層です。以下、上から順に見ていきます。

## 1. 書式：決まった型どおりに書けているか

一番安く、最初にやるべき層です。前回の記事で挙げた仕様の形式は、どれも機械で書式を検査できます。

- **A2UI などの生成 UI の JSON**：JSON Schema と、クライアントのコンポーネントカタログで検証します。カタログにない部品や必須の属性の抜けは、ここで弾けます。
- **デザイントークン**：DTCG フォーマットに対応したツール（Style Dictionary など）に通すと、型の誤りや存在しないトークンへの参照が見つかります。
- **EARS と Gherkin**：決まった型があるので、型から外れた文を検出できます。「速やかに」「適切に」のように、人によって解釈が分かれる語を見つけるのも、この層で機械化できます。

この層で見つかるのは「書き方の誤り」だけです。中身の矛盾までは見つかりません。

## 2. 仕様の中の整合：形式手法で矛盾や抜けを見つける

ここが形式手法の出番です。UI の仕様のうち、**論理として書ける部分**は形式化できます。

- **画面の状態遷移**：抜け出せない状態がある、どこからも到達できない画面がある
- **決定表・業務ルール**：どのルールにも当てはまらない入力がある（抜け）、結果の違う 2 つのルールに同時に当てはまる入力がある（矛盾）
- **権限**：一般ユーザーが管理画面に行ける経路がある

形式手法の強みは、問題があるときに**反例**を返してくれることです。「たぶん大丈夫」ではなく、「この入力のときに破れる」という具体的な値が手に入ります。

小さな例を 2 つ動かしてみます。

### 例 1：状態遷移から抜け出せない状態を探す

予約フォームの状態遷移を、EARS で次のように仕様にしたとします。

```text
When the user presses "確認", the system shall show the confirmation screen.
When the user presses "戻る" on the confirmation screen, the system shall return to the input screen.
When the user presses "送信" on the confirmation screen, the system shall submit the reservation.
When the submission succeeds, the system shall show the completion screen.
If the submission fails, then the system shall show the error screen.
```

書かれているのはここまでです。エラー画面の後に何ができるかは、どこにも書かれていません。

これを状態遷移の表にして、「どの状態からも、最終的に『完了』へたどり着けるか」を調べます。到達できるのに、そこから『完了』へ行けない状態を、ここでは**抜け出せない状態（トラップ状態）**と呼びます。この程度の規模なら、どの状態からどの状態へたどり着けるか（到達可能性）を Python で計算するだけで十分です。

```python
def trap_states(transitions, start, goal):
    # start から到達できる状態
    reachable, stack = {start}, [start]
    while stack:
        s = stack.pop()
        for (src, _event), dst in transitions.items():
            if src == s and dst not in reachable:
                reachable.add(dst)
                stack.append(dst)
    # goal に到達できる状態（逆向きにたどる）
    can_finish, changed = {goal}, True
    while changed:
        changed = False
        for (src, _event), dst in transitions.items():
            if dst in can_finish and src not in can_finish:
                can_finish.add(src)
                changed = True
    return sorted(reachable - can_finish)


buggy = {
    ("入力中", "確認"): "確認中",
    ("確認中", "戻る"): "入力中",
    ("確認中", "送信"): "送信中",
    ("送信中", "成功"): "完了",
    ("送信中", "失敗"): "エラー",
}
fixed = {**buggy, ("エラー", "再試行"): "確認中"}

print("修正前:", trap_states(buggy, "入力中", "完了"))
print("修正後:", trap_states(fixed, "入力中", "完了"))
```

実行結果です。

```text
修正前: ['エラー']
修正後: []
```

検査器は「エラー」を抜け出せない状態として返しました。モックで正常系だけを触っていると、見落としやすい抜けです。修正版では「再試行」で確認画面に戻れるようにしたので、抜け出せない状態はなくなりました。

状態が増えたり、「送信中に戻るボタンを押す」のような並行した操作を扱ったりする場合もあります。そのときは [TLA+ と TLC](/blogs/posts/2026/11/tla-plus-tlc-model-checker/) のようなモデル検査器に移ると、全状態の総当たりを任せられます。状態遷移をモデルとして書いてから検査する流れは、「[形式検証 Skill を作る前に状態遷移をモデルにする](/blogs/posts/2026/11/statechart-before-formal-verification/)」でも紹介しています。

### 例 2：決定表の抜けと矛盾を Z3 で探す

次は、一覧画面の「削除」ボタンを誰に見せるかのルールです。最初の仕様は次の 4 行でした。

| ルール | 条件 | 削除ボタン |
|---|---|---|
| R1 | 管理者（admin） | 表示 |
| R2 | 編集者（editor）で、自分の記事で、下書き（draft） | 表示 |
| R3 | 閲覧者（viewer） | 非表示 |
| R4 | アーカイブ済み（archived） | 非表示 |

一見よさそうですが、Z3 に調べさせると問題が 2 つ見つかります。Z3 は `pip install z3-solver` で入ります。

コードでは、最初の表を `v1`、修正版を `v2` として両方を検査します。`v2` では、R1 を「アーカイブ済み以外」に絞り、編集者のそれ以外の場合を「非表示」にする R5 を足しています。

```python
from z3 import And, Bool, Const, EnumSort, Not, Or, Solver, sat

Role, (ADMIN, EDITOR, VIEWER) = EnumSort("Role", ["admin", "editor", "viewer"])
Status, (DRAFT, PUBLISHED, ARCHIVED) = EnumSort(
    "Status", ["draft", "published", "archived"]
)
role, status, is_owner = Const("role", Role), Const("status", Status), Bool("is_owner")


def check(rules):
    """rules: (名前, 条件, 表示するか) のリスト"""
    # 抜け: どのルールの条件にも当てはまらない入力があるか
    s = Solver()
    s.add(*[Not(cond) for _, cond, _ in rules])
    if s.check() == sat:
        print("  抜け:", s.model())
    # 矛盾: 結果の違う 2 つのルールに同時に当てはまる入力があるか
    for i, (n1, c1, v1) in enumerate(rules):
        for n2, c2, v2 in rules[i + 1 :]:
            if v1 != v2:
                s = Solver()
                s.add(And(c1, c2))
                if s.check() == sat:
                    print(f"  矛盾: {n1} と {n2}:", s.model())


v1 = [
    ("R1", role == ADMIN, True),
    ("R2", And(role == EDITOR, is_owner, status == DRAFT), True),
    ("R3", role == VIEWER, False),
    ("R4", status == ARCHIVED, False),
]
v2 = [
    ("R1", And(role == ADMIN, status != ARCHIVED), True),  # アーカイブ済みを除く
    ("R2", And(role == EDITOR, is_owner, status == DRAFT), True),
    ("R3", role == VIEWER, False),
    ("R4", status == ARCHIVED, False),
    ("R5", And(role == EDITOR, Or(Not(is_owner), status != DRAFT)), False),  # 追加
]

print("v1（最初の表）")
check(v1)
print("v2（修正後）")
check(v2)
print("陽性対照（v2 から R5 を外す）")
check(v2[:-1])
```

実行結果は次のとおりです。

```text
v1（最初の表）
  抜け: [is_owner = False, status = draft, role = editor]
  矛盾: R1 と R4: [status = archived, role = admin]
v2（修正後）
陽性対照（v2 から R5 を外す）
  抜け: [is_owner = False, status = draft, role = editor]
```

最初の表には、次の 2 つの問題がありました。

- **抜け**：編集者が**他人の**下書きを開いたとき、どのルールにも当てはまりません。ボタンを出すのか出さないのか、仕様が決めていません。
- **矛盾**：管理者がアーカイブ済みの記事を開くと、R1 は「表示」、R4 は「非表示」で、結果がぶつかります。

修正版（v2）では、Z3 は何も報告しなくなりました。同じ手法で契約書の条項の矛盾を探した例は「[契約書を形式手法で検証する](/blogs/posts/2026/11/contract-formal-verification/)」にあります。

### 「反例なし」を信じる前に：陽性対照

ここで大事なのが、最後の「陽性対照」の行です。修正版で何も報告されなかったのは、本当に問題がなくなったからでしょうか。それとも、検査の書き方を間違えて、何も調べていないからでしょうか。出力だけでは区別できません。

そこで、R5 を外して**抜けがあるとわかっている表**を作り、検査がそれを見つけることを確かめます。抜けが再び報告されたので、抜けの検査は空振りしていないと言えます。矛盾の検査については、v1 で R1 と R4 の矛盾を検出できたことが陽性対照になっています。例 1 でも同じで、修正前のモデルで「エラー」が検出されたことが、検査が働いている証拠です。

検査が「問題なし」と答えたときは、検査そのものが壊れていないかを先に疑う。この考え方は「[陽性対照とは？](/blogs/posts/2026/11/positive-control-in-systems/)」で詳しく書いています。

### 形式手法が苦手なこと

一方で、「余白が心地よい」「情報の階層がわかりやすい」といった見た目の良し悪しは、形式化できません。形式手法を当てるのは、状態遷移・決定表・権限のように、**論理で書ける部分に絞る**のが現実的です。それ以外は、次の層 3 と層 4 で扱います。

## 3. 実装との一致：受け入れテストとビジュアル回帰テスト

3 つ目は、仕様をテストに変えて、実装と突き合わせる層です。

- **Gherkin のシナリオ**：Cucumber などで受け入れテストとして実行します。EARS の各行を 1 つ以上のテストに対応づけておくと、「テストのない要件」を数えられます。
- **状態遷移のモデル**：XState などで状態機械として書いておくと、XState のグラフ用のユーティリティでモデルからテストの経路を自動で作れます（モデルベーステスト）。例 1 の「エラーから再試行で戻る」のような、手で書くと漏れがちな遷移もテストに含まれます。
- **見た目**：Playwright の `toHaveScreenshot()` などでビジュアル回帰テストをすると、モックとの見た目のずれを検出できます。また、stylelint の `color-no-hex` ルールで色コードの直書きを禁止できます。こうしておけば、デザイントークン以外の色を使っていないことを機械で確かめられます。

形式手法で見つけた反例は、そのままテストケースにできます。例 2 の「編集者が他人の下書きを開く」は、受け入れテストの 1 シナリオになります。反例をテストに落とす流れは「[形式手法を Claude Code で回す](/blogs/posts/2026/10/formal-methods-claude-code-spec-check/)」でも扱っています。

## 4. 意図との一致：利用者が欲しいものか

最後の層は、形式手法でもテストでも検証できません。**仕様の中に矛盾がない**ことと、**利用者が欲しいものと一致している**ことは別の話だからです。矛盾と抜けを解消した v2 は「仕様としては正しい」形ですが、それが利用者の望むルールかどうかはわかりません。

この層では、次のように人が判断します。

- モックを見せながら、EARS の各行を利用者に読んでもらって確認する
- 形式手法で見つけた反例を、**「この場合はどうなるべきですか？」という質問に変えて返す**

後者の、反例を質問に変えて返す使い方が、形式手法の一番効く使い方だと私は考えています。例 2 の抜けは、修正版では「非表示」と決めましたが、本当は利用者に聞くべき問題です。「編集者が他人の下書きを開いたとき、削除ボタンは出しますか？」という質問は、仕様を書いた人も利用者も思いつかなかったものです。それを、検査器が機械的に見つけてくれます。

## UI 仕様の検証を始める優先順位

UI モックの仕様なら、次の順に手を付けると費用対効果が高くなります。層の番号とは 2 と 3 の順序が入れ替わりますが、テストのほうが導入しやすいためです。

1. **書式の検証（層 1）**：ほぼ無料。CI に入れておく
2. **受け入れテストとビジュアル回帰テスト（層 3）**：実装との一致を確かめる
3. **形式手法（層 2）**：状態の多い画面（ウィザード、承認フローなど）と、条件分岐の多い決定表に絞る
4. **反例を質問にして利用者に返す（層 4）**：3 で見つかったものから

画面全体を形式化しようとすると、モデルを仕様の変更に追従させる手間のほうが大きくなりがちです。例 2 のように、決定表 1 つを Z3 にかけるだけでも、人の目では見落とす抜けが見つかります。小さく始めるのがおすすめです。

## まとめ

- 言語化した UI 仕様の検証は、書式・仕様の中の整合・実装との一致・意図との一致の 4 つの層に分けて考える
- 形式手法が効くのは 2 つ目の層で、状態遷移・決定表・権限のように論理で書ける部分に絞って使う
- 検査器の「問題なし」は、わざと誤りを入れた対象で検出できることを確かめてから信じる（陽性対照）
- 形式手法で見つけた反例は、テストケースにし、利用者への質問にも変える

まずは手元の決定表を 1 つ、例 2 のコードに書き写して Z3 にかけてみてください。
