## はじめに

ウォーターフォール開発で設計が終わると、次に問われるのが「製造（実装）・単体テストから受け入れテストまで、あと何人日かかるのか」という見積もりです。設計工程までは実績が見えています。一方でテスト工程は、不具合の出方や外部システムとの調整に左右されやすく、見積もりが外れやすい部分です。

日本の SI（システムインテグレーション）業界では、工程ごとの工数配分を考える材料として、IPA（情報処理推進機構）の『ソフトウェア開発データ白書』のような公開統計が参照されることがあります。実務では、こうした工程配分の考え方と、設計書から積み上げるボトムアップ見積もりを組み合わせて算出することが多いでしょう。

この記事では、設計後の工数見積もりを次の 3 つの観点で整理します。

1. 工程別の工数比率で全体を割り振る（トップダウン）
2. 設計書から積み上げる（ボトムアップ）
3. 見積もりが外れる典型的な落とし穴を先に織り込む

**以下に出てくる比率・標準工数・係数は、IPA 白書の値ではなく、現場で使われる経験則の目安です。** 案件の性質やテストの粒度で大きく変わるので、組織の実績データがあるなら、そちらを優先してください。

## 用語の整理

| 用語 | 意味 |
| --- | --- |
| 製造 | プログラムの実装（コーディング） |
| 単体テスト（UT） | 関数・モジュール単位のテスト。実装者が行う |
| 結合テスト（IT） | Integration Test。モジュール間（内部結合）や他システムとの連携（外部結合）を確かめる |
| 総合テスト（ST） | System Test。システム全体を業務の流れに沿って開発側が確かめる |
| 受け入れテスト（UAT） | User Acceptance Test。発注者（以下、利用者）が主体となって、業務に使えるかを確かめる |
| 人日・人月 | 1 人が 1 日（1 か月）で行う作業量。1 人月 = 20 人日前後で換算することが多い |

## 1. 工程別の工数比率で見積もる（トップダウン）

全体工数、あるいは設計フェーズまでの工数が確定している場合は、工程ごとの比率を使って各工程の工数を割り振れます。次の表は、要件定義から総合テスト・受け入れテスト支援までを 100% としたときの配分の一例です。**出典のある統計ではなく、経験則として語られる配分の一つ**として読んでください。

| 工程 | 全体に対する比率（目安） | 含まれる作業 |
| --- | --- | --- |
| 要件定義・基本設計 | 25〜30% | 前提となる上流工程 |
| **詳細設計・製造・単体テスト** | **40〜45%** | 設計後の開発フェーズの中心。画面・帳票・バッチの本数や複雑度で変動する |
| **結合テスト** | **15〜25%** | 内部結合と外部結合のテスト設計・実施・不具合修正 |
| **総合テスト・受け入れテスト支援** | **10〜15%** | 開発側の総合テストと、利用者が行う UAT の支援 |

なお、IPA 白書が工程別に集計している「開発 5 工程」は基本設計・詳細設計・製作・結合テスト・総合テスト（ベンダ確認）で、要件定義や受け入れテスト支援は含みません。上の表とは区分が異なるので、白書の数値と並べて比べるときは範囲を揃えてください。

出典のある配分としては、Barry Boehm が『Software Engineering Economics』（1981 年）で示した COCOMO 81 の工程別工数配分が知られています。organic モード（経験のある小規模チームが、要件の厳密さが比較的緩い案件を開発する場合）の中規模案件（約 3.2 万行）では、次のとおりです（原典ではなく、COCOMO 81 を解説した講義資料の表に基づく値です）。

| 工程 | 比率 |
| --- | --- |
| 製品設計 | 約 16% |
| 詳細設計 | 約 24% |
| コーディング・単体テスト | 約 38% |
| 結合テスト | 約 22% |

COCOMO では計画・要件定義（約 6%）をこの 100% の外に別枠で足します。上の経験則の表で「詳細設計・製造・単体テスト」に当たる部分は、COCOMO では約 62% になり、かなり差があります。工程の切り方も、元になったデータの時代や開発形態（1970 年代後半に米 TRW 社で集めた 63 案件）も違うので、どちらが正しいというより、**文献や前提によって配分には幅がある**と考えるのが妥当です。だからこそ、自組織の実績比率を持っておく価値があります。

設計と製造の釣り合いも見ておきましょう。上の COCOMO 81 の配分で、製品設計を基本設計、詳細設計を詳細設計に当てはめて計算すると、設計（約 16% ＋ 約 24% ＝ 約 40%）に対してコーディング・単体テストは約 38% で、設計と製造はほぼ 1:1 になります（工程の対応づけはこの記事での読み替えで、COCOMO 自体が設計と製造の比を示しているわけではありません）。また、これは COCOMO の数値が示すことではなく実務上の一般論ですが、設計が曖昧なまま製造に入ると、手戻りが結合テストなどの後工程にまで及びやすいと言われます。

トップダウンの比率は、見積もりの「当たり」を付けたり、ボトムアップの結果が大きく外れていないかを確かめたりする物差しとして使うのが向いています。

## 2. 設計書から積み上げて見積もる（ボトムアップ）

設計が完了していれば、成果物である設計書が手元にあります。比率だけに頼らず、設計書から実態に即して積み上げることで精度を高めるのが基本です。

### 製造・単体テストの工数見積もり

設計書から画面数・帳票数・バッチ数・API 数などを数え、難易度別の標準工数（人日）を掛け合わせます。画面開発の場合の分類例は次のとおりです。

| 難易度 | 例 | 1 本あたりの標準工数（目安） |
| --- | --- | --- |
| 簡易 | 照会のみ、単純な登録 | 1〜2 人日 |
| 標準 | 検索＋一覧＋更新、標準的なバリデーション | 3〜5 人日 |
| 複雑 | 複雑な画面遷移、動的な制御、大量データ処理 | 6〜10 人日以上 |

単体テストの工数は、製造工数の 30〜50% を目安に見込みます。

### 結合テストの工数見積もり

結合テストは「内部結合（機能間の連携）」と「外部結合（外部システム・API との連携）」に分けて見積もります。代表的な算出方法は 2 つあります。

- **テストケース数ベース**: 設計書の分岐やインターフェース数から想定テストケース数を出し、1 日あたりの消化件数で割る。消化件数の例は次のとおり（テストケースの粒度で大きく変わる）
  - テスト設計: 15〜20 件/日
  - テスト実施: 20〜30 件/日
- **工数比率ベース**: 開発（製造＋単体テスト）工数の 30〜40% を結合テストに充てる。外部システムとの連携が多い場合は 50% 近くまで引き上げる。この基準は「製造＋単体テスト」であって、セクション 1 の表の「全体」ではない点に注意する

さらに、テスト実施とは別に、見つかった不具合の調査・修正・再テスト、および修正が他機能に影響していないかを確かめるリグレッションテストの工数として、結合テスト（設計＋実施）の 20〜30% をバッファとして組み込んでおきます。

### 受け入れテスト（UAT）の工数見積もり

受け入れテストは原則として利用者が主体となって実施します。そのため見積もりは、誰の工数かで 2 つに分かれます。

1. **利用者のテスト実施工数（発注側）**: 業務シナリオ（ユースケース）の本数をもとに見積もる。「通常業務の 1 サイクルを回すのに何日かかるか × パターン数（正常系と代表的な異常系）」で算出する
2. **開発側の受け入れテスト支援工数（受注側）**: 次の作業を見積もる。計上方法の例としては、UAT 期間中に SE を 0.5〜1.0 人月張り付けるといった稼働率の形がある
   - QA 対応（仕様の問い合わせ対応）
   - テスト環境・データの準備
   - 見つかった不具合の改修

### 計算例

ここまでの目安を使って、架空のシステムで試算してみます（数字は説明用です）。ここでの「開発フェーズ」は製造＋単体テストだけで、詳細設計は含みません。

#### 製造・単体テスト

| 項目 | 本数 | 標準工数 | 工数 |
| --- | --- | --- | --- |
| 簡易画面 | 5 本 | 1.5 人日 | 7.5 人日 |
| 標準画面 | 10 本 | 4 人日 | 40 人日 |
| 複雑画面 | 3 本 | 8 人日 | 24 人日 |
| 製造 小計 | | | 71.5 人日 |
| 単体テスト（製造の 40%） | | | 約 28.6 人日 |
| **開発フェーズ 合計** | | | **約 100 人日** |

#### 結合テスト（テストケース数ベース）

想定テストケースを 300 件とすると、次のようになります。

- テスト設計: 300 件 ÷ 18 件/日 ≒ 17 人日
- テスト実施: 300 件 ÷ 25 件/日 ＝ 12 人日
- 小計 29 人日に、不具合修正バッファ（25%）を加えて ≒ 36 人日

工数比率ベースで出すと、開発フェーズ 100 人日の 30〜40% で 30〜40 人日です。どちらも経験則の目安なので、両者が近いことは正しさの証明にはなりません。それでも、2 つの方法が大きく食い違う場合は、次の点を見直すきっかけになります。

- テストケースの見積もり漏れ
- 画面の難易度の判定

#### 受け入れテスト支援

UAT 期間 1 か月に SE を 0.5 人月張り付けるとすると、約 10 人日です。

#### 合計

開発フェーズ 100 人日 ＋ 結合テスト 36 人日 ＋ 受け入れテスト支援 10 人日 ＝ 約 146 人日です（詳細設計と総合テストは別途）。

## 3. 見積もりの落とし穴を先に織り込む

標準的な手法に加えて、赤字や遅延を防ぐために見積もり段階で考慮しておきたい要素が 3 つあります。

### テストデータ作成と環境構築

結合テストや受け入れテストでは、本番に近い大量データや特殊な条件のデータを作るのに多くの時間がかかります。テスト実施工数に含めてしまうと見えなくなるため、「環境準備・データ作成」を独立したタスクとして切り出して見積もるのが基本です。

### 外部連携の調整コスト

他社や他部署のシステムなど、自分たちでコントロールできない相手との結合テストでは、相手側のスケジュール待ちや仕様の認識の食い違いがほぼ確実に発生します。経験則として、純粋な作業工数に 1.2〜1.5 倍程度の係数を掛けておくとよいでしょう。

### 受け入れテストでの「仕様変更」の切り分け

UAT で利用者から挙がる指摘には、「不具合」と「仕様変更（追加要望）」が混在します。見積もりの時点で「設計書どおりの動作に対する不具合修正のみを含む」と前提条件（スコープ）を明記しておかないと、追加要望の対応まで見積もりの範囲内として扱われてしまいます。

## まとめ

- 設計後の工数見積もりは、**工程別比率によるトップダウン**と、**設計書からのボトムアップ**を組み合わせ、互いに突き合わせる
- 開発フェーズは「本数 × 難易度別の標準工数」に単体テスト（製造の 30〜50%）を上乗せする
- 結合テストはテストケース数ベースと工数比率ベースの両方で出し、不具合修正バッファ（20〜30%）を忘れずに加える
- 受け入れテストは発注側の実施工数と受注側の支援工数を分けて考える
- テストデータ・環境構築、外部連携の調整、仕様変更の切り分けは、見積もりの段階で明示的に織り込む
- ここで挙げた数値はあくまで出発点。自組織の実績比率を記録しておくことが、次の見積もり精度を上げる近道になる
