## はじめに

Claude Code に頼めば、サーバを用意しなくても、HTML 1 ファイルで動く社内ツールを作って配れます。このやり方が X で話題になっています。発端は次の投稿です。

> Claude CodeでHTMLアプリを作って社内に配布するというのに慣れると、もはやサーバとかサーバレスにアプリをデプロイするという思想がなくなる。いかに単一HTMLファイルに機能を集約してモノリスにできるかの勝負になって、マイクロサービスという考え方ではなくなる。要らなくなったら捨てるのみ。
>
> — [@nasuvit_z](https://x.com/nasuvit_z/status/2121510581471707145)

これを引用した中小企業診断士の方の投稿では、中小企業との相性の良さが指摘されています。

> ベンダーに見積もりを取って、サーバを契約して、保守費を払い続ける。あの「システム導入の大げささ」が、ファイル1個で消えるかもしれない。
>
> （中略）
>
> CSVの整形や入力チェックみたいな、データを抱えない小さな道具は、捨てる前提で作るくらいがちょうどいい。
>
> 道具は軽く。残すのは仕事のほうです。
>
> — [@minorcoworker](https://x.com/minorcoworker/status/2121814636551098678)

本記事では、この「単一 HTML ファイルで配る」アプローチがなぜ成り立つのか、どんな道具に向いていて何に向かないのか、Claude Code で作るときに何を指示すればよいのかを整理します。最後に、API サーバがある構成へどう応用できるかも考えます。

## 用語の整理

| 用語 | この記事での意味 |
|---|---|
| 単一 HTML アプリ | HTML・CSS・JavaScript を 1 つの `.html` ファイルにまとめ、ブラウザで開くだけで動く道具 |
| 配布 | 共有ドライブ・チャット・メール添付などでファイルそのものを渡すこと。サーバへのデプロイは伴わない |
| データを抱えない道具 | 入力を受け取って変換・検査し、結果を返すだけで、データを保存し続けない道具 |
| CDN | ライブラリなどをインターネット経由で配信する仕組み。HTML から `<script src="https://...">` で読み込む |
| BOM | ファイルの先頭に付ける目印。Excel が CSV を UTF-8 だと判別するのに使う |
| `file://` | 共有ドライブやデスクトップの HTML をダブルクリックで開いたときの URL の形。Web サーバから配信されたページ（`https://`）とは扱いが異なる |
| SPA | Single Page Application。React などで作る、ブラウザ側で画面を組み立てる Web アプリ。データは API サーバから取得する |
| アトミックな API | 1 回の呼び出しで 1 つの操作を完結させ、途中で失敗したら何も変えない API |
| 不変条件 | どんな操作の後でも成り立っていなければならない業務上の条件（承認済みの申請は編集できない、在庫はマイナスにならない、など） |

## なぜ単一 HTML なのか

### 「システム導入」に必要だったものが要らなくなる

社内向けの小さな道具でも、Web アプリとして作るなら従来は次のものが必要でした。

- 実行環境（サーバ、サーバレス基盤、コンテナ）
- ドメイン・証明書・認証
- デプロイの仕組みと、それを保守する担当者
- 月々のインフラ費用と保守契約

単一 HTML アプリでは、実行環境は**利用者のブラウザ**です。インストールもデプロイも不要で、ファイルをダブルクリックすれば動きます。サーバが無いので、止まる心配も、パッチを当て続ける必要もありません。

### 作るコストが下がったので「捨てる前提」が成り立つ

この方式自体は昔からありましたが、HTML・CSS・JavaScript を 1 ファイルに書き切るのは、非エンジニアには敷居が高い作業でした。Claude Code のようなコーディングエージェントに「1 ファイルで完結させて」と頼めば、その部分を任せられます。

作り直すコストが下がると、道具に対する考え方が変わります。

- 仕様が変わったら、直すより**作り直す**ほうが速いことがある
- 使われなくなったら**ファイルを消すだけ**で廃止が終わる
- 部署ごとに少しずつ違う版があっても、サーバ側の整合性を気にしなくてよい（ただし、どれが最新版かは分かりにくくなります。後述の「版の管理」を参照）

元の投稿が、マイクロサービスではなくモノリスだと言っているのは、この性質を指しています。分割して組み合わせるのではなく、**1 つの用途に 1 つのファイル**を割り当てます。用途が終われば捨てる、という単位の取り方です。

## 単一 HTML アプリに向く道具・向かない道具

判断の軸は「**データを抱えるかどうか**」と「**複数人で状態を共有するかどうか**」です。

| 観点 | 向いている | 向かない |
|---|---|---|
| データの扱い | 入力 → 変換 → 出力で完結する | データを蓄積・検索し続ける |
| 利用者の関係 | 各自が手元で使う | 複数人が同じデータを同時に更新する |
| 外部連携 | 不要、またはファイルの読み書きだけ | 社内 DB や外部 API を毎回叩く |
| 秘密情報 | 持たない | API キーや DB のパスワードを埋め込む必要がある |

**向いている例**

- CSV の列の並べ替え・文字コード変換・全角半角の統一
- 入力値のチェック（郵便番号・電話番号・法人番号の桁数など）
- 見積もりや按分の計算シート
- 定型文やメール文面の組み立て
- JSON・YAML の整形や差分表示

**向かない例**

- 顧客台帳や在庫管理のように、他の資料の基準になる元データを持つもの
- 承認フローのように、複数人の操作の順序に意味があるもの
- 外部サービスの API キーが必要なもの（HTML に書いた時点で、ファイルを受け取った全員に見えます）

ただし、これらは「単一 HTML だけでは向かない」という意味です。バックエンドを足せば、「フロントは作り直せる・捨てられる」という考え方のまま、扱える業務を広げられます（後述の「API がある構成への応用」を参照）。

## Claude Code に単一 HTML アプリを作らせるプロンプト例

単一 HTML アプリを作らせるときは、最初に制約をはっきり伝えるのがコツです。たとえば次のように指示します。

```text
CSV を読み込んで、指定した列だけを残し、文字コードを UTF-8（BOM 付き）にして
ダウンロードできる道具を作ってください。

制約:
- 1 つの index.html で完結させる（CSS と JavaScript もインラインで書く）
- 外部の CDN やライブラリを読み込まない。ネットワークが無くても動くこと
- データはブラウザの外に送らない。サーバへの通信を一切しない
- ファイルの読み込みは <input type="file"> とドラッグ＆ドロップで行う
- 入力の CSV は UTF-8 と Shift_JIS の両方がありうる
- 結果はファイルとしてダウンロードさせる
- 画面の文言は日本語
```

「外部 CDN を使わない」は重要です。CDN からライブラリを読み込む作りにすると、社外のネットワークに出られない端末では動きません。また、CDN 側の変更の影響も受けます。どうしてもライブラリが必要なら、ファイルの中に埋め込ませます。

「社内の CSV は Shift_JIS が多い」といった事情も、最初の指示に書いておくとやり直しが減ります。

## 最小構成の例: CSV 列抽出ツール（HTML + JavaScript）

上の指示から生成される道具の骨格を、説明用に簡略化すると次のくらいの分量です（入力は UTF-8 のみ対応）。

```html
<!doctype html>
<html lang="ja">
<head>
  <meta charset="utf-8">
  <title>CSV 列抽出ツール</title>
  <style>
    body { font-family: sans-serif; max-width: 40rem; margin: 2rem auto; }
    #drop { border: 2px dashed #888; padding: 2rem; text-align: center; }
  </style>
</head>
<body>
  <h1>CSV 列抽出ツール</h1>
  <div id="drop">ここに CSV をドロップ、または <input type="file" id="file" accept=".csv"></div>
  <p>残す列（カンマ区切りの列名）: <input id="cols" placeholder="氏名,メール"></p>
  <button id="run" disabled>変換してダウンロード</button>

  <script>
    let rows = [];

    // 簡易パーサ（ダブルクォート内のカンマ・改行に対応）
    function parseCSV(text) {
      const out = []; let row = []; let cell = ""; let q = false;
      for (let i = 0; i < text.length; i++) {
        const c = text[i];
        if (q) {
          if (c === '"' && text[i + 1] === '"') { cell += '"'; i++; }
          else if (c === '"') q = false;
          else cell += c;
        } else if (c === '"') q = true;
        else if (c === ",") { row.push(cell); cell = ""; }
        else if (c === "\n") { row.push(cell.replace(/\r$/, "")); out.push(row); row = []; cell = ""; }
        else cell += c;
      }
      if (cell || row.length) { row.push(cell); out.push(row); }
      return out;
    }

    const toCSV = (rs) => rs.map(r => r.map(v => /[",\r\n]/.test(v) ? `"${v.replace(/"/g, '""')}"` : v).join(",")).join("\r\n");

    async function load(file) {
      rows = parseCSV(await file.text());
      document.getElementById("run").disabled = rows.length === 0;
    }

    document.getElementById("file").addEventListener("change", e => load(e.target.files[0]));
    const drop = document.getElementById("drop");
    drop.addEventListener("dragover", e => e.preventDefault());
    drop.addEventListener("drop", e => { e.preventDefault(); load(e.dataTransfer.files[0]); });

    document.getElementById("run").addEventListener("click", () => {
      const want = document.getElementById("cols").value.split(",").map(s => s.trim()).filter(Boolean);
      const idx = want.map(name => rows[0].indexOf(name)).filter(i => i >= 0);
      if (idx.length === 0) { alert("指定した列名が見つかりません"); return; }
      const result = rows.map(r => idx.map(i => r[i] ?? ""));
      // 先頭に BOM を付けて、Excel で開いても文字化けしないようにする
      const blob = new Blob(["\uFEFF" + toCSV(result)], { type: "text/csv;charset=utf-8" });
      const url = URL.createObjectURL(blob);
      const a = document.createElement("a");
      a.href = url;
      a.download = "extracted.csv";
      a.click();
      // クリック直後に解放するとダウンロードに失敗するブラウザがあるので、少し待つ
      setTimeout(() => URL.revokeObjectURL(url), 1000);
    });
  </script>
</body>
</html>
```

ポイントは 3 つです。

- **読み込み**は `<input type="file">` とドラッグ＆ドロップ。`File.text()` で中身を読むので、ファイルはブラウザの外に出ません
- **書き出し**は `Blob` を作ってダウンロードリンクをクリックさせるだけ。サーバは要りません
- **外部依存はゼロ**。ファイル 1 つをコピーすれば、どの PC でも同じように動きます

なお、この例の `File.text()` は常に UTF-8 として読みます。Shift_JIS の CSV を扱うなら、`await file.arrayBuffer()` で読んだ中身を `new TextDecoder("shift_jis").decode(...)` で文字列にします。

## 社内配布するときの注意点

サーバが無いぶん、気を付けるところはサーバ側からファイル側に移ります。

### 版の管理

ファイルがコピーされて広がるので、どれが最新か分からなくなりがちです。

- 画面の隅に**版数と更新日**を表示させる
- 置き場所を 1 か所（共有ドライブの特定フォルダなど）に決め、そこから開いてもらう
- ソースは Git で管理する（作り直すときに、Claude Code に前の版を読ませられる）

### file:// で開いたときの制約（fetch・localStorage）

ダブルクリックで開いた HTML は `file://` のページになり、Web サーバから配信されたページとは扱いが異なります。

- `fetch()` で同じフォルダの別ファイルを読む処理は、現行の主要ブラウザではほぼ失敗します
- `localStorage` に設定を保存する処理も、ブラウザによって挙動が一定しません

**必要なものはすべてファイル内に入れ、データは利用者に毎回選んでもらう**作りにしておくのが無難です。

### 「野良ツール」にしないために

手軽に作れるぶん、誰が作ったか分からない道具が増えるリスクもあります。作者が異動して誰も直せない Excel マクロが社内に残る、という問題と同じです。

- 作成者・問い合わせ先・用途をファイル内（画面かコメント）に書いておく
- 業務の元データを扱う用途には使わない、という線を引いておく
- 社内で配る前に、ブラウザの開発者ツールの［ネットワーク］タブを開いたまま操作し、外部への通信が 1 件も出ないことを確かめる

## API がある構成への応用 — 業務ロジックはできるだけフロントに

ここからは、単一 HTML の外側の話です。

複数人でデータを共有するなら、サーバは必要です。では、API サーバ + React などの SPA という構成になったら、この考え方は捨てるしかないのでしょうか。そうではありません。前半で見た「作り直せるから捨てられる」という性質は、業務ルールを正本（基準となる唯一の原本）として扱うことで、API がある構成にも持ち込めます。形としては、**業務ロジックはできるだけフロントエンド（以下、フロント）で実装する**ということです。

### 正本はコードではなく業務ルール

Claude Code のようなエージェントでソフトウェアを作るとき、業務ロジックは、エージェントに渡す業務ルールそのものです。業務ルールを正本にし、コードはそこから生成するものと考えれば、用途ごとにフロントがいくつあっても困りません。どれも同じルールから生成した成果物にすぎず、要らなくなれば捨てて、必要になれば作り直せます。後で述べるバックエンドの検査も、同じ業務ルールから導きます。

業務ロジックをフロントに置くと、画面ごとに実装が散らばって保守できなくなる。そんな心配が出るのは、コードを正本とみなしているからです。ルールが正本なら、直す対象はルールで、実装は作り直せばよいので、この心配は小さくなります。残るのは「作り直したものが正しいか」の確認で、これは後の「正しさは境界条件とテストで決める」で扱います。

### バックエンドは権限と不変条件を守るアトミックな API にする

ブラウザで動くコードは、利用者が開発者ツールで書き換えられます。そのため、共有データを守る役目はバックエンドに残します。ここで大事なのは、バックエンドを**アトミックな API の集まり**として小さく保つことです。

各 API は、呼び出しのたびに次の 2 つを自分で検査します。

- **権限**: この人がこの操作をしてよいか
- **状態に対する前提条件（不変条件）**: いまこのデータに対して、この操作をしてよいか（承認済みは編集不可、在庫を超えて引き当てない、など）

権限だけでは足りません。正当な利用者でも、API を想定外の順番で呼べば不変条件を壊せるからです。どの順番で呼ばれても壊れない API にしておけば、API の組み合わせ方、つまり業務フローはフロントに任せられます。

| 置き場所 | 持つもの |
|---|---|
| バックエンド（アトミックな API） | 権限、不変条件、整合性。どの順番で呼ばれても壊れないこと |
| フロントエンド | 業務フロー、API の組み合わせ方、画面ごとの業務ロジック |

この分担は、業務ルールが変わったときにも効きます。ルールが変われば、どのみちソフトウェアの改修は必要です。それでも、用途ごとに作ったフロントのうち更新し忘れたものが新しい API を呼んだ場合、API が検査している不変条件に反する操作は拒否されます。

ただし、拒否されるのは API が検査している範囲だけです。たとえば古いフロントが変更前の単価で計算した金額を送ってきても、API が金額の妥当性を検査していなければ、そのまま通ってしまいます。単価や税率のように結果を左右するルールは、API 側でも検査する（または API 側で計算する）不変条件に含めておく必要があります。

反対に、バックエンドを持たない単一 HTML アプリでは、拒否してくれる相手がいません。税率や単価のようなルールをファイルの中に持っていると、古いコピーは古い計算をし続けます。前述の「版の管理」が欠かせないのはこのためです。

### 正しさは境界条件とテストで決める

LLM は、同じルールからでも生成のたびに少しずつ違う実装を出します。しかし、これは人間が書く場合も同じです。A さんと B さんが同じ仕様から書いたコードは違うものになりますが、どちらも正しく動く必要があります。

つまり、実装が違っても正しく動くように、**境界条件とテストを業務設計の段階で決めておく**ことが必要です。これは LLM 特有の問題ではなく、業務設計の責任です。

違いがあるとすれば頻度です。フロントを使い捨てにすると作り直す回数が増えるので、テストは「たまに回すもの」から「作り直すたびに必ず通すもの」になります。テストが実質的な契約になる、ということです。

### 単一 HTML アプリとの関係

整理すると、単一 HTML アプリは、この構成からバックエンドを取り除いた特殊な場合にあたります。

| 構成 | バックエンド | フロントエンド |
|---|---|---|
| 単一 HTML アプリ | なし（共有データを持たない） | 業務ロジックのすべて |
| API + SPA | 権限と不変条件を守るアトミックな API | 業務フローと画面ごとの業務ロジック |

どちらも、業務ルールを正本にし、フロントはそこから生成して捨てられるようにする、という点で同じ考え方です。

## まとめ

- 単一 HTML アプリは、実行環境を利用者のブラウザに任せることで、サーバ・デプロイ・保守費をまとめて不要にする
- Claude Code で作り直すコストが下がったことで、「直して使い続ける」より「作り直す・捨てる」が現実的な選択肢になった
- 向いているのは、データを抱えず、各自が手元で使い、秘密情報を持たない小さな道具
- 作らせるときは「1 ファイルで完結」「外部 CDN 禁止」「通信しない」を最初に伝える
- `file://` で開く前提で、必要なものはすべてファイル内に入れる
- 配るときは版数の表示・置き場所の一本化・作成者の明記で、野良ツール化を防ぐ
- 共有データが要るなら、バックエンドは権限と不変条件を守るアトミックな API に絞り、業務ロジックはできるだけフロントに置く
- フロントの正しさは、業務ルールの境界条件とテストで決める

引用した投稿の言葉を借りれば、「道具は軽く。残すのは仕事のほう」です。システムを導入するかどうかを迷う前に、まずファイル 1 個で済まないかを考えてみる価値はありそうです。
