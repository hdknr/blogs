## AIに「作らせる」だけでは足りない時代

AIコーディングツール（Claude Code、Codex、Cursor など）を使う際、多くの開発者がこんなプロンプトで止まってしまっている。

```text
「作って」
「修正して」
「いい感じにして」
```

これで機能は動く。しかし、後から「なぜそうなったのか」が一切わからない。

Claude Code Studio（@ClaudeCode_love）が紹介した、Anthropic 社員が使っていると伝えられるプロンプトは、その問題に真正面から切り込んでいる。

## Anthropic 社員が使うプロンプト

元ツイート（2026-05-19）では「自分がいちばん使っているプロンプト」として次の指示が紹介されている。

```text
仕様書通りに実装して。
その途中で、仕様書に書かれてなかった判断・変更・妥協点・意思決定を、
全部 implementation-notes に残して
```

英語で書くなら次のようになる。

```text
Implement according to the specification.
Along the way, record all judgments, changes, trade-offs, and decisions
that were not in the specification into implementation-notes.
```

一見地味に見えるが、これはAIコーディングの本質を突いたプロンプトだ。

## なぜ implementation-notes が必要なのか

仕様書には「何を作るか」しか書かれていない。しかし実装の過程では、仕様書が想定しなかった数多くの判断が生まれる。

- 仕様に曖昧な部分があったので A ではなく B を選んだ
- ライブラリ X のバージョン制約で回避策が必要だった
- パフォーマンスとシンプルさのトレードオフで後者を選んだ
- エラーハンドリングの粒度について仕様に記載がなかったので推測した

AI は黙ってコードを書く。その際に下した判断は、コードの中には残らない。コメントにも残らない。`git log` にも残らない。**これらの判断はすべて、黙って消える。**

`implementation-notes` の指示を加えることで、AI はこれらの判断を明文化して記録に残す。

## 意思決定ログがあると何が変わるか

### あとから修正しやすくなる

「なぜこの実装になったのか」がわかれば、変更のリスクも見積もれる。理由のわからないコードを変えるのは怖い。理由が書いてあるコードは変えやすい。

### 次の AI に引き継ぎやすくなる

Claude Code を使って実装を継続する際、前のセッションで何を決めたかを新しいセッション開始時に渡せる（コンテキスト引き継ぎ）。引き継ぎの精度が上がるため、会話が切れても設計方針がブレにくい。

### 仕様と実装のズレに気づける

AI が「仕様にはこう書いてあったが、実際にはこうしました」と書いてくれると、設計上の問題が表面化する。

### 人間がレビューしやすくなる

コードレビューは「このコードが正しいか」だけでなく「この判断が正しいか」を確認する行為でもある。判断が記録されていればレビューの質が上がる。

## 実践：Claude Code での使い方

Claude Code で実際に使う場合、`implementation-notes` を残す場所はいくつか考えられる。

### CLAUDE.md に残す

```markdown
## 実装メモ

### 2026-05-20: 認証フローの設計
- JWT の有効期限を 1 時間にした（仕様には記載なし）
  → 理由: セキュリティとUXのバランス。リフレッシュトークンで補完
- ミドルウェアを共通化しなかった
  → 理由: 現状は認証ルートが2つのみ。DRY より読みやすさを優先
```

### 専用ファイルに残す

たとえば以下のパスに専用ファイルを用意して、AI に常にそこへ追記させる運用も有効だ。

```text
docs/implementation-notes.md
```

### コミットメッセージに埋め込む

```bash
git commit -m "feat: JWT認証を実装

implementation-notes:
- 有効期限1時間（仕様外の判断）
- アルゴリズムはHS256を選択（RS256への移行は将来タスク）
"
```

## プロンプトテンプレートとして使う

このプロンプトは汎用的に使えるテンプレートとして整理できる。

```markdown
## タスク
[ここに何を実装するかを書く]

## 仕様書 / 要件
[ここに仕様や要件を書く]

## 指示
上記の仕様に従って実装してください。
実装中に発生した以下の内容をすべて `implementation-notes` セクションとして出力の末尾に追記してください：
- 仕様に記載のなかった判断
- 複数の選択肢から選んだ場合の理由
- 妥協した点とその背景
- 将来的に変更が必要になりそうな箇所
```

## コードを書かせる時代から「記憶も残させる」時代へ

AI がコードを書くのは当たり前になった。次のステージは、**AI に実装の記憶を残させること**だ。

コードは動く証拠だが、判断は残らない。`implementation-notes` はその判断を言語化して記録する仕組みだ。

「いちばん使っているプロンプト」として紹介されるほど日常的に使われているとすれば、それが開発の持続可能性に直結するからではないか。
