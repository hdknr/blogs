これまでの 4 本では、レイクハウスの仕組みと周辺の技術を見てきました。最後に、「AI エージェントに社内のデータを分析させる基盤を作るなら、何から考えるか」という実践的な問いに答えます。

結論を先に書くと、**データはオープンな形式で S3 などに置く（レイクハウス）を土台にするのが堅い方向**です。ただし、レイクハウスだけではエージェントは安全にも賢くも動きません。その上に「意味・費用・権限・取り消し」の 4 つの守りを足す必要があります。

## なぜレイクハウスが土台に向くのか

### エージェントが使う道具を選べる

エージェントは、問いに応じて道具を使い分けます。ちょっとした集計なら DuckDB、大量のデータなら Athena や Spark、定型のダッシュボードなら Redshift、といった具合です。データがオープンな形式で 1 か所にあれば、どの道具からも同じデータを読めます。将来エージェントの得意な道具が変わっても、データを移す必要はありません。

### 技術の入れ替わりに強い

4 本目で見たとおり、レイクハウスの周辺はカタログもフォーマットもまだ動いています。それでもデータファイルは共通の Parquet で、XTable のようにフォーマット間でメタデータを変換する仕組みもあります。個々の製品を選び直しても、データそのものは残せます。

### 書き込みを取り消せる

エージェントに書き込みを任せると、誤った更新は必ず起きます。Iceberg はスナップショットで過去の状態を持っているので、間違えても元に戻せます。分析を同じ時点のデータで再現できるのも、エージェントの出した数字を検証するうえで大事です。

## 4 つの守り

![AI エージェントのためのデータ基盤の構成と、4 つの守りを示した図。上から順に、AI エージェント、窓口（MCP サーバーとセマンティックレイヤーによる指標の定義）、計算エンジン（DuckDB・Athena・Redshift）、カタログ（Glue Data Catalog・S3 Tables・Iceberg REST カタログ）、S3 上の Iceberg テーブル（Parquet、スナップショット、ブランチ）が重なっている。各層の右に守りが対応している。窓口には「① 意味：列や指標の定義を渡し、LLM に計算させない」、計算エンジンには「② 費用：スキャン量や RPU に上限を設ける」、カタログには「③ 権限：読めるテーブルを絞り、既定は読み取り専用にする」、Iceberg テーブルには「④ 取り消し：書き込みはブランチで検証し、失敗はスナップショットで戻す」](/blogs/images/ai-agent-data-platform-guardrails.png)

### ① 意味：エージェントに定義を渡し、計算させない

エージェントがよく間違えるのは、SQL の文法よりも「この列は何を意味するか」「売上はどう定義するか」です。たとえば「売上」が税込か税抜か、返品を引くかどうかを知らなければ、正しい SQL でも誤った数字を返します。

対策は、指標の定義を**セマンティックレイヤー**としてエージェントの外に持つことです。

- **指標を定義しておく**：dbt Semantic Layer のような仕組みで「売上」「アクティブユーザー数」などを定義しておき、エージェントには指標の名前と集計の軸だけを選ばせます。[dbt の MCP サーバー](https://github.com/dbt-labs/dbt-mcp)には、定義済みの指標を一覧する `list_metrics` や、指標を集計する `query_metrics` といったツールがあります。
- **LLM に算術をさせない**：集計はデータベース側で実行し、LLM には条件の指定だけを任せます。[デジタル庁の行政手続 MCP サーバーに学ぶ「LLM に計算させない」データ設計](/blogs/posts/2026/08/digital-agency-mcp-ai-ready-data/)で見た考え方です（Wiki の [AI-ready データ設計](/blogs/wiki/concepts/ai-ready-data/)にもまとめています）。

### ② 費用：エージェントのクエリに上限を設ける

エージェントは人よりはるかに多くのクエリを投げます。試行錯誤のたびに大きなテーブルを全件スキャンすれば、費用はすぐに膨らみます。エンジンの側で上限を設けておきましょう。

- **Athena**：ワークグループごとに、[クエリ 1 本あたりのスキャン量の上限](https://docs.aws.amazon.com/athena/latest/ug/workgroups-setting-control-limits-cloudwatch.html)を設定できます。上限を超えたクエリはキャンセルされます。ワークグループ全体の 1 時間・1 日あたりのスキャン量にもしきい値を設けられますが、こちらはキャンセルではなく SNS への通知です。
- **Redshift Serverless**：ワークグループごとに、[自動で増える RPU の最大値](https://docs.aws.amazon.com/redshift/latest/mgmt/serverless-capacity.html)と、[1 日・1 週・1 か月あたりの RPU 時間の上限](https://docs.aws.amazon.com/redshift/latest/mgmt/serverless-workgroup-max-rpu.html)を設定できます。上限に達したときに、ログを残す、通知する、クエリを止める、から動作を選べます。

エージェント専用のワークグループを作って上限を設定しておけば、人の分析と費用を分けて管理できます。テーブルをパーティションで区切ったり、よく使う集計を事前に作っておいたりして、そもそものスキャン量を減らすことも大切です。

### ③ 権限：読めるテーブルを絞り、既定は読み取り専用に

エージェントに渡す権限は、人に渡す権限より狭くするのが基本です。

- **カタログで絞る**：4 本目で見たように、カタログはテーブル単位の権限管理の中心になりつつあります。エージェント用のロールには、必要なテーブルだけを読める権限を与えます。
- **既定は読み取り専用**：たとえば AWS Labs の [Amazon Redshift MCP サーバー](https://awslabs.github.io/mcp/servers/redshift-mcp-server)は、クエリを読み取り専用モードで実行し、書き込みを拒否します。それでも、ドキュメントはデータベースのユーザーに最小権限の読み取り専用ロールを与えることを勧めています。MCP サーバー側の制限だけに頼らず、データベースやカタログの権限でも二重に守るのが安全です。

### ④ 取り消し：書き込みはブランチで検証してから反映する

エージェントに書き込みまで任せるなら、Iceberg の**ブランチ**が役立ちます。ブランチはテーブルのスナップショットに名前を付けた参照で、本番（`main`）とは別の場所に書き込めます。

[Iceberg のドキュメント](https://iceberg.apache.org/docs/latest/branching/)にある WAP（Write-Audit-Publish：書き込み → 検証 → 公開）の流れは、Spark では次のようになります。

```sql
-- テーブルで WAP を有効にする
ALTER TABLE db.table SET TBLPROPERTIES ('write.wap.enabled'='true');

-- 検証用のブランチを作る（7 日間保持）
ALTER TABLE db.table CREATE BRANCH `audit-branch` AS OF VERSION 3 RETAIN 7 DAYS;

-- 以降の書き込みをブランチに向ける
SET spark.wap.branch = audit-branch;
INSERT INTO prod.db.table VALUES (3, 'c');

-- 検証が済んだら main をブランチの先頭まで進める
CALL catalog_name.system.fast_forward('prod.db.table', 'main', 'audit-branch');
```

エージェントはブランチにだけ書き込み、件数や値の範囲のチェックに通ったものだけを本番に反映します。チェックに通らなければ、ブランチを捨てれば済みます。万一本番に誤った書き込みが入っても、スナップショットで過去の状態に戻せます。

## 段階的に始める

最初から全部をそろえる必要はありません。規模に合わせて段階的に進めるのが現実的です。

| 段階 | 構成 | 守りの重点 |
|---|---|---|
| 試行 | DuckDB（＋ DuckLake）を手元で使い、エージェントに読ませる | 意味（列の説明を渡す） |
| チームでの利用 | S3 ＋ Iceberg（S3 Tables など）に置き、Athena や DuckDB から読む | 費用（Athena の上限）、権限（読み取り専用のロール） |
| 業務への組み込み | セマンティックレイヤーを用意し、定型の集計は Redshift にも持つ | 意味（指標の定義）、取り消し（ブランチでの検証） |

どの段階でも、データはオープンな形式で持っておきます。そうすれば、次の段階に進むときにデータを作り直さずに済みます。

## まとめ

- AI エージェントのためのデータ基盤は、データをオープンな形式で S3 などに置くレイクハウスを土台にするのが堅い方向です。道具を選べて、技術の入れ替わりに強く、書き込みを取り消せます。
- ただしレイクハウスだけでは足りず、次の 4 つの守りを足します。
  - **意味**：セマンティックレイヤーで指標を定義し、LLM には条件の指定だけを任せる
  - **費用**：Athena のスキャン量や Redshift Serverless の RPU に上限を設ける
  - **権限**：カタログで読めるテーブルを絞り、既定は読み取り専用にする
  - **取り消し**：Iceberg のブランチで検証してから反映し、失敗はスナップショットで戻す
- 個々の製品は差し替えられるように選び、規模に合わせて段階的に進めます。
