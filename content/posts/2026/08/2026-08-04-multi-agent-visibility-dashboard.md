## TL;DR

- X で「Codex の『見えないAI組織』が全部丸見えになるダッシュボードが鳥肌立った」という投稿が話題になっていた。エージェントを並列で何体走らせても、誰が何をしていて、どこで止まっているかが分かるという内容だ。
- ただし元投稿には**具体的な製品名やリンクは含まれていない**。中身は「こういう管理画面が必要だ」という一般論であり、特定ツールの機能検証はできない。
- 一方でこの「並列エージェントが増えると誰が何をしているか分からなくなる」という悩み自体は、実際によくある問題である。
- Claude Code にはこの問題に対応する仕組みが**すでに存在する**。タスクの一覧管理、ワークフローの進捗ツリー表示、バックグラウンド処理のイベントストリーム監視、名前で呼び戻せるエージェント――4つの機能に分けて整理する。
- 「AIを使う」から「AI組織を監督する」への移行は誇張ではなく、**観測できる単位を用意すること**という具体的な設計問題に落とし込める。

## 元投稿について

きっかけは [@ai_300](https://x.com/ai_300) が 2026 年 8 月 4 日に X に投稿した以下の内容だ。

> Codexの「見えないAI組織」が全部丸見えになる。誰が動いてる。何をしてる。どこで止まってる。SkillsもPluginもTaskも、進捗まで全部見える。エージェントを10体並列で走らせても迷子にならない。

投稿は動画付きで、内容としては「AIエージェントで一番キツいのは指示を出すことではなく、何をしているか分からなくなること」という課題提起と、それを解決する「ダッシュボード」の存在を紹介する構成になっている。

ただしこの投稿には、ダッシュボードの製品名・提供元・リンクが一切含まれていない。動画のサムネイルと文章だけで具体的な検証対象がないため、**この記事では「特定製品の機能紹介」としては扱わない**。代わりに、投稿が指摘している「並列マルチエージェントは何をしているか分からなくなる」という課題そのものを掘り下げる。

この課題は、実際に複数エージェントを並列運用してみると誰もが一度は経験する。

## なぜ並列エージェントは「迷子」になるのか

1 体のエージェントに 1 つの仕事を頼んでいる間は、進捗はチャット欄を読めば分かる。ところが並列数が増えると事情が変わる。

- **どのエージェントが何を担当しているか**が一覧できない。指示を出した瞬間にコンテキストから消える
- **どこまで終わったか**を確認するために、各エージェントのチャット欄を1つずつ遡る必要がある
- **止まっているのか、単に時間がかかっているのか**を区別できない
- 完了したエージェントの結果を**後から呼び出して追加の指示を出す**手段がない

これは元投稿が言う「AIに仕事を投げて眺めるだけ」がなぜ成立しないかの説明にもなっている。眺める対象――つまり**観測可能な単位**――が最初から用意されていないと、並列数を増やすほど管理コストが増える。

## Claude Code に実在する4つの仕組み

「見えないAI組織を可視化する」という要件は、実は目新しいものではない。Claude Code は次の4つの機能でこの問題に対応している。いずれも筆者が実際にこのブログの執筆・PR作成フローで使っている、検証済みの機能だ。

### 1. タスク管理 — 誰が何を担当しているかの一覧

`TodoWrite` ツールで複数の作業項目を明示的に登録し、進行中・完了のステータスで管理できる。バックグラウンドで走らせたシェルコマンドやサブエージェントの方は `/tasks` コマンドで一覧でき、個別のタスクには `TaskOutput` で出力を取りに行き、`TaskStop` で止められる。並列で複数の作業を進めるとき、チャット履歴を遡らなくても「今何が残っているか」を一覧で確認できる。

### 2. 進捗ツリー — ワークフローの今どこにいるか

複数のサブエージェントを `pipeline()` や `parallel()` で組んだワークフローを実行すると、フェーズ（`phase()` で名付けた作業のまとまり）ごとに進捗がツリー表示される。`/workflows` コマンドで実行中のワークフローをライブで確認できるため、「今どのフェーズか」「どのエージェントがまだ動いているか」が一目で分かる。

```js
export const meta = {
  name: 'review-changes',
  description: '変更を複数の観点でレビューし、指摘を検証する',
  phases: [{ title: 'Review' }, { title: 'Verify' }],
}

phase('Review')
const findings = await parallel(
  ['bugs', 'perf', 'security'].map(topic => () =>
    agent(`${topic} の観点でレビューして`, { phase: 'Review' }))
)

phase('Verify')
// Review フェーズが終わった時点で、進捗ツリー上では
// Review が完了・Verify が実行中として表示される
```

（これは Claude Code のワークフロー定義ファイルの一部を示す例で、単体では実行できない。）

### 3. イベントストリーム — 止まっているか動いているかの区別

バックグラウンドで実行しているエージェントやコマンドに対して、`Monitor` ツールで出力をリアルタイムに追跡できる。ポーリングでステータスを聞き直す必要がなく、標準出力の1行ごとに通知が来る仕組みのため、「進んでいるが遅い」のか「本当に止まっている」のかを区別しやすい。

### 4. 名前付きアドレス — 完了後も呼び戻せる

`Agent` ツールでサブエージェントを起動する際に `name` を指定すると、そのエージェントは名前で識別できる状態になる。完了後に `SendMessage` で名前を指定して追加の指示を送れば、同じエージェントを文脈を保ったまま再開できる。「並列で走らせたうちの1体だけに後から確認を入れる」という、まさに元投稿が課題としていた操作に対応する。

## 「AIを使う」から「AI組織を監督する」までの距離

元投稿は次のように整理していた。

> 「AIを使う」→「AIを複数動かす」→「AI組織を監督する」

この移行に必要なのは、より賢いモデルではない。**観測できる単位が用意されているかどうか**である。

- タスクという単位がなければ、何が終わったかを追えない
- フェーズという単位がなければ、今どこにいるかを追えない
- イベントという単位がなければ、動いているか止まっているかを判定できない
- 名前という単位がなければ、後から特定の1体だけに介入できない

これらはどれも「AIエージェントの性能」の話ではなく、**運用側が用意するべき最小限のインターフェース設計**の話である。並列数を増やす前に、この4つの単位が揃っているかを確認する方が、ダッシュボードそのものの見た目より重要になる。

## まとめ

「Codex の見えないAI組織が丸見えになる」という投稿は、具体的な製品検証はできないものの、指摘している課題自体は実務でよく遭遇するものだった。エージェントを並列で走らせるほど、「誰が・何を・どこまで」を追う仕組みが先に要る。

Claude Code の場合、この要件はタスク管理・進捗ツリー・イベントストリーム・名前付きアドレスという4つの既存機能に分解できる。**「AIを複数動かす」段階に入ったら、まずこの4つの単位が揃っているかを確認する**——それが「監督する」ための最初の一歩になる。
