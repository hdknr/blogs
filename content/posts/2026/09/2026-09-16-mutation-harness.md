テストが全部緑だった。だからといって、そのコードについて何かが分かったわけではない。

この記事は、わざとコードを壊してテストが落ちるかを確かめる仕掛け（**mutation harness**）の話である。専用ツールは使わない。30 行の Python スクリプトを手で書いて回した実例、そこで踏んだ 6 つの罠、同じ発想を共有する周辺の技法、そして**この検査を AI コーディングエージェントに任せるときの指示の書き方**までをまとめた。コード例は Python と pytest だが、発想は言語を問わない。

## 発端

あるレビューで、こういう指摘を受けた。

> このガード、`if False:` に書き換えても全テストが緑のままです。

ガードは実在した。コメントも付いていた。レビューでも「妥当な防御」に見えた。
しかし**誰も守っていなかった**。到達不能な分岐だったのだ。

テストは 20 件すべて緑だった。緑であることは、そのガードについて**何も語っていなかった**。

これが mutation harness を回す動機のすべてである。

## 概要 — 何をする道具か

**mutation harness** とは、**わざとコードを壊して、テストが落ちるかを確かめる仕掛け**のこと。

- コードを 1 箇所だけ変異させる（mutant を作る）
- テストを回す
- **落ちなければ**、その変異は「生き残った（survived）」= テストに**検出力がない**
- 必ず元に戻す

学術的には **mutation testing**（ミューテーション（mutation）テスト）と呼ばれる古い技法である
（DeMillo, Lipton, Sayward, 1978）。ただし専用ツール（`mutmut` / `cosmic-ray` / `Stryker` / PIT）は要らない。
**手書きの 30 行のスクリプトで十分な価値が出る。** というより、手で狙いを定めたほうが、
自動生成された数千の mutant を眺めるより速く核心に届くことが多い。

### なぜ必要か — カバレッジは検出力ではない

行カバレッジ 100% のテストは、assert が 1 つもなくても達成できる。

```python
def test_it_works():
    do_everything()      # 全行を通る。何も検査していない
```

カバレッジが測るのは「**実行されたか**」であって「**検査されたか**」ではない。
この差を埋める唯一の実用的な方法が**変異を当てること**である。

**否定的な主張ほど危ない。** 「変わらない」「起きない」「呼ばれない」という結論は、
**実験が壊れていても同じ形で出る**。テストが空振りしていても、対象が存在しなくても、
早期 return で到達していなくても、出力は同じ「緑」だ。

## 使い方 — 最小の実装

やることは 3 つしかない。

1. 対象ファイルの元の内容を保存する
2. 変異を当てる → テストを回す → RED / GREEN を記録する
3. 必ず元に戻す（`finally` / `trap` で。ここを落とすと作業ツリーが壊れる）

図にすると、2 を「変異」「テスト」「記録」に割った 5 段のループになる。
右側は判定の読み方、下は最後に残す成果物である。

![mutation harness の 1 周を示した図。左列は保存・変異を当てる・テストを回す・判定を記録・必ず復元という 5 段のループで、復元から変異へ戻る矢印が付いている。右上は判定の読み方で、RED はテストに検出力がある、GREEN は本当の穴・等価変異・死んだコードの 3 つに切り分けると示す。右下はリポジトリに残す結果の表の例で、3 つの変異それぞれに RED または GREEN と対処が並んでいる](/blogs/images/mutation-harness-loop.png)

Python なら 30 行で書ける。`MUTATIONS` のアンカー文字列は、対象ファイルの実際の中身に合わせて書き換える。

```python
import pathlib
import subprocess

TARGET = pathlib.Path("src/prune.py")
TESTS  = "tests/test_prune.py"

MUTATIONS = [
    # (説明, 置換前, 置換後)
    ("dry-run ガードを外す", 'if not apply_it:\n        return 0\n', ""),
    ("排他生成を上書き生成に戻す", 'open(path, "x")', 'open(path, "w")'),
    ("型ガードを消す", 'if not isinstance(data, list):\n        raise SystemExit(...)\n', ""),
]

original = TARGET.read_text()
try:
    for title, old, new in MUTATIONS:
        if old not in original:
            print(f"{title}: !! アンカーが見つからない（表が腐っている）")
            continue
        TARGET.write_text(original.replace(old, new, 1))
        r = subprocess.run(["pytest", TESTS, "-q"], capture_output=True, text=True)
        # FAILED 行は "FAILED tests/test_prune.py::test_name - AssertionError: ..." の形。
        # 失敗理由まで付いてくるので、テスト名だけを取り出す
        failed = [line.split("::")[-1].split(" ")[0]
                  for line in r.stdout.splitlines() if line.startswith("FAILED")]
        print(f"{title}: {'RED' if failed else 'GREEN'}  {failed}")
        TARGET.write_text(original)          # 各変異のあとで戻す
finally:
    TARGET.write_text(original)              # 例外・中断でも必ず戻す
    print("restored")
```

出力はこうなる。GREEN が並んだ行が、次に調べるところである。

```text
dry-run ガードを外す: RED  ['test_dry_run_writes_nothing']
排他生成を上書き生成に戻す: GREEN  []
型ガードを消す: GREEN  []
restored
```

Bash なら `trap 'cp "$BACKUP" "$TARGET"' EXIT` が同じ役割を果たす。

### 結果の読み方

| 結果 | 意味 | すること |
|---|---|---|
| **RED** | テストがその変異を検出した | その検査には検出力がある。表に記録する |
| **GREEN** | 検出できなかった | **3 つに切り分ける**（下記） |

GREEN が出たら、次のどれなのかを**必ず判定する**。混ぜると次の人が誤読する。

1. **本当の穴** — 検査を足す
2. **等価変異（equivalent mutant）** — 意味が変わっていない。例: 正常系で到達しない
   `except` 節の中身を変えた。より強い変異と重ねて RED になることで示せる
3. **到達不能な死んだコード** — そのガードは**削る**。効かない防御は次に読む人を誤解させる

3 番目が一番よく出る。そして一番価値がある。

### どこに置くか

**リポジトリに入れない。** mutation harness は使い捨ての計測器であって、成果物ではない。
リポジトリに残すのは**結果の表**（どの変異がどのテストを落としたか）だけでよい。

置きっぱなしにすると、本体の変更に追随せずアンカーが腐り、
「昔は動いていたが今は何も当たっていないスクリプト」になる。

## 実例 — 実際に何が見つかったか

ある PR（本番 DB の 1 行を書き換える運用スクリプトとその検証）で、
**変異を当てて**見つかったものを挙げる。**すべて、テストが緑のまま潜んでいた**。

### 到達不能な死んだガード

```python
if class_names(after) != EXPECTED_AFTER and not args.force:
    return 2
```

`--force` が無い経路では、直前のチェックで `EXPECTED_BEFORE` が保証されている。
だから `after` は決定的に `EXPECTED_AFTER` になる。`--force` がある経路では
`not args.force` が偽。**どちらからも到達しない。**

`if False:` に書き換えても全テスト緑。→ `and not args.force` を外して、
本当に検査したい場面（`--force` のとき）で効くようにした。

### テストが 1 件も無い防御

```python
if not isinstance(data, list):
    raise SystemExit(...)     # 消しても緑だった
```

docstring には「壊れていたら例外を投げる（黙って空にしない）」と書いてあった。
**書いてあるだけだった。**

### 消しても緑な「足場」

検証用に mock を 9 個、フィクスチャを 1 セット足していた。
**全部消しても緑だった。** 原因は広すぎる `except`:

```python
try:
    do_it()
    outcome[name] = None
except SpecificError as e:
    outcome[name] = str(e)
except Exception:
    outcome[name] = None      # ← 「成功」と「別の理由で落ちた」が同じ値に潰れる
```

ここまで潰れると、その先の assert は何も区別しない。足場は**足さずに削る**のが正解だった。

## 罠 — 踏んだ 6 つ

6 つとも実際に踏んだ。共通しているのは、**どれも出力は正常に出る**ことだ。
壊れた計測器は、壊れた顔をしていない。

![踏んだ罠 6 つを 3 列に分類した図。左列は変異の作り方を間違える系で、assert を消すのは変異ではない、汚い変異で関数ごと壊す、の 2 件。中央列は測定の再現性が崩れる系で、基準に動く参照を使う、失敗件数を表に書く、時計に依存する検査、の 3 件。右列は主張を実測より強く書く系で「網羅した」と先に書く 1 件と、6 つとも出力は正常に出るため結果を見ても気づけないという注記](/blogs/images/mutation-harness-traps.png)

### 罠 1: assert を消すのは変異ではない

```diff
# これは「変異」ではない。今通っている assert を消せば、必ず緑になる
- self.assertGreater(sentinel.reads, 0)
+ pass
```

検出力を測りたいなら、**機構のほう**を壊す。

```diff
# 正しい変異: 番兵が読み取りを数えないようにする
  def __get__(self, obj, objtype=None):
-     self.reads += 1
      raise AssertionError(...)
```

### 罠 2: 基準に「動く参照」を使うと黙って無効になる

```bash
# NG: 長い作業の途中で基準そのものが動く
git show origin/master:src/foo.py

# OK: 固定 SHA
git show 397bd5774:src/foo.py
```

比較対象のブランチが作業中にマージされ、「何も変えない変異」に化けたことがある。
**出力は正常に出るので「測った」感覚だけが残る。** 固定 SHA を指すこと。

### 罠 3: 汚い変異は、別のものを測ってしまう

```diff
  def restore(...):
-     before = write_backup(...)          # この 1 行だけ消した
      print(f"退避: {before}")            # → NameError
```

RED にはなった。しかし**ガードを外したのではなく関数を壊していた**。
測りたかったものを測っていない。**変異は意味の単位で当てる。**

### 罠 4: 失敗件数はテストスイートの性質ではない

同じ趣旨の変異でも、テキストが違えば巻き込む範囲が変わる。
2 人が別々に当てたら、3 つの変異それぞれで落ちたテストの件数が
`2 / 9 / 3` と `1 / 10 / 1` に食い違った。どちらも正しい。

→ 表に書くのは件数ではなく、**どのテストが落ちたか**。

### 罠 5: 「網羅した」と書く前に、分岐を数え上げる

これを 3 回続けて外した。1 回目は対象ファイルの分岐を 1 つも当てていなかった。
2 回目は「今度は両方覆った」と書いてまだ 2 つ残っていた。3 回目も 6 つ残っていた。

**主張の強さを、実際に検証したことに合わせる。** 「全部当てた」は、
分岐を列挙した表を作ってからでないと書けない。

### 罠 6: 時計に依存する検査は、検出力が揺れる

```python
stamp = now().strftime("%Y%m%d_%H%M%S")   # 秒解像度
```

「同じ秒に 2 回走ると上書きされる」バグを、2 回の実行が秒境界をまたぐと**見逃す**。
変異が RED になったのは運かもしれない。時刻を固定するか、衝突を強制する。

## 似たような考え方

mutation harness は孤立した技法ではない。「**その観測は、主張が偽のときに違う結果を出すか**」
という一つの問いの、いろいろな現れ方がある。

### ポジティブコントロール / ネガティブコントロール（実験科学）

生物学や化学で最初に習うこと。「検出されなかった」と言う前に、
**検出できるはずの対象を入れて、実際に検出されること**を見る。

ソフトウェアでの対応物:

```python
# 「0 件でした」の前に、1 件出ることを見る
self.assertEqual(24, len(found_for_known_input))   # ポジティブコントロール
self.assertEqual(0,  len(found_for_target))        # 本命
```

**「0 件」を合格の証拠にしない。** 対象が空でも 0 件、クエリが壊れていても 0 件、
そもそも到達していなくても 0 件になる。
逆にネガティブコントロールは、**検出されないはずの対象を入れて、実際に 0 件になること**を見る。
ポジティブだけだと「何を入れても検出する」計測器を見逃す。

### 反証可能性（Popper）

「この主張が偽なら、何が観測されるはずか」を先に決める。
決められないなら、その実験は主張を支持していない。

GREEN を見たとき「検出力がない」と読むか「バグがない」と読むかは、
**先に決めておかないと後付けで都合よく決まる。**

### 交絡（confounding）の排除

「変わらなかった」という結果が、**主張が正しいから**なのか、
**実験の設定がそうさせたから**なのかを切り分ける。

実際に踏んだ例: ある属性が「読まれない」ことを番兵（読むと落ちるデスクリプタ）で
示したが、**そのクラスにはその属性を触るコードが 1 行も無かった**。
番兵が効いていようがいまいが `reads == 0` になる。**結果が他の形では出ようがない**実験は、
証拠ではない。
このときポジティブコントロールは*別の属性*に当てていた。
だから「番兵という機構は動く」ことは示せても、
「この実験が読み取りを検出しえた」ことは示せない。

この落とし穴の実例は [AI エージェントにリファクタさせるときの「完了の定義」の引き方](/blogs/posts/2026/07/ai-refactor-completion-boundary/) でも扱っている。

### TDD の RED を先に見る

新しいテストを書いたら、**まず落ちることを確認してから**実装する。
これは「1 個の変異（= 実装が無い状態）を当てている」のと同じこと。
後からテストを足したときに省略されやすい手順で、省略すると検出力ゼロのテストが量産される。

### フォールトインジェクション / カオスエンジニアリング

対象がコードではなくインフラになっただけで、発想は同じ。
「落ちても大丈夫なはず」を**実際に落として確かめる**。
Netflix の Chaos Monkey が有名だが、粒度が違うだけで問いは変わらない。
pytest に障害注入を組み込む具体例は
[pytest.mark.chaos で始めるカオスエンジニアリング](/blogs/posts/2026/04/pytest-chaos-engineering/) に書いた。

### Property-based testing（Hypothesis / QuickCheck）

mutation が「**実装**を揺らして**テスト**の感度を測る」のに対し、
property-based testing は「**入力**を揺らして**実装**の穴を探す」。
方向は逆だが、どちらも「例示 1 個で満足しない」という同じ不満から来ている。
**併用すると強い** — 不変条件を property で書き、その property の検出力を mutation で測る。

### メタモルフィックテスティング

期待値が書けない対象（機械学習の推論、複雑な数値計算）で、
「入力をこう変えたら出力はこう変わるはず」という**関係**を検査する。
「変えたら変わること」を見るという点で、mutation と発想を共有している。

### コードレビューにおける「削ってみる」

レビューで一番効く質問は、しばしば
**「この行、消したら何が壊れますか？」である**。
答えられないなら、その行は誰にも守られていない。

## AI に検査させるときの指示の書き方

「この行、消したら何が壊れますか？」は、AI コーディングエージェントに投げる問いとしても効く。
ただし**投げ方を間違えると、ここまで書いてきた失敗がそのまま再現する**。

「適切なテストをして」と指示しても効かない。
エージェントは「妥当な検査に見えるもの」を選んで緑を報告できる。
**その報告は、検査が効いていなくても同じ形で出る。**
人間が空振りのテストを書くのと、構造はまったく同じである。

指示すべきは手法名ではない。**手法の選び方の規則**と、**止まってよい条件**の 2 つである。

### 検査は「コードの形」ではなく「主張の形」で選ばせる

レビューで出てくる指摘は、必ず何かを主張している。その主張の形が、効く検査をほぼ一意に決める。
表にして渡すのが一番速い。

| 指摘の主張の形 | 効く検査 |
|---|---|
| 「このガード / 検査は効いている」 | **mutation** — その行を壊して RED になるか |
| 「〜は起きない」「呼ばれない」「0 件」 | **ポジティブコントロール** — 起きるケースを先に入れ、検出できることを見る |
| 「この入力範囲で正しい」 | **property-based** — 不変条件を書いて入力を揺らす |
| 期待値が書けない（推論・数値計算・描画） | **メタモルフィック** — 入力を変えたとき出力がどう変わるはずかを検査 |
| 「落ちても復旧する」「timeout しても安全」 | **フォールトインジェクション** — 実際に落とす |
| 「既存の挙動を変えていない」（リファクタ） | **固定 SHA との比較（罠 2）+ 特性テスト** — 現在の出力をそのまま期待値に固定する |
| 「性能は劣化していない」 | **ベースライン付きベンチ** — 固定シード・相対値。絶対秒数を根拠にしない |

肝は表そのものより、**まず指摘の主張を 1 行で書き出させる**ことにある。
そこを飛ばすと、主張ではなくコードの見た目から検査を選んでしまう。

### 止まってよい条件を、反証可能な形で渡す

表だけ渡しても形骸化する。次の 1 文を添える。

> **その検査は、主張が偽のときに違う結果を出すか。** 出ないなら、それは証拠ではない。

これは反証可能性の節で書いたことの言い換えにすぎないが、**指示に書いていないと実行されない**。

### 書き手と検査役を分ける

一番効くのは、指示の中身より**配置**である。
プロジェクト共通の設定ファイルに書くと常時読まれるが、**書いた本人が自分で検査する形になる**。
経験上、同じモデルは同じ思い込みを持つらしく、
**書き手が確信を持って間違えた箇所は、検査役にも正しく見える**。

だから専用のサブエージェントに分け、**使うモデルも実装側と変える**。
エージェントを分ければ見ている文脈がずれ、モデルを変えれば間違え方がずれる、という見立てである。
片方だけでは足りない。

この記事自体、書いたモデルとファクトチェックしたモデルを変えて通している。

### 検証エージェントに mutation をやらせると詰まる

ここが実際に詰まったところである。検証エージェントには、普通こういう不変条件を置く。

> リポジトリの追跡対象ファイルを変更しない。終わったときに `git status` が検証開始時と同じであること。

1 文目は行為そのものの禁止、2 文目は終わった時点の条件である。**どちらを取るかで読みが割れる。**
そして **mutation は対象ファイルを一時的に書き換えないと成立しない**。
制約を素直に読んだ検査役は、これを違反と判断して、コードを読むだけの静的なレビューに引き下がる。

**その報告は「反証なし」と見分けがつかない。**
罠 1（今通っている assert を消せば必ず緑になる）とまったく同じ形である。
そしてこれは交絡そのものでもある。報告が緑なのは対象が正しいからではなく、
**検査役が制約に縛られたから**かもしれない。

明示的に例外を書いておくこと。

```markdown
- **mutation のための一時的な書き換えは許される。** ただし復元を `finally` /
  `trap ... EXIT` に置き、報告の末尾に `git status --short` の出力を貼ること。
  復元できなかった場合は、隠さず申告する。
```

`git status` の出力を要求するのは、**復元したという主張にも証拠を付けさせる**ためである。
ここを自己申告で済ませると、検査役の報告だけが緑になる。

### 「当てたか」ではなく「届いたか」を検査させる

最後は、一番外しやすいところである。

「mutation を当てたか」を検査させると、**当てた事実だけ確認して通る**。
必要なのは「当てた変異が、検査したい分岐に届いているか」である。
罠 3（汚い変異）と罠 5（数え上げる前に「網羅した」と書く）が、そのままここに出る。

対処も同じで、**分岐を列挙した表を先に作らせ、どれに当てたかを埋めさせる**。
列挙していない状態で「網羅した」とは書けない。
これは人間に対する規律と、1 文字も変わらない。

## まとめ

- **カバレッジは「実行されたか」、mutation は「検査されたか」を測る。**
- 専用ツールは要らない。**30 行のスクリプト**と、意味の単位で選んだ数個の変異で足りる。
- **GREEN が出たら 3 つに切り分ける**: 本当の穴 / 等価変異 / 死んだコード。
  死んだコードは足すのではなく**削る**。
- **否定的な結果ほど疑う。** 「変わらない」「起きない」は、実験が壊れていても同じ形で出る。
- **主張の強さを、実際に検証したことに合わせる。**
  「全部当てた」は、分岐を列挙してからでないと書けない。
- **AI に検証させるときは、手法名ではなく「主張の形 → 検査」の対応と停止条件を渡す。**
  書き手と検査役は分け、**復元したという主張にも `git status` という証拠を出させる。**

まずは直近の PR から分岐を 1 つ選び、`if False:` に書き換えてテストを回すところから始めればいい。
エージェントに任せるのは、自分で 1 周回してからでいい。

最後にもう一度。

> テストが緑であることは、そのコードについて何も語っていない。
> **何かを語らせたければ、壊してみるしかない。**
