## 概要

**Lean**（[lean-lang.org](https://lean-lang.org/)）は定理証明支援系であり、関数型プログラミング言語でもある。定義を書いてそのまま実行（`#eval`）でき、同じ定義について「すべての入力で成り立つ」性質を証明できる。この 2 つを 1 つの言語で持つため、**仕様の正本を Lean で書き、可読ドキュメントとテストオラクルをそこから生成する**という使い方が提案されている（mizchi さんの投稿を t_wada さんが「仕様駆動開発は自然言語駆動開発ではない」と引用して話題になった）。

[形式手法](/blogs/wiki/concepts/formal-methods/)の道具の中では「無限の範囲での定理」を担当し、アルゴリズムや計算ルールの正しさを示すのに向く。並行・分散の状態の組み合わせを網羅的に調べるなら [TLA+](/blogs/wiki/tools/tla-plus/) や [Quint](/blogs/wiki/tools/quint/) のモデル検査のほうが手軽である。

## 詳細

### 自然言語を正本にした SDD の弱点

Markdown の仕様書を正本にした[仕様駆動開発](/blogs/wiki/concepts/spec-driven-development/)は手軽だが、次の弱点を抱える。

- **意味が一意に決まらない**：「1 万円以上の会員は 10% 割引」は、1 万円ちょうどを含むか、税込か、端数の扱いが文章から決まらない
- **矛盾を機械で見つけられない**：別の章の「割引は最大 500 円」と衝突するかを確かめる手段がない
- **LLM の解釈が揺れる**：セッションやモデルが変わると補い方が変わり、実装も変わる
- **ずれを判定できない**：仕様から機械的にテストを導けず、「仕様どおりか」はレビューする人の読みに頼る

実態は「LLM がその文章をどう読んだか」で駆動されており、これが「自然言語駆動開発」と呼ばれる状態である。

### 形式仕様を正本にした流れ

| | 自然言語が正本 | 形式仕様が正本 |
|---|---|---|
| 正本 | Markdown の仕様書 | Lean などの形式仕様 |
| 人が読む文書 | 正本そのもの | 正本から生成した出力 |
| テスト | 人や LLM が仕様書を読んで書く | 正本から生成する |
| LLM の役割 | 仕様書を解釈して実装する | 自然言語と形式モデルの翻訳役 |
| 食い違ったとき | どちらが正しいか決まらない | 形式仕様が勝つ |

**書くのは LLM、確かめるのは検査器**という分担である。人間は自然言語で要求を伝え、LLM が Lean に落とし、検査器が通るまで LLM が直す。人間が見るのは検査を通った仕様から生成された説明と具体例だけでよい。仕様の追加や問い合わせも LLM が形式モデルを経由して読み書きする。

### 小さな例

```lean
def discount (total : Nat) (isMember : Bool) : Nat :=
  if isMember && total ≥ 10000 then total / 10 else 0

theorem discount_le_total (t : Nat) (m : Bool) : discount t m ≤ t := by
  unfold discount
  split <;> omega
```

`total ≥ 10000` で境界を含むこと、`Nat` の割り算で切り捨てることが一意に決まり、「割引額は合計を超えない」はすべての入力について証明される。新しい要求が既存の性質と衝突すれば、証明が通らないという形で表に出る。

### テストオラクルの生成

`#eval discount 10000 true`（→ 1000）のように定義を評価した値を JSON などに書き出し、スクリプトで実装言語のテストを組み立てる。

- **例ベースのテスト**：評価値をそのまま期待値にする。境界値（9999 と 10000）を必ず含める。生成物なので手で編集しない
- **性質テスト**：Lean で証明した定理を、実装側では Hypothesis などのプロパティベーステストで確かめる

仕様が変われば Lean を直し、テストを再生成し、落ちたテストを実装で直す、という一方向の流れになる。仕様の保守を人の注意力ではなく**テストの再生成という仕組み**で担保できるので、SDD の Spec-as-Source の一形態と見なせる。

### 注意点

- **検証と妥当性確認は別**：検査器が保証するのは「書かれた仕様が内部で整合し、宣言した性質を満たす」ことまで。「本当は税込で判定したかった」のような意図とのずれは、生成した可読ドキュメントと具体例を利用者が読んで見つけるしかない。これがこの方式の安全弁になる
- **何でも形式化できるわけではない**：向くのは料金計算・権限判定・状態遷移など入出力と性質がはっきりした部分。画面の見た目や文言は形式化しても得るものが少ない。まずは**間違えると損害が大きいドメインの中核**から始める

### モデル検査と比べた弱点（spec-loop が Lean を使わない理由）

[要求仕様書作成ループ](/blogs/wiki/concepts/requirements-spec-loop/)（hdknr 版 spec-loop）は形式手法を使うが Lean は使わず、Z3・TLC・Alloy を使う。設計から読み取れる理由は 4 つ。

| 観点 | Lean を正本にする方式 | spec-loop |
|---|---|---|
| 正本を持つ人 | 開発者（利用者は生成物を読む） | 利用者（Q&A 表・決定表を直接合意する） |
| 形式モデルの位置づけ | 正本 | 正本から作るレビューの証拠 |
| 判定の出方 | 証明が通る／通らない | 有限の範囲で反例を自動で探す |
| 対象 | アルゴリズム・計算の正しさ（無限の範囲） | 決定表・状態遷移・権限（有限の組み合わせ） |

証明が通らないとき、仕様が誤っているのか証明が書けないだけなのかを区別しにくい。また spec-loop の[陽性対照](/blogs/wiki/concepts/positive-control/)（壊したモデルで反例が出ることを確かめる）は、モデル検査ならそのまま反例が出るが、Lean では「通らない」ことしか示せない。反例探しには [Plausible](https://github.com/leanprover-community/plausible) のような別の道具が要り、それも有限の範囲を網羅するものではない。反例は「この組み合わせはどう扱いますか」という利用者への質問に直しやすいので、利用者が仕様を持つ業務システムではモデル検査が合う。
