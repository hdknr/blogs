## 概要

mezura は Petros Papatheodorou 氏が開発する Rust 製のコード行数カウンタ（`tokei` や `scc` と同じジャンル）。Linux カーネル v6.15（約 3,600 万行・約 6 万 3,700 ファイル・1.37GB）を、Ryzen 7 9700X・ページキャッシュが温まった状態で **67ms** で数える。

| ツール | Linux (ext4) | Windows (NTFS) |
|---|---|---|
| mezura 3.5.0 | 67ms | 175ms |
| scc 4.1.0 | 208ms | 521ms |
| tokei 15.0.0 | 411ms | 617ms |

数値はいずれも作者の計測（機能を揃えた equal-work モード、30 回平均）。ツールそのものより、約 0.4 秒→166ms→88ms→67ms と縮めた過程の記録が、性能最適化の教訓として価値が高い。

## 詳細

### 最適化の教訓

**1. 先に「ハードウェアの床」を測る**

フレームグラフで目立つ箇所を潰し終えると「もう限界」に見えるが、それは今の設計の局所最適にすぎないことが多い。作者は libc と intrinsics だけの C プログラムで、メモリ帯域→ファイル I/O→走査＋読み込み→SIMD＋状態機械と段階的に床を測り、約 41ms と特定した。88ms の時点で半分以上がまだ自分のコードの取り分だと分かり、さらに進めた。個別コストは足し算にならない（スレッドがコアや VFS を取り合う）点にも注意。

**2. プロファイラの数字は逆を指すことがある**

- フレームグラフで 2〜5% を占める処理を消しても壁時計時間は変わらなかった（アウトオブオーダー実行で他と重なっていた）。効いたのは関数呼び出しを丸ごと消す変更
- 分岐レス（SWAR）化で分岐予測ミスは 14% 減ったが、命令数が 16% 増えて 12% 遅くなった
- フェーズタイマーで遅く見えた走査スレッドは、実は消費者スレッドにプリエンプトされていただけ。経過時間は CPU コストではない
- スリープ中のスレッド（`sched_yield` など）は CPU フレームグラフに出ない。work stealing は同じ物理コア上のスピンで逆効果になり、消費者数を減らし盗むタイミングを限定して初めて効いた
- `unsafe` は壁時計時間で明確に効くときだけ許可。命令数が 7% 減っても IPC 低下でサイクルが増えた変更は却下

**3. ファイル I/O は OS と設定で別物**

- Linux：Rust 標準の「サイズ問い合わせ＋2 回 read」をやめ、64KiB バッファに 1 回 read（95.7% のファイルはこれで完結）、大きいファイルだけ `fstat` / `mmap`。直近更新のファイルは `SIGBUS` 回避のため read に戻す
- Windows：CPU 時間の半分以上がカーネル内。D ドライブだけ 36% 遅かった原因は、保存先設定の変更で差し込まれたミニフィルタドライバ（wcifs、FileCrypt）。`fltmc instances` で発見し `fltmc detach` で解消（再起動で再アタッチされる）
- Defender のプロセス除外はファイル名で一致するため、A/B 比較用にバイナリ名を変えたコピーは 24〜32% 遅くなった

**4. SIMD とビット演算で行をまとめて処理する**

64 バイトブロックごとに AVX2 / NEON で改行と区切り候補のビットマスクを作り、候補のない「普通の行」（カーネルの 87.6%）はスキャン自体を省く。さらに加算の繰り上がりを使って行を「単語を含む行／記号だけの行／空行」に `count_ones()` だけで一括分類する。既定の x86-64 ターゲットでは `popcnt` が無効なので、`#[target_feature]` で CPU 世代別にホットループをコンパイルし実行時に選ぶ。

**5. 速くしたら正確にもなった**

区切りの重なりを 330 行のインデックス計算で解決していた旧パーサを、状態遷移テーブル駆動の単一レキサ（左から右へ 1 カーソル）に置き換え、命令数 21% 減と同時に重なりのバグを構造的に消した。参照レキサと突き合わせる小さなファザーが、実在の 37 万 8,000 ファイルで見つからなかった `/* x /*/` のバグを数分で見つけている。ただし正確さはタダではなく、正規表現リテラルなどの修正で命令数は 2.3% 増えた。

### 言語定義と正確さの担保

- 80 以上の言語を 1 つのエンジンで処理。言語ごとの定義（コメント、文字列、エスケープ、ネスト、正規表現の文脈、補間）はプレーンテキストの設定ファイルで、初回使用時に遷移テーブルにコンパイルされる。Python・TypeScript・TSX も対応（TSX は TypeScript と同一定義ではない）
- Python の docstring は複数行文字列として扱われ、コメントではなくコード行として数えられる
- 適合性テストスイート **LineJudge**（v0.4.0 で 107 ケース）を CI で毎回実行。「正しい行数」ではなく文字列とコメントのバイト範囲を定め、各カウンタの宣言に照らして検査する

### コーディングエージェントからの利用

別バイナリの MCP サーバー `mezura-mcp`（`cargo install mezura-mcp`）が `count_lines_of_code`、`count_lines_of_code_as_json`、`explain_file` を提供する。

- エージェントの待ち時間はモデル推論が大半なので、速さの差はほぼ体感されない。価値は**推測ではない決定的な数値**
- 用途：知らないリポジトリの規模とテスト比率の把握、git リビジョン間の差分の観測（`--diff`、`--tests-breakdown split`）
- MCP にするとツール定義が毎回コンテキストに乗る。頻度が低いなら CLI を Bash から呼ぶので十分
- 行数は書き方で増減するため、見積りの根拠や受入基準の証明には使えない。dev-loop や [要求仕様書作成ループ](/blogs/wiki/concepts/requirements-spec-loop/) では判定ではなく**補助の観測値**として使うのが筋（dev-loop なら `.claude/dev-loop.md` に数行追記する）
