## 概要

外部 API のレートリミット（429）や過負荷（529）に対して、**再試行の間隔を指数的に伸ばす（指数バックオフ）**と、**失敗が続いたら呼び出し自体を遮断する（サーキットブレーカー）**を組み合わせる制御パターン。自律エージェントのように無人で大量の API 呼び出しを行うシステムでは、これがないと「翌朝には全部止まっていた」という事故が起きる。

## 3段構えの実装

### 1. 検知

まず「何がレートリミットなのか」を正しく拾う。エラーが「その他のエラー」に落ちていると、再試行制御が一切効かない。

CLI 経由で LLM を呼ぶ場合、**API のエラー本文が stderr ではなく stdout に出る**ことがある点に注意が必要。stderr だけ監視していると診断情報が消える。

観測される主なパターン:

- `429` — `rate_limit_error`（毎分のトークン／リクエスト上限）
- `529` — `overloaded_error`（サービス側の過負荷）
- usage limit — プラン上限に達したケース

### 2. 指数バックオフ

再試行間隔を指数的に伸ばす。サーバーが `retry-after` を返す場合は**それを尊重する**のが原則。

重要なのは**上限を決めること**で、たとえば「300 秒を超える待ちは待たずに degrade する」といった判断を入れる。無限に待つ設計は、無人運用では実質的な停止と変わらない。

### 3. サーキットブレーカー

失敗が閾値を超えたら回路を「開く」（呼び出しを遮断する）。一定時間後に「半開 (half-open)」にして試行を 1 件だけ通し、成功すれば「閉じる」（通常復帰）。

## ハマりどころ

### 半開スロットのリークによる永久ロック

半開状態で試行枠（スロット）を取得したまま解放し損ねると、**回路が永久に閉じない**バグになる。試行枠の獲得と解放を確実に対にすること。例外パスでの解放漏れが典型的な原因。

### 制御機能は「壊れる」より「効かない」で失敗する

サーキットブレーカーのような制御系は、例外を投げて派手に壊れるのではなく、**静かに何もしなくなる**形で失敗する。したがってテストの観点が通常のロジックと異なる。

- **配線テスト** — そもそも検知関数が呼ばれる経路につながっているか
- **発動率の計器** — バックオフやブレーカーが実際に何回発動したかを記録し、常時観測する
- **ミューテーション** — 制御コードをわざと壊してテストが落ちることを確認する（落ちないなら、そのテストは何も検証していない）

## 適用文脈

毎朝数十回 CLI を叩く自律トレーディングシステムのような、**無人・定期実行・外部 API 依存**の構成で特に効く。人間が張り付いていないため、失敗の検知と自動復帰がそのまま可用性になる。
