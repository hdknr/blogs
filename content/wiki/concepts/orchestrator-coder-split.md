## 概要

1 体のエージェントに計画から実装まで全部やらせると、スコープが膨張し、巨大な diff が出て、レビュー不能になる。これを防ぐために **「計画するAI（オーケストレーター）」と「書くAI（コーダー）」を分業させ、間に承認ゲートを置く**設計パターン。OSS スキル `codex-build` がこの分業を Claude Code のスキルとして実装している。

## 2つの役割

| 役割 | 担当 | 実装例 |
|---|---|---|
| **オーケストレーター** | 計画を読みタスクに分解、出力をレビュー、ゲートを判定する「指揮者」 | Claude Code など Skills を扱えるハーネス |
| **コーダー** | 実装だけを担当する「手」 | OpenAI Codex CLI（`codex` コマンド） |

> Orchestrator drives, Codex codes（オーケストレーターが運転し、Codex がコードを書く）

## 設計の核心：コーダーに全体像を渡さない

最も重要なのは、**コーダーには「今回いじってよいファイル」と「1 タスク分のブリーフ」しか渡さない**点である。全体像や意思決定はオーケストレーターが握り、コーダーは目の前の 1 タスクだけを閉じた範囲で書く。

これにより、コーダーが「ついでにあそこも直しておこう」と判断する余地が構造的に消える。スコープ膨張は指示の問題ではなく**渡す情報の範囲の問題**である、という発想の転換になっている。

## 3種類の承認ゲート

タスクごとにゲートを通し、失敗したら停止する。

1. **スコープゲート** — 変更が許可されたファイル範囲に収まっているか
2. **テストゲート** — 当該タスクに関係するテストが通るか
3. **フルスイートゲート** — 全体のテストが通るか

コミットごとにゲートを通し、最後に **PR を 1 本だけ出す**。

## 持ち帰れる設計原則

この手法は特定ツール（`codex-build` / Codex CLI）に依存しない。以下は自分の `CLAUDE.md` にも移植できる。

- 計画の承認と実装の実行を**別のフェーズに分ける**
- 実装役に渡す情報を**タスク単位で絞る**
- ゲートは**通過ではなく停止**をデフォルトにする（失敗したら進めない）
- 1 タスク = 1 コミット、1 プラン = 1 PR に対応させる
