## 概要

デザイントークンは、色・余白・タイポグラフィ・角丸などのデザイン要素を、ツールやプラットフォームに依存しない JSON で表す仕組み。W3C の Design Tokens Community Group（DTCG）が仕様を策定しており、2025 年 10 月に初の安定版（2025.10）が出た。

AI エージェントに UI を作らせるときの価値は、`#0066CC` のような生の値ではなく `semantic.color.action.primary` のような**役割の名前**と、`$description` に書いた**使ってよい場面・いけない場面**を値と同じ場所に置けること。エージェントは行間を読むのが苦手なので、意図と値を直結させておくと「もっともらしいがズレた」出力が減る。

一方で、ルールとトークンで品質のすべてを担保できるわけではない。デザインの良し悪しの多くは言語化しきれず、ユーザーの反応を見るまでわからない。トークンが強くするのは「意図どおりに作れたか」（verification）で、「正しいものを作ったか」（validation）は別の層で確かめる必要がある。

## 詳細

### DTCG 形式の基本

1 つのトークンは 3 つの要素を持つ。

| キー | 中身 |
|---|---|
| `$value` | 値。`{primitive.color.blue.500}` のように波括弧でパスを書くと別トークンを参照（エイリアス） |
| `$type` | `color`・`dimension`・`fontFamily`・`shadow`・`duration` など。グループに書けば配下に継承される |
| `$description` | 意味・用途の説明 |

安定版 2025.10 では値の書式が変わっている。color は `colorSpace` と `components` を持つオブジェクト（`hex` は任意のフォールバック）、dimension は `value` と `unit` を持つオブジェクトで、`"#0066CC"` や `"16px"` のような文字列は旧ドラフトの書式として無効。また DTCG ではトークンが子を持てないので、`primary` をトークンにしたまま `primary.hover` と階層を切れない。状態は `primaryHover` のように役割名に付けるか、最初から階層に切るかのどちらかに揃える。

### AI 向けに書くときの 5 つのポイント

1. **`$description` を指示書として書く** — 「メインの青色」ではなく、「最も重要な CTA にのみ使用。装飾目的のアイコンや背景には使用禁止」のように Do と Don't を書く
2. **セマンティック層だけを参照させる** — プリミティブ（生の値）とセマンティック（役割）の 2 層をエイリアスでつなぎ、`AGENTS.md` / `CLAUDE.md` に「`semantic.*` 以外とハードコード値は使わない」と書く
3. **命名を予測可能にする** — `種類.対象.役割`（`semantic.color.border.focus`）のような一般的なパターンに揃える。`brandColor1` や `specialBox` は誤推測を招く
4. **`$type` を明記する** — CSS などに変換するときの単位の取り違えを防ぐ
5. **コンポーネント固有の第 3 層は最小限に** — `button.primary.bg.color` まで作ると JSON が肥大してコンテキストを圧迫し、選択に迷う原因にもなる

### concept / tokens / spec の 3 ファイル構成

人間が最初に用意する文書を役割で分ける。

| ファイル | 中身 |
|---|---|
| `concept.md` | ターゲット、提供価値、**トレードオフの判断基準**（「A と B が衝突したら A を取る」）、NG 例 |
| `tokens.json` | DTCG 形式のデザイントークン |
| `spec.md` | 画面・要素の一覧、Given-When-Then のユーザーフロー、制約、受け入れ基準と**その検証方法** |

ここから PRD（やらないことを先に書く）→ `spec.md` → AI が分解した `plan.md` を人間がレビュー → 1 タスクずつ実装と自動検証 → 意匠面の人間レビュー、と[仕様駆動開発](/blogs/wiki/concepts/spec-driven-development/)のループで回す。トークンは検証にもつながる。

- **Stylelint** の `color-no-hex`・`unit-disallowed-list` などでハードコード値を禁止し、トークンから生成した `tokens.css` だけを除外する
- **Playwright** で計算済みスタイルを確かめる。テスト側の期待値はあえて生の値（`rgb(220, 38, 38)`）で書くと、トークンの値が意図せず変わったときに気づける
- **axe-core** のアクセシビリティ検査は、ダイアログを開いてから走らせないと中身を検査せずに合格する（[陽性対照](/blogs/wiki/concepts/positive-control/)で確かめる価値がある）

運用上のルールは 2 つ。同じタスクで 3 回落ちたら人間に渡す（原因は実装より spec やトークン側の矛盾であることが多い）、検証コードの変更は人間の承認制にする（AI はテストを緩めて合格させることがある）。レビューで見つけたズレはチャットで直させず、振る舞いのズレは `spec.md`、値のばらつきは `tokens.json` の `$description`、判断の方向のズレは `concept.md` に戻して直す。そうしないと次のタスクで再発する。

### デザインハーネス批判：ルールで測れる範囲

ルールやデザインシステムを AI に渡してデザインを生成・評価させる発想は「デザインハーネス」と呼ばれる。takanorip 氏の論考「デザインハーネスという虚像」はこれに異を唱え、評価ループにユーザーがいない、デザインに「当たり前品質」の線はない、第一印象は後から覆せない、デザインは Markdown のルールだけでは評価しきれない、などを論じた。

ブログ記事ではこれを層に分けて読み直している。

| 層 | 中身 | コードでいえば |
|---|---|---|
| ① 生成時 | ルール・トークンを渡して生成させるハーネスそのもの | コーディングエージェントのハーネス |
| ② リリース前の内部確認 | Linter・AI・デザイナーによるチェック | CI のテスト・Linter |
| ②' 全ユーザーに出す前のユーザー検証 | ユーザビリティテスト・インタビュー・限定公開 | カナリアリリース |
| ③ リリース後の運用 | 全ユーザーの評価を観測して ① に戻す | 本番の利用状況の観測 |

コードでハーネスが効くのは「② で測れる範囲が広い」「③ でのやり直しが安い」からで、デザインはどちらも弱い。言語化できないもの（デザイナーの暗黙の判断と、ユーザーの反応）があり、悪い第一印象は書き換えられないからだ。3 層のままだとリリース前に一発で当てる「スーパーマン」が要るが、②' を置けば、言語化を経ずに観察で反応を確かめつつ、損失を見た人の範囲に抑えられる。

デザイントークンとの関係で整理すると次のようになる。

- **言語化できる・すべきもの**: デザインコンセプト（誰に、何を、どう感じてほしいか）と、アクセシビリティやユーザビリティの原則などの機能面。トークンと `concept.md` はここを担う
- **言語化が難しいもの**: 原則どうしのトレードオフ、美しさやブランドらしさといった意匠面
- **事前には書けないもの**: ユーザーに実際に効いたか。②' と ③ で観察するしかない

コンセプトは「親しみやすい」ではなく「初めての人でも迷わずに予約を終えられる」のように、外れたことが判定できる粒度で書く。そうすれば ② のチェックにも ②' の検証項目にも落とせる。ルールで担保できるのは主に最低ラインの側なので、② の自動化で浮いた時間を ②' やより良いデザインに使えているかを問うのが、ハーネスの考え方をデザインに持ち込むときの要点になる。
