## 概要

AI がコードを書く速度に人間のレビューが追いつかず、レビューは多くのエンジニアにとってボトルネックかつ苦痛になっている。XP の原則でいえば Mutual Benefit（相互利益）の問題である（[エクストリーム・プログラミング](/blogs/wiki/concepts/extreme-programming/)）。

ただしレビューは**複数の役割の束**なので、廃止するなら役割を分解して、それぞれに代替手段を割り当てる必要がある。欠陥・規約・セキュリティは自動化でかなり補えるが、設計の一貫性・知識共有・育成は自動化しにくく、人の仕組みを別枠で用意する。現実的な落とし所は全廃ではなく「**高リスクな変更だけ人がレビューする**」形である。

## 詳細

### レビューの価値はバグ取りだけではない

Microsoft Research の調査（Bacchelli & Bird, ICSE 2013）では、開発者がレビューに期待する一番の役割は欠陥の発見だったが、実際に得られていたのは知識共有・チーム内の状況把握・別解の発見が中心だった。バグ取りだけを見ると、廃止したときに何が抜けるかが見えない。

### 8 つの役割と代替手段

| # | 役割 | 主な代替手段 | XP の対応 |
|---|---|---|---|
| 1 | 欠陥の発見 | テストを先に書く、CI で全テスト、ミューテーションテストで質を確認 | Test-First、CI、Ten-Minute Build |
| 2 | 規約・スタイル | linter / formatter を CI で強制、pre-commit | — |
| 3 | セキュリティ・危険な変更 | SAST、依存関係スキャン、シークレット検出、危険なパスだけ人が必須 | Redundancy |
| 4 | 設計の一貫性 | ADR、アーキテクチャテスト、AI 向けルールファイル | Incremental Design |
| 5 | 知識共有・属人化防止 | ペアプロ・モブプロ、マージ後に読み合う会、変更要約の共有 | Pair Programming、Shared Code |
| 6 | 若手の育成 | ペアプロ、レビューとは別のメンタリング時間 | Pair Programming、Humanity |
| 7 | 本番障害の防止 | フィーチャーフラグ、カナリア、監視、即時ロールバック | Daily / Incremental Deployment |
| 8 | 責任の所在 | 作者がマージの責任を負い、障害は根本原因分析で仕組みに | Accepted Responsibility、Root-Cause Analysis |

1〜3 と 7 は機械やデプロイの仕組みに移しやすく、2 はそもそも人が見る必要がない。4〜6 は人の仕組みでしか補えず、8 はチームの約束事である。XP の **Redundancy** のとおり、外した穴を 1 つの手段で埋めず複数を重ねる。

### 人が見ていたことを CI に移す

| 人が見ていたこと | 機械の検証 | 例 |
|---|---|---|
| 書き方の規約 | linter / formatter | ESLint、Ruff、Prettier |
| 型の整合 | 型チェック | tsc、mypy |
| 層の依存ルール | アーキテクチャテスト | ArchUnit、dependency-cruiser、import-linter |
| 脆弱性 | 静的解析・依存スキャン | CodeQL、Semgrep、Dependabot |
| 秘密情報 | シークレット検出 | gitleaks、Secret scanning |
| テストが効いているか | ミューテーションテスト | Stryker、mutmut、PIT |

最後の行が AI 時代には特に重要。LLM は**テストを通すためにテスト側を書き換える**ことがあるので、「緑」だけでは品質の担保にならない（[ミューテーションテスト](/blogs/wiki/concepts/mutation-testing/)）。「テストも書いて」ではなく「テスト駆動で実装して」と指示するのも効く。

### 全件必須から「リスクに応じて必須」へ

- **人のレビューを残す**: 認証・認可、課金、個人情報、DB マイグレーション、インフラ設定、公開 API
- **自動ゲート通過でマージ可**: テスト付きの小さな変更、内部リファクタリング、ドキュメント

この振り分けを**人の判断に任せない**のが要点。「今回は小さいから不要」と作者が決められると抜け道になる。

GitHub の標準設定では作りにくい。「Require review from Code Owners」は承認数と組み合わせて働き、承認数を 1 以上にすると CODEOWNERS 対象外の PR にも承認が要り、0 にするとコードオーナーのレビューが強制されなかったという報告がある。そこで振り分けを**必須ステータスチェック**として実装する。

1. Actions で PR の変更ファイルを取得する
2. 高リスクなパスに触れていなければ成功させる
3. 触れていれば担当チームの承認を API で確かめ、無ければ失敗させる（`pull_request_review` でも起動して再評価）
4. ルールセットは承認数 0 のまま、このチェックを必須にする

チームの所属確認には組織のチーム情報を読む権限が要り、既定の `GITHUB_TOKEN` では足りない可能性が高い（GitHub App か権限を絞ったトークン）。フォークや Dependabot の PR ではトークンが読み取り専用でシークレットも渡らないので、その場合の振る舞いも決めておく。CODEOWNERS はレビュー依頼の自動化用に残せる。設定の組み合わせで挙動が変わりうるので、テスト用リポジトリで「低リスクは承認なしでマージでき、高リスクは止まる」を実際に確かめてから入れる。

### AI レビューを入れるときの注意

- **書いた AI と同じモデルにレビューさせない**。規模や提供元を変えて盲点をずらす（[maker-checker](/blogs/wiki/concepts/maker-checker/)）
- **指摘には証拠を付けさせる**。再現テストやコマンドの実行結果がない指摘は、人の確認の手間を増やすだけ
- **設計の一貫性と知識共有は AI レビューでは補えない**。ルールファイルは書く側の AI を方針に沿わせるもので、レビューの代わりではない。AI が読んでもチームの誰かが理解したことにはならない

### いちばん失われやすいのは知識共有

廃止すると「チームの誰もそのコードを読んでいない」状態が生まれる。レビューを**マージを止める関門**と**知識を共有する場**に分け、前者は自動化と振り分けで軽くし、後者は別枠で残す。

- ペアプロ・モブプロは難しい変更や新メンバーが関わる変更に絞る
- 週 1 回 30 分、その週にマージされた主な変更を眺める（承認のための読み方ではないので負担が小さい）
- AI に PR の要約を書かせてチャンネルに流す

必須レビューをやめることは品質への要求を下げることではなく、人の注意という限られた資源を、本当に人が見るべき変更とチームの知識を育てることに振り向け直すことである。
