## 概要

Text-to-SQL は、利用者の自然文の質問から LLM が SQL を書き、DB に実行して答える方式。試作はスキーマをプロンプトに入れるだけで動くが、難しいのは「動く SQL」ではなく**「正しい SQL」**を出すこと。業務システムに組み込むときは、精度に加えて**権限と計算の正本**をどこで守るかが設計の中心になる。

## 詳細

### 誤りは文法より「意味の推測」で起きる

LLM がつまずくのは、スキーマに書かれていない意味を推測で補う部分。どれも SQL はエラーにならず、もっともらしい数字が返るので気付きにくい。

| つまずく点 | 例 | 補う知識 |
|---|---|---|
| 言葉と列の対応 | 「売上」が英語の略語の列。似た列が複数ある | 用語・同義語と列の対応 |
| 指標の計算式 | 単価×数量か明細金額か、返品を引くか | レビュー済みの計算式 |
| 結合の経路 | 顧客→州の経路が配送先と郵送先の 2 通り | 使うべき結合キー |
| 答えられない質問 | データにない「広告費」を似た列で計算する | 何が定義されているか |

これを補う層が[オントロジー](/blogs/wiki/concepts/ontology/)や[セマンティックレイヤー](/blogs/wiki/concepts/semantic-layer/)。dbt Labs の 2026 年 4 月のベンチマーク（11 問・1 データセットの小規模評価で、実施者は製品提供元）では、全体の正答率はセマンティックレイヤー 72.7% 対 生テーブルへの Text-to-SQL 64.5%。定義済み指標の範囲に限ると 100% 対 5〜6 割台だった。定義の外の質問にはセマンティックレイヤーは答えられないので、両方を持つ前提で読む。

### 業務システムの中核に据えない理由

会計・原価管理のように**利用者ごとに見える範囲が決まっている**システムでは、Text-to-SQL を中核にすると次の問題が出る。

1. **行単位の権限を通らない** — SQL は接続用 DB ユーザーの権限で実行され、アプリの権限（Django の django-rules・django-guardian、所属で絞るクエリセットなど）を通らない。共通の API トークン 1 つで呼べば全員が同じ権限になり、他事業所の数字が返る。MySQL には PostgreSQL の RLS 相当がなく、DB 側で防ぐのも難しい
2. **数字の正本がアプリのコードにある** — 締め処理・端数処理・取消の扱いを SQL で書き直すと二重管理になり、チャットと画面の数字が食い違う
3. **データが外に出る** — スキーマ・サンプル値・質問文が LLM に渡る。推論先はセルフホストか承認済みエンドポイントにする
4. **別スタックの運用** — 専用サービスを使うなら、認証・バックアップ・監視が別に増える

### 代わりの中核：ツール呼び出し

LLM には**どのツールをどの引数で呼ぶか**だけを決めさせ、ツールはログイン中の利用者として既存の業務ロジックを呼ぶ（Function Calling / Tool Use）。

- 利用者は LLM の引数にせず、アプリが `request.user` などから渡す
- 照会専用にし、書き込み系ツールは用意しない
- 「存在しない」と「権限がない」を同じ応答にする
- 件数上限・画面へのリンク・ログを付け、答えられない質問は答えないと指示する
- まず頻出質問の上位 5〜10 個から。増えたら業務領域ごとにまとめ、用語集（オントロジー）で `description` を正確に書く

### ハイブリッド運用：役割で Text-to-SQL を開放する

ツールは用意した範囲でしか答えられない。管理本部・監査担当の「起票者と承認者が同じ伝票」「締め後に修正された伝票」のような一度きりの問い合わせには Text-to-SQL が要る。こうした役割はもともと全社データを見る権限を持つので、行単位の権限の問題が消える（子会社・機密部門の制限がないかは確認する）。

- **振り分けはアプリが役割で決める**（例: `has_perm("chatbot.use_text_to_sql")`）。LLM に権限を広げさせない
- **ツールを優先**し、答えられないときだけ Text-to-SQL へ
- 接続先は読み取り専用レプリカか分析用 DB、読み取り専用ユーザー、タイムアウトと件数上限付き
- 生成した SQL を必ず見せ、結果は**調査用の数字**として扱う
- 誰が何を聞きどの SQL が走ったかを監査ログに残す

### 終着点にしない：改善サイクル

Text-to-SQL は同じ要件でも毎回 SQL を作り直す（1 回数十秒、毎回少し違う SQL になりうる）。ログを「利用者が本当に必要な照会の一覧」として使い、繰り返し来るものは開発者が決定論的に実装して昇格させる。

1. 質問・役割・方式・SQL・実行時間・評価を記録
2. 意図ごとにまとめて件数と重要度で候補を選ぶ
3. 生成 SQL を仕様の下書きにして、権限と正本の計算に沿った API とテストを書く
4. ツールとして公開（一般利用者も即答できる）
5. Text-to-SQL に回る割合を測る

分析基盤があれば昇格先は 2 つになる。帳票と一致すべき「特定レコードの今の値」は業務 API に、分析用で足りる「集計・推移」は dbt の指標定義に置く。接続先も読み取り専用レプリカから DWH の mart（説明付き・PII ハッシュ化済み・指標定義あり）に移すと精度が上がる（[AI ネイティブなデータ分析基盤](/blogs/wiki/concepts/ai-native-data-platform/)）。

### 導入前の準備

用語の定義は、仕様書やコードを網羅的に解析するより**過去の問い合わせ事例（需要側）から対象を絞り、コードと仕様書（供給側）で裏付ける**のが効率的。事例から同義語・頻度・正解つきの評価用質問集・最初のツール群が取れる。「締め済み」の条件や正本の計算など DB にない意味はコードから補う。

### 自前か既製か

自前で難しいのは、メタデータからの用語生成、外部キーの推定とデータでの裏付け、SQL の検査・修復、回答可否の判定、評価環境。最初は [NVIDIA Auto Ontology](/blogs/wiki/tools/nvidia-auto-ontology/) などで PoC し、監査担当の実際の質問 20〜50 件で正答率を測ってから決める。価値があるのは実行環境ではなく作り込んだ定義のほう。
