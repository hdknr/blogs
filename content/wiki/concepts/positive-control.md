## 概要

陽性対照（ポジティブコントロール）は生物学・医学の実験の言葉で、「必ず陽性になる」と分かっている試料を本番の試料と一緒に検査し、**検査の仕組みそのものが働いていること**を確かめる手順。陽性対照が陽性にならなければ、その回の結果は「陰性」も含めてすべて信用できない。

IT では「陽性対照」という訳語はあまり使われず、ヘルスチェック・Watchdog・EICAR テストファイル・サニティチェック・ミューテーションテストなど分野ごとの名前で同じことをしている。共通の狙いは、[沈黙する失敗](/blogs/wiki/concepts/silent-failure/)（検知の仕組みが死んでいるのに「異常なし」と表示され続ける状態）を防ぐこと。

## 詳細

### なぜ要るのか

「アラートが来ない」「テストが通る」「ウイルスは検出されなかった」「反例なし」は、検知の仕組みが正常な場合と死んでいる場合とで**見た目がまったく同じ**になる。陰性の結果だけを見ていても両者は区別できない。必ず陽性になるはずの入力が陽性になるのを見て、初めて陰性を「本当に異常がない」と読める。

### 分野ごとの現れ方

| 分野 | 陽性対照に当たる仕組み | 確かめていること |
| --- | --- | --- |
| サーバー監視 | ヘルスチェック（`curl -fsS --max-time 5 .../healthz`）。応答が来ないことを異常とみなす | サーバーやネットワークが止まっていないか |
| アラート基盤 | 常に発火するアラート（kube-prometheus の `Watchdog`、条件 `vector(1)`）を外部の Dead man's switch に送り続ける | Prometheus・Alertmanager・通知経路そのものが生きているか |
| cron ジョブ | 成功時だけ ping を送り（Healthchecks.io など）、来なければ通知 | ジョブが黙って止まっていないか |
| セキュリティ検査 | EICAR テストファイル（68 バイトの無害な文字列）を流す | 検知 → 隔離 → 通知の経路が最後まで動くか |
| 機械学習 | 1 バッチだけで学習させ、損失がほぼ 0 まで下がる（過学習できる）かを見る | 損失関数・ラベル・前処理にバグがないか |
| センサー・製造ライン | わざと不良品を通す | センサーが故障して「全部良品」になっていないか |
| ソフトウェアテスト | コードをわざと壊し、テストが落ちることを見る（[ミューテーションテスト](/blogs/wiki/concepts/mutation-testing/)） | テストがバグを検出できる作りか |

### 対象が一段ずつ外側に移る（spec-loop の例）

Claude Code プラグイン spec-loop は、否定的な結論を「道具が空振りしていない証拠」とセットでしか出させない設計で、陽性対照を 3 段に置いている。

| 段 | 疑っているもの | 陽性対照 |
| --- | --- | --- |
| 仕様の形式検査（Formal Checker） | 仕様を書き起こしたモデル | ルールを 1 つ壊したモデルで反例が出る。加えて正常な状態に到達できること |
| 検査器の点検（`check-tlc.py` / `check-alloy.py`） | 検査器の起動コマンド | 通るモデルで `No error has been found`、違反するモデルで `is violated` が出る |
| スキルの Eval | 採点する grader | 誤った振る舞いを 1 行で直接させるプロンプトで grader が不合格になる |

要点:

- **陽性対照は毎回やり直す**。前回反例を出したことは、今回の検査が空振りしていない証拠にならない
- 最小の構成（ふつう 2〜3）で正常な状態に到達でき、陽性対照で反例が出るなら、[TLA+](/blogs/wiki/tools/tla-plus/) の検査構成は広げない。陽性対照は構成の大きさを決める根拠にもなる
- grader の `not_contains` は、エージェントが何もしなかった実行でも緑になる。正規表現の取りこぼしや `path` の指し間違いも緑に化ける
- 「修正前のスキルで不合格になる」（振る舞いの差）と「対照で不合格になる」（grader が不合格を出せる）は**別の問い**として grader ごとに記録する
- 陽性対照は**どの壊れ方を検出できるかまでしか保証しない**。「ファイルが無い」で不合格になっても、「中身が違う」で不合格になるかは別に確かめる

### 導入の 4 ステップ

1. 「〜は起きていない」「0 件」と結論する仕組みを探す（監視・アラート・スキャン・テスト・データ検証）
2. それが必ず「起きた」と判定する入力を用意する（ダミーの異常、既知の正解データ、壊したコード）
3. その入力を定期的に、または結論を出す前に流す
4. 陽性対照が陽性にならなかったら、それ自体を異常として通知する
