## 概要

複数の工程・AI・ツール・人間の確認ポイントを**ノードとエッジの関係**として設計する実践。「誰が並列で、誰が待ち、どこで再試行・エスカレーションするか」という協調構造を、グルーコードで書き散らすのではなく**一度だけ宣言的に記述する**。[AIエージェント設計の5レイヤー](/blogs/wiki/concepts/ai-agent-design-layers/) の最上位レイヤーにあたる。

## プロンプト → ループ → スワーム → グラフ

AI エージェント運用の進化は 4 段階で整理できる。

| Stage | 段階 | 特徴 |
|---|---|---|
| 1 | **プロンプト** | 人がプロンプトを打ち出力を読む。**人間自身がループ**であり、ラップトップを閉じれば何も残らない |
| 2 | **ループ** | プロンプトをスクリプトで包みスケジュールで発火。ループが状態を持ち、閉じても走り続ける |
| 3 | **スワーム** | ループを役割ごとに多数のエージェントへ扇状に展開。ただし調整は手書きのグルーコード |
| 4 | **グラフ** | 協調構造を一度だけ記述。ノードがエージェント、エッジがデータの受け渡し |

### 段階モデルは「名詞」ではなく「性質」で使う

この 4 段階を「導入するツール」の名前として読むと誤診する。**並列がネイティブか／失敗がノードに限定されるか**といった*性質*で自己診断すべきである。実在の自律トレーディングシステムを診断した事例では、「スワーム導入」というタスクは存在せず**すでにスワームだった**という結論に至っている。

## グラフの3要素

LangGraph はエージェントワークフローを 3 要素で表現している。

- **State（状態）** — 現在どこまで進み、何が判明しているかを記録したデータ
- **Nodes（ノード）** — 仕事をする場所。決定論的なコード、単一の LLM 呼び出し、内部にループを持つエージェントまるごと
- **Edges（エッジ）** — 次にどこへ進むかを決める接続。結果や State に応じた条件分岐を含む

## なぜスクリプトは壊れるのか

スクリプトは次の 3 つの瞬間に壊れ、グラフはこれを構造として吸収する。

1. あるエージェントが別のエージェントの完了を待つ必要が出たとき
2. 状態をサイクル（実行の周回）をまたいで保持しなければならなくなったとき
3. 複数ループを並列に回す必要が出たとき

## 偽エッジを消す

多段エージェントを組むと、ほとんどの人が**一列の行列**を作る。ステップ 1 → 2 → 3 と前が終わるのを律儀に待つが、**その半分は最初から何も待つ必要がなかった**。

> エッジは「その後で」ではなく、**データが実際に渡る**ときだけ存在する。

データが渡らないエッジ＝**偽エッジ**を消すだけで待ち時間の多くが消える。コストはゼロ。

## 反対ルール — グラフが買えるのは「幅」だけ

グラフエンジニアリングで最重要の歯止め。

> グラフが買えるのは**幅**（同時に走らせられる仕事の量）だけで、**「判断の質」は買えない**。仕事が分割できないなら、エージェント 1 体のままでいい。

工程が 1 つしかないのに 5 体の AI を使えば、費用と待ち時間が増えるだけである。AI 同士の伝言で情報が変形することもある。

### 設計の勘所

- **確実性が必要な場所は経路を固定する** — 請求・削除・公開・契約は、決められた経路と人間の承認を通す
- **創造性が必要な場所は裁量を渡す** — 調査方法や文章表現のように正解が一つでない部分は AI に任せる

## 実装例：多因子アルファモデル

ヘッジファンドが使う多因子アルファモデルを **7 つの並列な因子ノード＋4 つの逐次な調整ノード**の 11 ノード・グラフとして組む設計が知られている。因子構築は並列、検証ゲートは逐次に置く。

重要なのは **maker-checker パターン**で、検証は必ず**作り手とは別のノード**にやらせる。調査した本人は自分の間違いを見つけられないためである。

## Claude Code の動的ワークフロー

Claude Code の**動的ワークフロー（Dynamic Workflows / Workflow ツール）**は、このグラフを直接書くための仕組み。Claude が素の JavaScript でオーケストレーション用スクリプトを書き、サブエージェントのフリートがそれを実行する。`agent()` / `parallel()` / `pipeline()` / `schema` を組み合わせる。

**調整レイヤ自体はモデルのトークンを消費しない**（コードだから）。ただし「0 トークン」は調整レイヤに限った話で、**実行全体のトークンは会話でやるより増える**点には注意が必要。

実装ロードマップは 4 ブロック構成で整理されている。

| ブロック | 内容 |
|---|---|
| 01–04 | 今あるグラフを見る（偽エッジの削除） |
| 05–08 | フリートを動かす（`parallel()` / `pipeline()` で並列化） |
| 09–11 | 出力を信頼する（敵対的検証とノード隔離） |
| 12–14 | 破産しない（トークンコストとモデルの段階化） |
