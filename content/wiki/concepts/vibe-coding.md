## 概要

構文の記述やデバッグを AI エージェントに丸投げし、「こんな感じ」という曖昧な指示でコードを作らせる開発スタイル。Andrej Karpathy が 2025 年 2 月の投稿で広めた言葉で、元の定義は「雰囲気に身を任せ、コードの存在すら忘れる」「いつも Accept All で、もう diff は読まない」というもの。Karpathy 自身は使い捨ての週末プロジェクトなら悪くない、という位置づけで書いていた。

元の定義の核心は**生成物を読まずに受け入れること**（検証の放棄）にある。チーム開発や業務システムに持ち込むと、判断の経緯が残らない差分と、誰も決めていない仕様の実装という形で問題が表に出る。

## 詳細

### 「バイブしているのは仕様のほう」という見方

よく語られる整理では、コードはコンパイラを通る厳密なテキストであり、感覚で処理されているのは「要求の言語化」と「仕様の確定」のほうだとされる。人間の曖昧な指示を LLM が統計的な常識で補完し、「動いたからヨシ！」で受け入れる。暗黙知を爆速でプロトタイプにできる一方、エッジケースの放置と、再プロンプトのたびに暗黙の仕様が書き換わる「もぐら叩き」がリスクになる、という見立てである。

この見立てには一理あるが、次の点で修正が要る。

- **コードの側も厳密ではない**：LLM の生成はサンプリングに基づくので、同じプロンプトでも出力は変わりうる。型検査と構文解析を通っても、仕様と違う振る舞いのコードは普通に書ける。AI が埋めた仕様は生成されたコードの中にしか存在せず、コードが暗黙の仕様の唯一の置き場になる
- **検証の放棄が抜け落ちる**：「仕様の決定がバイブしている」と一点に絞ると、Karpathy の元の定義と話がかみ合わない
- **「AI が埋めた穴を見抜く力」は後追いの対策**：見抜けるのは見えた穴だけ（例外処理・排他制御・認証トークンのライフサイクルは動かしても目に入らない）。着手前の仕様がなければ照らし合わせる先もなく、「もぐら叩き」は AI の気まぐれというより、壊れたと判定する仕様が最初から無いことから起きる。誰も決めていないので、なぜそう決まったかを説明できる人もいない

AI が埋めるのは「最大公約数的なベストプラクティス」というより「よく見かける書き方」で、安全でない初期値も含まれる。実例は [医療データ流出の事例](/blogs/posts/2026/04/vibe-coding-security-risk/) や [セキュリティの落とし穴](/blogs/posts/2026/05/vibecoding-security-checklist/) を参照。

### 業務要件の決定権

「誰が何をできるか」「どの条件で受け付け、どの条件で断るか」「失敗したら利用者にどう見せるか」といった業務要件は、業務を持つ側（利用者・業務部門・発注者）が決める。開発者が自分で決められるのは実装方法・アーキテクチャ・運用といった技術の範囲で、業務要件については選択肢と技術的な帰結（費用・難しさ・運用負担）を示すところまで。

Vibe Coding で AI が埋めている空白の多くは、例外時の扱いや権限の範囲という業務要件である。開発者でさえ決めてはいけないものを AI が決め、それを開発者が「見抜いて境界を引く」ことにすると、決定権が気づかれないまま開発者に移る。

### 根本原因：人間が定義しきれない

AI に仕様を埋めさせてしまうのは、決めるべき人が要求・条件・例外を定義しきれないからで、Vibe Coding はその症状にあたる。理由は少なくとも 4 つある。

1. 暗黙知は当たり前すぎて書かれない
2. 例外は組み合わせで爆発する（条件 3 つ × 3 通りで 27 通り、順序や同時実行でさらに増える）
3. 見て触らないと分からない要求がある
4. 書いた本人は自分の書き漏れに気づけない

従来はシステムコンサルタント（ビジネスアナリスト）がヒアリング・決定表・画面モックで決められる形に整えてきたが、品質は個人の力量に依存した。Vibe Coding ではこの役割すら抜け落ち、実装が安くなった分、曖昧な仕様が大量のコードに増幅される。

対案の共通原則は「**AI には空白を埋めさせず、表に出させる**」こと。業務要件の空白は業務を持つ側に返し、技術の空白は開発者が決めて記録する。4 つの理由への具体策（場面と選択肢で問う・機械に総当たりさせる・捨てるプロトタイプ・別の目でのレビュー）は [仕様駆動開発](/blogs/wiki/concepts/spec-driven-development/) にまとめた。

### 成果に影響する要因（CHI2026 研究）

CHI2026 採択論文の実験から、バイブコーディングの成果を左右する要因が明らかになった。

| 要因 | 傾向 |
|------|------|
| CS 基礎知識 | あるほど成績が高い |
| 文章力 | 高いほど成績が高い |
| LLM 利用頻度 | **高いほど成績が低い**（意外な逆相関） |

- CS 基礎知識：コードを書かなくても、問題分解・アルゴリズム的発想・データ構造の概念が AI への指示を構造化する
- 文章力：文章力が高いほどプロンプトの品質が上がり、アプリの出来がよくなる
- LLM ヘビーユーザーの逆説：LLM を多用するほど自分で言語化する機会が減る可能性がある。もともと言語化が苦手な人が LLM に頼りやすいとも考えられる

細かいルール記述より価値観駆動の指示が効くという側面もあり、[CLAUDE.md](/blogs/posts/2026/03/claude-md-less-is-more/) を短く保つ運用とも関係する。

### チーム開発での批判

- **判断の経緯が残らない巨大な差分** — 意図だけ伝えて隙間をモデルに埋めさせると、なぜそう書いたかの記録がない大きな差分が出る。レビューは「考古学」になり、テストはうっかり省かれる。逆に完全な仕様を先に書こうとするウォーターフォールも、仕様が膨らんで変更を阻むか無視される。その中間として「次の小さな仕様だけを書き、レビューし、テスト付きで実装する」を繰り返すのが [Spec Loop](/blogs/wiki/concepts/spec-driven-development/)
- **レビューの丸投げ** — vibe coding で作った巨大 PR を他人にレビューさせるのは、XP の原則 Mutual Benefit（相互利益）の違反例として挙げられる。書く側は数秒でも、読む側には数十分の負担が転嫁される（[エクストリーム・プログラミング](/blogs/wiki/concepts/extreme-programming/)）

### Vibe Hacking（対義概念）

Vibe Coding の反対側が Vibe Hacking（AI による攻撃の民主化）。攻撃者が AI にターゲットを指定するだけで脆弱性発見・エクスプロイト作成が自動化される脅威。
