## 概要

オントロジーは、もとは哲学の「存在論」。情報科学では**ある分野にどんな概念があり、何を意味し、互いにどう関係するかを機械が読める形で定義したもの**を指す。「用語辞典」と「概念の関係図」を合わせたものと考えるとよい。記号的 AI やセマンティックウェブ（RDF / OWL）の系譜にあり、2026 年には LLM にデータベースを問い合わせさせるための「業務上の意味の層」として再び注目されている。

## 詳細

### 何を持つか

販売業務なら次のような知識がオントロジーになる。データ分析の文脈では、最後の計算ルールまで含めて扱うことが多い。

- **概念** — 顧客・注文・請求明細・商品・州
- **意味と同義語** — 「売上」は revenue・売上高とも呼ぶ
- **関係** — 顧客は注文を出す。顧客は都市に属し、都市は州に属する
- **計算の決まり** — 売上は請求明細の金額の合計

### スキーマとは別物

スキーマは「データがどう保存されているか」（テーブル・列・型・制約）、オントロジーは「そのデータが業務上なにを意味するか」。`sales.invoicelines.extendedprice` という列名から、それが売上として数えるべき金額かは分からない。外部キーも「つなげられる」ことまでで、「この質問ならどの経路でつなぐべきか」は示さない。

### LLM に効く理由

[Text-to-SQL](/blogs/wiki/concepts/text-to-sql/) で LLM がつまずく「言葉と列の対応」「指標の計算式」「結合の経路」「答えられない質問」を、あらかじめ定義した知識で埋める。LLM の担当を言葉の理解と SQL の記述に狭めることで、次が得られる。

- **正確さ** — 動くが間違った SQL が減る
- **一貫性** — 誰が聞いても同じ式・同じ経路
- **説明可能性** — 使った定義を回答に添えられる
- **誠実さ** — 定義のない概念は「答えられない」と返せる
- **統制** — 計算式を 1 か所直せば以後の回答すべてに効く

Text-to-SQL を使わずツール呼び出しで答える場合でも、用語・同義語・関係の整理はツールの `description` を正確に書く土台になる。「コスト」「経費」と聞かれて「原価」のツールを選べるようになる。

### 作る手間をどう減らすか

数百テーブルの用語・計算式・結合を人が一から書くのは現実的でない。2 つの方向がある。

| 方向 | 材料 | 例 |
|---|---|---|
| 供給側から自動生成 | DB のメタデータ・サンプル値・クエリ履歴 | [NVIDIA Auto Ontology](/blogs/wiki/tools/nvidia-auto-ontology/) が草案を作り、推定した結合をデータで裏付け、人が認定する |
| 需要側から絞る | 課題管理に残る過去の問い合わせ事例 | 頻出の意図から対象の用語を絞り、コードと仕様書で裏付ける |

業務システムで大事な意味は DB ではなく**コードと仕様書**にあることが多い。「締め済み」の判定条件、複数列からなる業務キー、正本の計算関数、論理削除の扱い、必要な権限はメタデータからの草案に出てきにくい。モデル・URL ルーティング・権限名のように機械的に取れる部分はフレームワークのイントロスペクション（Django の `_meta`・URL リゾルバー）で自動生成し、残りは人が確かめる。

### 運用の注意

- **コードを正本、オントロジーは派生物**とし、自動で作り直せる部分を最大にする
- 最初からグラフ DB は要らない。リポジトリの YAML / JSON の対応表で十分
- 「業務用語 ↔ モデル・項目 ↔ 正本の計算 ↔ API ↔ 画面 ↔ 必要な権限」の対応表があると、繰り返し来る質問が既存 API で答えられるかをすぐ判断できる
- 抜き出した権限の定義でアクセス制御をしない。制御はアプリの中で行う
- 分析基盤を併設したら、分析指標の説明は dbt の `schema.yml` を正にし、[セマンティックレイヤー](/blogs/wiki/concepts/semantic-layer/)と用語を二重にしない
- 推論の質は入力の事実を超えない（OWL 推論でも元データの抜けは補えない）
